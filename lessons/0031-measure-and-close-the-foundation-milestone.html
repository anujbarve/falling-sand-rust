Measure and close the foundation milestone

Record repeatable tick, frame and memory measurements and make an evidence-based M0 decision.

Previously: Keep resident storage bounded. Keep that working result available before starting this lesson.

Why we need this now

A simulation that looks smooth on a modern laptop may fail on the target i3. We need a repeatable workload and separate measurements for a tick and the whole rendered frame. This module closes the foundation only when its claims have actual evidence.

Your result: Record repeatable tick, frame and memory measurements and make an evidence-based M0 decision.

01Freeze the workload before measuring

Use fixed dimensions, seed, camera, material counts and input sequence. The i3 reference active load is74624 cells at the specified720p view with margins; the reference1080p load is154624. Include a sand fixture and a50%-water fixture. State exactly which cells are active rather than quoting only visible counts.

Before this benchmark, the sequential four-phase chunk traversal should exist so the measured algorithm matches the intended update order. Keep it single-threaded until a footprint proof and measurement justify parallel dispatch. Benchmarking a different toy traversal would not establish the proposed architecture’s cost.

02Measure tick time and frame time separately

Use Instant around simulation work and around the complete frame’s CPU work, with a documented sampling interval. A20TPS simulation can still hitch if one synchronous tick takes40ms. Multiple ticks in one frame must be budgeted together. Record distributions or at least average and worst observed values, not only a flattering mean.

GPU presentation and OS scheduling can complicate frame measurement, so state what the timer includes. Do not label a CPU-only duration as complete display latency. The initial goal is honest comparable evidence, not a profiler dashboard with unexplained numbers.

03Use optimized builds and real hardware

Run cargo run --release for performance measurements. Debug builds are useful for development but not the agreed optimized performance target. Record CPU model, memory, OS, graphics device, resolution and build revision with the results. If the exact floor machine is unavailable, mark the result unverified rather than extrapolating a certification from the Mac.

Check that the graphics context opens and draws on that target GPU before spending weeks on more reactions. A supported-platform list does not prove old integrated graphics compatibility. If the floor fails, revise the target or renderer through an explicit design decision.

04Turn the measurement into a gate

The M0 report should answer: does sand meet the target, what do water timings show, is memory bounded under the current policy, and are threads needed next? Keep failing evidence and the selected response in the report. Dirty regions, a smaller capped view or later threading are options to evaluate, not invisible changes to acceptance conditions.

The worked timing fixture below demonstrates measurement mechanics only; its tiny synthetic loop is not a substitute for the real sand/water benchmark. End the episode with a reproducible command and a table of actual results, including any unresolved hardware access. Completion means making the decision honestly, not forcing every number green.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

use std::time::Instant;
fn main() {
    let mut values=vec![0_u64;74_624];
    let start=Instant::now();
    for tick in 0..600_u64 {
        for value in &mut values { *value=value.wrapping_add(tick); }
    }
    let elapsed=start.elapsed();
    println!("synthetic total={elapsed:?}");
    println!("synthetic mean per iteration={:?}",elapsed/600);
    std::hint::black_box(values);
}

Read what each part does

  1. The benchmark mechanics use black_box so the computed state remains observable to optimization.
  2. The synthetic loop has no physical meaning.
  3. Real M0 closure requires the actual simulation and graphics path.

Expected result

Timing values vary by machine and build. This synthetic example verifies timer use only; substitute the actual fixed simulation workload for the M0 report.

01

Compare build modes

Run the synthetic fixture in development and release profiles.

Need a hint?

Use cargo run and cargo run --release.

Worked solution

Record both commands and values, but use release for the game target. Do not treat the speed ratio as a universal Rust fact; it depends on workload and compiler decisions.

How to verify your result

The report names the profile and avoids mixing unlike measurements.

02

Expose a tail spike

Insert a deliberately expensive event in one tick of a test fixture.

Need a hint?

A mean can hide rare frame-breaking work.

Worked solution

Record every sample or the maximum alongside the mean. The exceptional tick should appear in the evidence even if the average remains small.

How to verify your result

The report does not certify smoothness from average time alone.

03

Write the M0 decision

Create a short table for hardware, workload, build, tick/frame timing, memory and verdict.

Need a hint?

Unmeasured is different from failed and passed.

Worked solution

Include pass/fail/unverified explicitly. Choose the next optimization only from measured bottlenecks, and keep the current changed-chunk cache limitation in the memory notes.

How to verify your result

Another person can reproduce the command and understand the verdict’s limits.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Performance seems far below expectations

What is happening: Measurements may use a debug build or include setup repeatedly.

Try this: Record profile and sampling scope; use release for the target workload.

Average FPS is fine but motion hitches

What is happening: Tail tick/frame cost exceeds the frame budget.

Try this: Measure individual tick and combined per-frame work.

The Mac result is called an i3 pass

What is happening: Different hardware was substituted for the acceptance machine.

Try this: Mark floor support unverified until measured on the claimed target.

Explain it without the example

Why does an acceptable average tick time not prove smooth 60 FPS?

Reasoning to compare

Long individual ticks or multiple ticks in one frame can exceed the frame period. Tail frame times and combined frame work matter too.
