Use a small trait for deterministic choices

Tests can force a left or right choice without changing simulation rules. Empty ranges and source state are specified.

Previously: Schedule independent work before adding threads. Keep that working result available before starting this lesson.

Why we need this now

A test needs sand to choose left while production needs a deterministic coordinate-based choice. Changing the simulation every time we test a direction would couple rules to the test harness. A narrow trait makes the choice source replaceable while the movement rule stays the same.

Your result: Tests can force a left or right choice without changing simulation rules. Empty ranges and source state are specified.

01Find the variation before inventing an abstraction

The varying behavior is “choose one of two valid directions,” not “be any possible material.” Material remains an enum because its alternatives are known and data-oriented. Define a trait only around the operation that needs multiple implementations. This keeps the interface deep enough to hide the source of a choice but small enough that a beginner can read the entire contract. Do not turn every struct into a trait simply because traits exist.

02Describe the contract in the method

The lab trait returns a boolean: true means choose left. A production interface might instead accept a bounded range or a context containing seed, tick and cell position. Whichever shape you choose, document it completely. Does calling the method mutate source state? Does the same context always return the same answer? A deterministic source should not rely on thread arrival order; a scripted test source may intentionally return a fixed answer to expose one branch.

03Read a generic bound as a requirement

In fn direction(source: &impl Choice), the helper can call methods promised by Choice without knowing the concrete source type. The compiler generates suitable code for the implementation used. We do not need trait objects, lifetime annotations or a plugin system for this seam. The useful fact is that one rule works with two sources and its callers supply the behavior explicitly. Keep the example small enough to inspect both implementations beside the rule.

04Use scripted choices to reveal hidden branches

Random integration tests can repeatedly miss a rare left or right path. A scripted source forces the branch now: put stone below a grain, air on the left, a trap on the right, then choose left and inspect the result. The coordinate-hash source is tested separately for repeatability and range. This separation gives two clear failures: movement logic is wrong under a chosen input, or the source does not satisfy its documented contract.

trait Choice { fn choose_left(&self) -> bool; }
struct Fixed(bool);
impl Choice for Fixed {
    fn choose_left(&self) -> bool { self.0 }
}
struct TickParity(u64);
impl Choice for TickParity {
    fn choose_left(&self) -> bool { self.0 & 1 == 0 }
}
fn direction(source: &impl Choice) -> i32 {
    if source.choose_left() { -1 } else { 1 }
}
#[test]
fn the_rule_accepts_scripted_and_tick_sources() {
    assert_eq!(direction(&Fixed(true)), -1);
    assert_eq!(direction(&Fixed(false)), 1);
    assert_eq!(direction(&TickParity(2)), -1);
    assert_eq!(direction(&TickParity(3)), 1);
}

Read what each part does

  1. Start by writing down the inputs and the result you expect from the first assertion. Read the helper from top to bottom, naming every branch and state change before running the test. The small fixture is deliberate: a landscape hides errors that a few cells expose.
  2. All four branch checks pass. TickParity is deliberately a trivial demonstration, not a statistically adequate production random hash.
  3. This complete headless example isolates one mechanism. It does not replace your existing game file or implement an entire milestone. After the tests pass, move the relevant rule behind the world interface introduced earlier, then repeat the same fixture through that interface. Keep rendering out of this test path.

01

Force both paths

Use one movement fixture and run it once with Fixed(true), once with Fixed(false).

Need a hint?

Only the injected source should change.

Worked solution

Assert left displacement -1 and right displacement +1 in the corresponding fixtures. Keep starting geometry identical so the direction source is the cause of the difference.

How to verify your result

Both movement branches have deterministic assertions.

02

Avoid hidden time

Would reading wall-clock time inside choose_left preserve replay?

Need a hint?

Ask whether identical recorded simulation inputs guarantee the same clock reading.

Worked solution

No. Wall-clock time is an external unrecorded input. Production deterministic choices should derive from recorded seed, executed tick, position and operation index.

How to verify your result

The source contract lists all inputs used.

03

Keep materials simple

Should adding Oil require implementing Choice for Oil?

Need a hint?

Choice models a decision source, not a substance.

Worked solution

No. Oil is a Material variant with properties. A movement helper may ask a separate Choice source to break a directional tie. The trait does not belong on every material.

How to verify your result

Material data and choice-source behavior remain separate.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Trait method is unavailable

What is happening: The type does not implement the trait or the trait is out of module scope.

Try this: Check the impl and import before widening visibility.

Tests accidentally use production randomness

What is happening: The source is constructed inside the movement rule.

Try this: Accept it as an argument at the narrow seam.

Replay differs with worker count

What is happening: Random state is consumed in arrival order.

Try this: Use coordinate/tick context or a fixed recorded sequence.

Explain it without the example

Why add a trait here instead of making every material a trait object?

Reasoning to compare

The useful variation is the choice source used by tests. Material identity already has an enum; adding unrelated dynamic interfaces would not serve this requirement.
