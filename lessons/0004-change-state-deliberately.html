Change state deliberately

Use mutable state for a falling row and explain the compiler error when reassignment is forbidden.

Previously: Name the cell position. Keep that working result available before starting this lesson.

Why we need this now

Yesterday’s position was fixed for one run. Falling means the same piece of state must take a new value during that run. Rust makes that permission explicit with mut, which helps us distinguish fixed configuration from changing simulation state.

Your result: Use mutable state for a falling row and explain the compiler error when reassignment is forbidden.

01Reassignment is different from choosing an initial value

In let row = 5;, the value 5 initializes the binding. A later row = 6; tries to assign a different value to that same binding. Rust rejects that reassignment unless the binding was declared mutable. Add mut between let and the name: let mut row = 5;.

The permission belongs to this binding. It does not make every value in the program mutable, and it does not automatically change row. It simply permits later assignments that satisfy the type rules. We still need an update statement telling the program what new value to store.

02Read the update as a state transition

row += 1; is shorthand for adding one to the current row and storing the result back. Starting from 5, the state after the statement is 6. A print before and after the assignment makes that transition visible. This is the smallest useful model of movement: read old position, calculate new position, store it.

Our temporary teaching grid counts rows downward, so increasing row means moving lower on screen. This sign is a convention, not a universal law of gravity. The final world design uses altitude increasing upward; later we will introduce an explicit conversion. For now, keep the prototype convention consistent instead of mixing altitude into the same variable.

03Use the compiler as an experiment

Run the working example, then remove mut and run cargo check. The error should identify reassignment to an immutable binding. Read the source location before applying a suggested repair. You intentionally created the invalid program, so the error confirms the rule you are testing.

Restore mut and keep the cell size immutable. We want positions to change as simulation proceeds, but the art design fixes cell size. Marking every binding mutable would compile in some cases, yet it would make that important distinction harder to see. Give each binding only the permission its job needs.

04Contrast reassignment with shadowing

Rust also permits another let statement with the same name, called shadowing. let row = row + 1; introduces a new binding, while row += 1; updates an existing mutable binding. They can produce the same printed number in a tiny example but express different intentions.

We will use mutation for persistent simulation state because the world evolves over many updates. Shadowing is useful for transformations such as parsing or converting an input into a more useful representation. Do not use shadowing merely to avoid understanding why an actual update needs mutable access. First describe whether you are replacing the state of a continuing object or naming a new transformed value.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

fn main() {
    let mut row = 5;
    let cell_size = 4;
    println!("Before: row={row}");
    row += 1;
    println!("After: row={row}");
    println!("Drawing y={}", row * cell_size);
}

Read what each part does

  1. mut permits updates; it does not perform them.
  2. The before/after prints observe one value across time.
  3. The computed drawing position uses the new row.

Expected result

Before: row=5
After: row=6
Drawing y=24

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

01

Fall farther once

Move from row 5 to row 8 with one update statement.

Need a hint?

Change the amount added, not the initial value.

Worked solution

row += 3;

The result is row 8 and drawing y 32 when size is 4. This is one larger step, not three separate simulation updates.

How to verify your result

You predict both state and drawing result before running.

02

Mutate one coordinate

Add an immutable column, then try to move it. Repair only the needed binding.

Need a hint?

Mutability is declared independently for each binding.

Worked solution

let mut column = 12;
column += 1;

Keep cell_size immutable. The repair expresses that column, too, is changing state. There is no reason to give unrelated configuration mutation permission.

How to verify your result

Both coordinates can update while cell size remains immutable.

03

Compare shadowing

Rewrite a terminal-only version using let row = row + 1 and explain the difference.

Need a hint?

Another let introduces another binding.

Worked solution

Shadowing creates a new binding initialized from the old value. Mutation changes the value associated with the existing mutable binding. For persistent cell state, return to the mutable version before the next lesson.

How to verify your result

Your explanation describes binding identity, not only the final printed number.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

cannot assign twice to immutable variable

What is happening: The binding lacks mut.

Try this: Add mut to the binding whose state must change, then rerun check.

row += 1 is outside main

What is happening: The update was placed outside a function body.

Try this: Keep executable statements inside main’s braces.

The grain moves the wrong direction later

What is happening: World altitude and screen-row conventions were mixed.

Try this: Use the current downward-row convention until the conversion lesson; do not compensate with unrelated camera changes.

Explain it without the example

Why should row be mutable while a fixed cell size can remain immutable?

Reasoning to compare

The update assigns a new value to row. A fixed cell size is only read, so it needs no reassignment permission. Mutability follows intended use.
