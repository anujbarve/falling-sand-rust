Borrow state to draw and reset

Use shared and mutable references so helpers inspect or update a cell without taking ownership.

Previously: Discover a move before borrowing. Keep that working result available before starting this lesson.

Why we need this now

The drawing helper should be allowed to read the cell, while reset should change it. In both cases main must keep ownership for the next frame. References express those access contracts directly, solving the moved-value problem we just observed.

Your result: Use shared and mutable references so helpers inspect or update a cell without taking ownership.

01Borrow instead of transfer

Change a read-only function parameter from Cell to &Cell. At the call, write &cell to create a shared reference. The helper receives access to an owned value elsewhere; it does not become the owner of the Cell. After the call, main can still use the cell.

References are not copied world snapshots. They refer to the same underlying value for their valid lifetime. Dot access can read fields through a reference conveniently. This is why a rendering helper can inspect a large world without cloning the world every frame. The interface says it only needs a view.

02Mutation needs a different permission

A reset helper changes the original row, so its parameter is &mut Cell and the call supplies &mut cell. The owner binding must also be mutable. These two uses of mut are related but occur at different places: one permits the owner’s state to change, the other requests exclusive mutable access during the borrow.

A shared reference does not permit ordinary field mutation. Try assigning row inside inspect_cell and observe the rejection, then undo it. Do not make every helper mutable just to avoid deciding what it does. Narrow permissions help readers and the compiler reason about whether a call can change simulation state.

03Reason about when access overlaps

Rust permits multiple shared borrows while they are used, or an exclusive mutable borrow while it is used; conflicting access cannot overlap. This protects the same value from incompatible operations. A simple sequence of inspect, reset, inspect works because the calls do not need conflicting simultaneous access.

Do not teach that every borrow lasts until the closing brace of main. The compiler can end a borrow after its last use. To observe the distinction, store a shared reference, read it, then mutate after its final use. Next add another read of that old reference after the mutation and inspect the conflict diagnostic.

04Connect the contracts back to the window

The terminal experiment below isolates borrowing syntax. Once it is understood, make draw_cell accept &Cell, keep let mut cell before the frame loop, and call reset_cell(&mut cell) when R is pressed. Draw with draw_cell(&cell) each frame. State remains in one owner; helpers receive only the access they need.

This is the core pattern we will reuse for world rendering and simulation updates. The concept is not “Rust makes me type ampersands.” The reason is that different operations need different temporary access to one persistent object. End by asking which helper can change the row before reading its body; the signatures should already answer that question.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

struct Cell { row: i32 }

fn inspect_cell(cell: &Cell) {
    println!("row={}", cell.row);
}
fn reset_cell(cell: &mut Cell) {
    cell.row = 5;
}
fn main() {
    let mut cell = Cell { row: 30 };
    inspect_cell(&cell);
    reset_cell(&mut cell);
    inspect_cell(&cell);
}

Read what each part does

  1. The terminal example is complete and independent of macroquad.
  2. The same borrowed value is observed before and after reset.
  3. Graphical integration keeps state outside the frame loop.

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Change without consuming

Write fall_once(&mut Cell) that increases row by one.

Need a hint?

The helper needs mutation but not ownership.

Worked solution

fn fall_once(cell: &mut Cell) {
    cell.row += 1;
}

Call it between the two inspect calls and keep ownership in main. The second observation should report the updated row.

How to verify your result

The caller remains able to inspect and update the same Cell.

02

Read the permission from a signature

Which of inspect_cell(&Cell) and reset_cell(&mut Cell) may change the original row?

Need a hint?

The reference type is part of the contract.

Worked solution

The shared reference supports inspection; the mutable reference grants exclusive mutation access while used. This does not mean a mutable helper must mutate, only that it is permitted to.

How to verify your result

The explanation distinguishes permission from guaranteed behavior.

03

Create a real overlap

Keep a shared reference alive with a later use while trying to take a mutable reference in between.

Need a hint?

A borrow’s last use changes the overlap.

Worked solution

let shared = &cell;
reset_cell(&mut cell);
println!("{}", shared.row);

These lines intentionally conflict. Move the last shared read before reset, or avoid keeping the shared reference across the mutation. Do not hide the issue by cloning the world.

How to verify your result

You can explain both the conflict and the non-overlapping repair.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

cannot borrow cell as mutable

What is happening: The owner binding may lack mut.

Try this: Declare let mut cell when mutation is intentional.

cannot assign through shared reference

What is happening: The helper accepts &Cell but tries to mutate a field.

Try this: Use a read-only implementation or deliberately change its contract to &mut Cell.

immutable borrow later used here

What is happening: A shared reference remains in use across attempted mutable access.

Try this: Shorten the shared usage sequence or reorder operations so access does not conflict.

Explain it without the example

Why should draw_cell accept a shared borrow instead of a mutable one?

Reasoning to compare

Drawing only reads state. A shared reference grants the necessary access without claiming exclusive mutation permission. Reset needs a mutable reference because it changes the original.
