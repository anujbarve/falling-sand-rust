Find connected support groups

Small unsupported groups are identified correctly. The cap/off-region support exception is visible in tests and the acceptance requirement is scoped accordingly.

Why we need this now

A floating row of two wooden cells can fool a local “solid beside me” test: each points to the other as support. We must ask about the connected structure as a whole. This is the first nonlocal search in the physics, so we also need a bound and a declared approximation.

Your result: Small unsupported groups are identified correctly. The cap/off-region support exception is visible in tests and the acceptance requirement is scoped accordingly.

01Define a group before looking for support

Rigid cells connected by four-neighbour adjacency form one group. Collect that set using a queue or stack and a visited set. Only then can you distinguish internal contact from external support. Two cells in the collected group do not support each other against gravity; they are parts of one object. A proper anchor is bedrock or a valid supporting condition outside the group, as defined by the current game rules.

02Follow the queue in a tiny grid

Begin with one affected rigid neighbour after a cell is removed. Pop it, skip if already visited, add its rigid neighbours, and continue. Mark visited when inserting or use a set on pop so loops cannot grow the work indefinitely. The lab below searches a one-dimensional chain to expose queue/visited behavior with minimal indexing. Port it to four-neighbour grid coordinates through your checked index helper, never raw unchecked arithmetic at edges.

03Bound the work and name the exception

The design stops at 4096 cells or the active-region edge and treats the group as supported. This keeps a giant terrain mass from causing unbounded work, but it also makes some large floating structures remain airborne. That is not a proof of support; it is an accepted fallback if approved. Keep the result enum expressive: Supported, Unsupported, or AssumedSupportedBecauseLimit. Tests and developer counters should reveal which path was used instead of disguising it as an exact algorithm.

04Schedule searches only after relevant changes

Removal of a rigid cell, a changed supporting cell, impact or an edit can dirty support. Queue affected starting positions and deduplicate them where useful. Running a full search from every cell every tick wastes work, while checking only player edits misses fire and erosion. After a blast, many events may refer to the same group. Bound the total support work per update and measure bursts, not merely the maximum size of one search.

use std::collections::{HashSet, VecDeque};
fn connected(start: usize, rigid: &[bool], limit: usize) -> (usize, bool) {
    if start >= rigid.len() || !rigid[start] { return (0,false); }
    let mut queue = VecDeque::from([start]);
    let mut seen = HashSet::new();
    while let Some(i) = queue.pop_front() {
        if !seen.insert(i) { continue; }
        if seen.len() > limit { return (seen.len(),true); }
        if i > 0 && rigid[i-1] { queue.push_back(i-1); }
        if i+1 < rigid.len() && rigid[i+1] { queue.push_back(i+1); }
    }
    (seen.len(),false)
}
#[test]
fn loops_do_not_duplicate_group_members() {
    assert_eq!(connected(1, &[true,true,true,false,true], 10), (3,false));
    assert_eq!(connected(1, &[true,true,true], 2), (3,true));
}

01

Find the cycle

Why does a visited set matter even for a line?

Need a hint?

A neighbour points back to the cell that queued it.

Worked solution

Without visited handling, 0 queues 1 and 1 queues 0 repeatedly. A line already contains backtracking edges even without a visual ring.

How to verify your result

Each valid group member contributes once to the complete count.

02

Separate an anchor

Why must support membership be checked against the entire group?

Need a hint?

A neighbour might be internal.

Worked solution

After collecting the group, inspect downward contacts and reject contacts whose target is another member. Only an external valid support or bedrock anchor can qualify.

How to verify your result

Two adjacent floating cells remain Unsupported.

03

Expose the cap

Create a floating group larger than the configured search limit. What should the test report?

Need a hint?

Do not silently equate a fallback with a proven anchor.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Floating roofs never fall

What is happening: Local same-group contact counts as external support.

Try this: Collect the group and reject internal anchors.

Support search never finishes

What is happening: Visited nodes are queued repeatedly without deduplication.

Try this: Track visited indices and enforce the configured cap.

Explosion frames spike

What is happening: Many dirty starts repeat the same search.

Try this: Deduplicate/group changes and measure aggregate queue work.

Explain it without the example

Why do two adjacent floating cells not prove each other supported?

Reasoning to compare

They belong to the same group. Support must come from outside that group or an explicit anchor, not circular internal contact.
