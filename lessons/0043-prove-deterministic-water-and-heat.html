Prove deterministic water and heat

Identical cases match and changed inputs are not accidentally ignored. Camera comparisons are restricted to the scope allowed by boundary effects.

Previously: Use a small trait for deterministic choices. Keep that working result available before starting this lesson.

Why we need this now

We now have enough interacting rules that “it looks similar” is not a useful regression check. A deterministic run should reproduce the same complete state under identical inputs and schedule. The important work is defining those inputs before comparing anything.

Your result: Identical cases match and changed inputs are not accidentally ignored. Camera comparisons are restricted to the scope allowed by boundary effects.

01Write the replay envelope

The seed describes generated terrain and deterministic choices, but it does not describe where the camera went, which cells were active, what the player painted or how much world time each executed step represented. Record starting state, command sequence with step indices, active-region history and multiplier sequence. If a test omits one of these, it may compare genuinely different simulations and call the difference nondeterminism. Keep the envelope explicit in the fixture rather than scattered through global variables.

02Compare canonical state, not container accidents

A world may store chunks in a hash map whose iteration order is not a public physics contract. For comparison, sort chunk keys, then visit cell fields in a defined order. Exclude irrelevant rendering cache data while including material, temperature, moisture and simulation-relevant flags. A quick hash helps summarize thousands of cells, but when it differs, compare fields to locate the first mismatch. In small tests, direct equality is more informative than a checksum alone.

03Separate three different claims

Repeatability under one thread count, equality across thread counts, and invariance under camera motion are distinct claims. The first catches unrecorded inputs. The second tests dispatch and merge semantics. The third can only be scoped to shared active interior where margin walls/absorption do not influence the result. A camera changes which cells run by design, so unrestricted equality after arbitrary panning is impossible under frozen-off-screen simulation. State the exact comparison region and duration.

04Make the first divergence easy to find

Run both simulations one step at a time and compare after every completed tick while debugging. On mismatch, print tick number, chunk key, local coordinate, old/new fields and the commands applied. Once fixed, retain a compact regression fixture that previously failed. A 10000-tick final hash is useful for the gate, but waiting until the end to learn that something went wrong makes diagnosis unnecessarily expensive. Always report the fixed multiplier and initial seed alongside the result.

#[derive(Clone, Copy, Debug, PartialEq)]
struct Cell { material: u8, temperature: i16 }
fn canonical_digest(cells: &[Cell]) -> u64 {
    let mut hash = 0xcbf29ce484222325_u64;
    for cell in cells {
        for byte in [cell.material, cell.temperature.to_le_bytes()[0],
                     cell.temperature.to_le_bytes()[1]] {
            hash ^= u64::from(byte);
            hash = hash.wrapping_mul(0x100000001b3);
        }
    }
    hash
}
#[test]
fn state_fields_affect_the_digest() {
    let a = [Cell { material: 1, temperature: 20 }];
    let b = [Cell { material: 1, temperature: 21 }];
    assert_eq!(canonical_digest(&a), canonical_digest(&a));
    assert_ne!(canonical_digest(&a), canonical_digest(&b));
}

01

Find an omitted field

Add moisture to Cell but leave the digest unchanged. What false result becomes possible?

Need a hint?

Different worlds can have equal serialized digest input.

Worked solution

A wet and dry cell would compare equal through this incomplete digest. Add moisture to the byte sequence and retain direct field equality for small fixtures.

How to verify your result

Changing any simulation-relevant field is detected in the fixture.

02

Record a speed change

How should a run using multipliers 1,1,4,4 be compared with 1,1,1,1?

Need a hint?

They advance different calendar time.

Worked solution

They are different replay inputs, so equality is not required. Compare only when multiplier sequences and other inputs match, or test an explicitly defined higher-level invariant instead.

How to verify your result

The replay report includes the multiplier sequence.

03

Localize divergence

Design output for the first differing cell after tick 721.

Need a hint?

A final hash does not name a cell.

Worked solution

Print tick=721, sorted chunk coordinate, local x/y, field name, expected and actual. Also print that tick’s commands and multiplier. Re-run the smallest prefix ending at 721.

How to verify your result

One report points directly to the first mismatch.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

World hashes differ after a save

What is happening: Saved-state inventory omits a relevant field or canonical ordering differs.

Try this: Compare decoded fields at the snapshot tick.

Parallel mismatch appears rarely

What is happening: Merge order or a shared write is nondeterministic.

Try this: Audit footprint and event ordering with a minimal failing seed.

Camera test always fails

What is happening: It compares cells influenced by different active boundaries.

Try this: Scope the fixture to the promised shared interior and a bounded horizon.
