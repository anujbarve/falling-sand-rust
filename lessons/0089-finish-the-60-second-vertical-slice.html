Finish the 60-second vertical slice

Record and evaluate a reproducible 60-second house-on-a-hillside scene with visible reactions and honest frame-time evidence.

Previously: Fit settings and camera to real displays. Keep that working result available before starting this lesson.

Why we need this now

The first YouTube opener should demonstrate a game that actually exists. A still screenshot can hide slow reactions, lost support, missing sound and frame spikes. This lesson assembles one short scene and a repeatable inspection procedure.

Your result: Record and evaluate a reproducible 60-second house-on-a-hillside scene with visible reactions and honest frame-time evidence.

01Choose a scene that carries the project

Use one fixed hill, house, grass patch and contained water feature. Include a flammable beam, a sheltered patch under the roof and a neighbouring exposed patch. That small arrangement can demonstrate placement, exposure, wetness, fire and structural loss without rapidly panning through unrelated systems. Record the seed, generator version, camera coordinate, physical view dimensions, world/step ticks, weather and graphics preset.

Write the viewer’s expected observations in order: rain wets the open slope; the roof shelters its interior; a dry exposed patch can burn; renewed rain suppresses flame; seasonal change alters the visible environment. If two observations fight each other, adjust the starting fixture or timing rather than cutting around a broken reaction.

02Use a fixture schedule, not manual luck

A schedule states when a known input is injected. It is not a replacement simulation and should call the same event interface as player tools. In the example, a pure function lists events whose timestamps have just been crossed. This avoids missing an event because a rendered frame jumped from 7.9 to 8.1 seconds. A per-event consumed flag or a monotonically advancing event cursor prevents repeated dispatch.

Seasonal change takes longer than ordinary physical reactions. Prepare a documented near-boundary calendar state or use the displayed fast-forward control; do not imply that a full season naturally takes seconds at 1x. The evidence file records this setup so the opener remains a truthful demonstration.

03Capture without changing the workload

On macOS, the built-in Screenshot toolbar opens with Shift-Command-5 and can record a selected region. Choose the world and UI region intentionally and record at the actual tested physical view. Recording adds CPU/GPU work, so measure a baseline without capture and compare a captured run; report the difference instead of claiming the encoder is free. No new recording package is necessary for this exercise.

Capture the same schedule at the reference settings and target hardware. Keep a raw recording before editing for YouTube. Edit the presentation later, but preserve a link between the claim and the raw run that proves it. A beautiful exported clip is not evidence that the target machine rendered those frames interactively.

04Score the scene against separate promises

Use four columns in the review: visual identity, reaction timing, performance and usability. Check the art bans explicitly: no filtered edges, reflections, bloom or added middle terrain. Check visible deadlines from the reaction table and inspect whether shelters and support remain readable at real cell size. Use average and worst-case frame times, not an FPS number sampled during a quiet moment.

Approved reference images and tolerances must exist before claiming visual sign-off. If they are missing, label the comparison a proposal review. Store the fixture, event script, raw clip and results together. A failed criterion becomes a concrete issue such as rain enters the sheltered cell, not a vague request to add polish.

Walk through the working example

Complete schedule experiment: examples/lesson_089.rs; run cargo run --example lesson_089.

Download this worked example ↧

#[derive(Clone, Copy, Debug, PartialEq)]
struct Event { at_ms: u64, action: &'static str }
fn crossed(events: &[Event], before: u64, now: u64) -> Vec<Event> {
    events.iter().copied().filter(|e| before < e.at_ms && e.at_ms <= now).collect()
}
fn main() {
    let events = [Event { at_ms: 8_000, action: "rain fixture begins" },
        Event { at_ms: 18_000, action: "clear fixture resumes" },
        Event { at_ms: 28_000, action: "ignite dry exposed grass" },
        Event { at_ms: 36_000, action: "rain suppresses the fire" }];
    assert_eq!(crossed(&events, 7_900, 8_100).len(), 1);
    assert!(crossed(&events, 8_100, 8_200).is_empty());
    for event in crossed(&events, 0, 60_000) {
        println!("{:>2}s  {}", event.at_ms / 1000, event.action);
    }
}

Read what each part does

  1. Crossing a timestamp is different from comparing for exact equality with a frame time.
  2. The schedule returns inputs; it does not assert that their required consequences occurred. Measure those consequences separately.
  3. Events at time zero need explicit initialization; this helper dispatches events strictly after the previous timestamp.

Expected result

Four schedule lines at 8,18,28,36 seconds; both crossing assertions pass.

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Skip across two events

Ask crossed for the interval from 7,000ms to 19,000ms.

Need a hint?

Both interval boundaries matter.

Worked solution

It returns the 8,000ms and 18,000ms events in list order. Assert two entries. Call the next interval beginning at 19,000ms and verify neither reappears.

How to verify your result

Long frames do not skip or repeat either fixture event.

02

Make one falsifiable claim

Write one exact rain/shelter acceptance statement before recording.

Need a hint?

Name the cause, target and allowed observation.

Worked solution

For example: while rain runs for ten seconds, the exposed soil moisture rises and the roof-protected comparison cell receives no direct precipitation. Record both moisture values and the matching frame.

How to verify your result

The statement can fail and identify a specific system.

03

Separate encoder overhead

Compare one identical run with and without native screen recording.

Need a hint?

Keep scene, seed and preset fixed.

Worked solution

Report both frame-time distributions and the capture settings. If recording exceeds budget, choose a documented capture platform rather than quietly calling the raw uncaptured performance proof a captured result.

How to verify your result

The report does not confuse game performance with export smoothness.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

One event sometimes never fires

What is happening: It requires exact equality with a floating-point frame time.

Try this: Detect interval crossing or consume an integer event queue.

Season change looks staged without explanation

What is happening: The starting calendar or speed was omitted.

Try this: Include initial time and displayed fast-forward state in the capture notes.

Screenshot matches but clip feels broken

What is happening: Motion/timing and audio were never reviewed.

Try this: Score the full raw scene against separate behavior and experience checks.

Explain it without the example

Why isn't a screenshot comparison alone enough to approve the slice?

Reasoning to compare

The slice depends on motion, reactions, sound and performance over time. A still image cannot establish those behaviors.
