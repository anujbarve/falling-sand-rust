Separate world altitude from screen rows

The same world cell can be drawn and picked after panning. Increasing altitude moves it upward, not downward.

Previously: Run a year and close the ecology milestone. Keep that working result available before starting this lesson.

M4 starts here. Review this milestone’s implementation plan against the current spec. The lessons teach the work; they do not silently approve new game behavior.

Why we need this now

The early renderer counted rows downward from the top-left corner. The world design counts altitude upward. Both conventions are valid, but silently using one where the other is expected reverses gravity, growth and camera picking. One named conversion makes the relationship explicit.

Your result: The same world cell can be drawn and picked after panning. Increasing altitude moves it upward, not downward.

01Name spaces before writing formulas

World coordinates describe persistent locations independent of the current view. Camera coordinates describe which world area appears in the window. Drawing coordinates are measured downward/rightward from the view origin. Local chunk coordinates are offsets inside one 64×64 storage block. These are related spaces, not interchangeable integers. Separate types are useful when practical; at minimum use names such as world_y, view_top_y and screen_row rather than a generic y everywhere.

02Derive the vertical conversion

If the top visible world altitude is top_y, a cell at altitude y appears top_y-y rows down. A world altitude increase makes the result smaller, so the cell moves upward on the screen. Multiply that row by the drawing cell size only after this conversion. For x, subtract the camera’s left world x. The inverse adds the horizontal offset and subtracts the screen row from top_y. Decide whether camera origins are cell-aligned or rounded at drawing boundaries and test the chosen picking behavior.

03Keep physics in world units

After adopting world altitude, falling decreases world y, rising steam increases it and a trunk template grows with positive y offsets. Do not change the physical rule based on screen orientation; only the renderer/picking conversion knows about downward rows. When porting prototype code, search every row+1 gravity operation and classify whether it belongs to a screen grid or world state. Rename deliberately instead of flipping signs blindly across all expressions.

04Negative coordinates need Euclidean chunk mapping

For world x=-1 and chunk width 64, the containing chunk is -1 and local offset is 63. Truncating division would point at chunk zero with an invalid negative local position. Use div_euclid and rem_euclid so reconstruction chunk*64+local returns the original coordinate. Test -65,-64,-1,0,63,64. A viewport that crosses the origin should neither mirror cells nor lose brush strokes.

fn to_view(world:(i32,i32), left:i32, top:i32)->(i32,i32) {
    (world.0-left, top-world.1)
}
fn to_world(view:(i32,i32), left:i32, top:i32)->(i32,i32) {
    (view.0+left, top-view.1)
}
#[test]
fn world_view_conversion_round_trips() {
    let world=(-3,12);
    let view=to_view(world,-10,20);
    assert_eq!(view,(7,8));
    assert_eq!(to_world(view,-10,20),world);
    assert_eq!((-1_i32).div_euclid(64),-1);
    assert_eq!((-1_i32).rem_euclid(64),63);
}

01

Move upward

World y increases from 12 to 13 with top=20. What happens to screen row?

Need a hint?

Compute top-y twice.

Worked solution

It changes from 8 to 7, moving one row upward. Cell size then converts that to four physical pixels under the production mapping.

How to verify your result

The sign agrees with altitude increasing upward.

02

Map a negative boundary

Calculate chunk/local for x=-65 with width 64.

Need a hint?

Choose the containing interval, not truncation toward zero.

Worked solution

Chunk -2, local 63. Reconstruct -2*64+63=-65. Add assertions for both quotient and remainder.

How to verify your result

All tested negative positions reconstruct exactly.

03

Pick after panning

Which camera values should inverse mouse conversion use?

Need a hint?

Use the actual view rectangle/origin used for drawing.

Worked solution

Use the same left/top and world-view panel offset as the draw pass. A stale camera or unremoved panel offset makes clicks select a different cell than the one shown.

How to verify your result

A drawn cell and its clicked cell identity match after panning.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Gravity reverses after camera refactor

What is happening: A screen-row update was reused as world-altitude physics.

Try this: Keep physical updates in world coordinates and convert only at boundaries.

Chunk seams appear left of zero

What is happening: Truncating division handles negatives incorrectly.

Try this: Use Euclidean quotient/remainder and round-trip tests.

Picking shifts under capped views

What is happening: Mouse conversion ignores the centred world-panel origin.

Try this: Subtract the actual view rectangle origin before cell conversion.

Explain it without the example

Why avoid applying the screen-row gravity sign directly to world altitude?

Reasoning to compare

They use opposite vertical conventions. A named conversion keeps drawing conventions from silently changing physics direction.
