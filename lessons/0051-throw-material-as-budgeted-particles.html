Throw material as budgeted particles

No thrown material exists in both list and grid. Destruction beyond the cap is explicitly counted as the designed exception.

Previously: Drop and float rigid groups as units. Keep that working result available before starting this lesson.

Why we need this now

An explosion must throw matter outward, but ordinary grid cells only store material state, not a continuous velocity. A temporary particle list fills that gap. The key invariant is ownership: each thrown parcel is either in the grid or in the list, never both and never silently nowhere.

Your result: No thrown material exists in both list and grid. Destruction beyond the cap is explicitly counted as the designed exception.

01Transfer ownership at launch

When a blast chooses a cell for throwing, copy or move its complete state into a particle record, then clear its grid slot in the same event application. The record stores floating-point position and velocity plus original material/temperature/moisture fields needed on re-entry. A separate list has its own cap. If the cap is exhausted, the design destroys additional blast cells rather than spawning unlimited particles; count that exception so conservation tests know why matter disappeared.

02Integrate velocity using the physics tick

Choose explicit units: position in cells and velocity in cells per physics second, or per tick. The worked lab uses seconds: position advances by velocity times dt and velocity by acceleration times dt. A fixed executed tick supplies dt, not the render frame duration. Interpolation between previous/current particle positions can make display motion smoother without changing the collision decision. This is a game effect, not a complete rigid-body physics engine.

03Sweep for collisions and bound reinsertion

A fast particle can cross a wall between two endpoint samples. Trace the segment through candidate grid cells or otherwise sweep the path, stopping at the first non-gas hit. Reinsert the parcel into a nearby valid free slot using a bounded, deterministic search. “Nearest free” without a radius/order policy can become an unbounded flood fill or yield different answers across runs. A fully occupied region needs an explicit keep-pending/destruction/fallback policy rather than overwriting existing material.

04Treat saving as another ownership boundary

The current design reinserts particles before saving, which changes a live explosion. That policy is still a design lab: either accept and demonstrate the visible interruption, or serialize particle state in a coherent snapshot. Do not claim exact mid-flight round trips while discarding velocity. The same ownership inventory should include falling groups and queued effects. A test that saves one tagged airborne parcel catches duplication or loss at this boundary more clearly than an entire blast cloud.

#[derive(Clone, Copy, Debug)]
struct Particle { x: f32, y: f32, vx: f32, vy: f32 }
fn integrate(p: &mut Particle, dt: f32, gravity: f32) {
    p.vy += gravity * dt;
    p.x += p.vx * dt;
    p.y += p.vy * dt;
}
#[test]
fn velocity_uses_physics_time_units() {
    let mut p = Particle { x:0.0, y:0.0, vx:20.0, vy:0.0 };
    integrate(&mut p, 0.05, 40.0);
    assert!((p.x-1.0).abs() < 0.0001);
    assert!((p.vy-2.0).abs() < 0.0001);
    assert!((p.y-0.1).abs() < 0.0001);
}

Exercises you actually do

01

Check units

Why multiply vx by 0.05 instead of adding vx directly?

Need a hint?

vx is cells per second in this lab.

Worked solution

Multiplying by seconds gives cells. Adding 20 directly would move 20 cells every tick, equivalent to 400 cells/second at 20 TPS rather than the declared 20.

How to verify your result

A one-tick horizontal displacement is one cell.

02

Count one parcel

Which count should remain constant while launching and landing a tagged non-destroyed parcel?

Need a hint?

It changes representation during flight.

Worked solution

Count tagged material in grid plus particles. Launch decrements grid and increments list; landing does the reverse. The sum stays one.

How to verify your result

No transition creates a second copy.

03

Fill the landing region

What should a test assert if no free landing slot exists within the search bound?

Need a hint?

The fallback policy must be declared first.

Worked solution

Assert the chosen bounded outcome: retain a pending particle, use a specified fallback slot if valid, or count explicit destruction if approved. The important checks are no overwrite, no unbounded search and no unaccounted disappearance.

How to verify your result

The fixture terminates within its search budget.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Debris speeds vary with FPS

What is happening: Integration uses render delta for physics steps.

Try this: Use the fixed physics dt and interpolate only for drawing.

Particles pass through a thin wall

What is happening: Only the final position was checked.

Try this: Sweep the path through intermediate cells.

Saving deletes or duplicates debris

What is happening: Representation transfer is incomplete.

Try this: Inventory ownership before/after launch, save and landing.

Explain it without the example

Why is checking only a particle's final position unsafe at high speed?

Reasoning to compare

It can cross a solid between its start and end. Swept/path collision checks prevent tunnelling through intermediate cells.
