Ship the release and preserve the next starting point

Assemble a release candidate with explicit evidence, reproducible artifacts and a clean starting point for the next build.

Previously: Write the small manual and check real usability. Keep that working result available before starting this lesson.

Why we need this now

Finishing the course should leave a game you can explain, rebuild and recover—not merely a development binary that happened to launch once. Release readiness is the intersection of several independently proven promises.

Your result: Assemble a release candidate with explicit evidence, reproducible artifacts and a clean starting point for the next build.

01Freeze a candidate before collecting evidence

Choose a candidate revision and build all reviewed artifacts from that revision and its lockfile. Record the Rust toolchain, native targets, generator/save versions and approved asset set. If a bug fix changes source afterward, identify which checks it invalidates and rebuild the affected artifacts rather than attaching old evidence to a new executable.

Keep the working tree status visible in the release report. Do not silently rely on ignored local assets, hand-edited saves or personal settings that a fresh checkout cannot recreate.

02Use gates as claims with evidence

List the M0–M7 outcomes and link their reports: target-load timing, water/heat deadlines, shelter/fire/support behavior, ecological year and32-seed results, generated-terrain rest, memory panning, save recovery, approved visuals, native packages and usability. A checkbox without a linked observation is a reminder, not proof.

The sample gate evaluator below deliberately fails when any required row is false. Real automation should also distinguish failed from not-run; an absent report is not a pass. Accepted limitations belong beside the affected gate, such as a scoped support-cap rule, not in a hidden footnote that contradicts the headline feature.

03Identify the exact package being reviewed

Compute checksums for candidate archives and retain a small manifest containing filename, target, version, size and digest. On macOS shasum -a256 followed by the actual archive path prints a SHA-256 digest. Windows can use Get-FileHash -Algorithm SHA256 with the actual path. Hashes identify bytes; they do not establish safety or correctness by themselves.

A signing/notarization step may modify the artifact, so compute the final distribution checksum after the final approved packaging/signing operation. Do not reuse a checksum from an unsigned earlier zip. Test the same final package through fresh installation, save creation, quit, restart and backup recovery.

04Prepare publication without performing it automatically

Write a changelog that says what the player can now do and names known limitations. Prepare the release tag name, artifacts and notes for review. Ask yourself to implement one small change from memory and explain the ownership/update path it touches. That is the learning outcome that distinguishes building this game from merely collecting generated source files.

Read → predict → run → change

Walk through the working example

Complete release-gate experiment: examples/lesson_100.rs; run cargo run --example lesson_100. Replace sample booleans with actual report results in your release tooling.

Download this worked example ↧

struct Gate { name: &'static str, passed: bool }
fn ready(gates:&[Gate])->Result<(),Vec<&'static str>> {
    let failures:Vec<_>=gates.iter().filter(|g|!g.passed).map(|g|g.name).collect();
    if failures.is_empty() { Ok(()) } else { Err(failures) }
}
fn main() {
    let gates=[Gate{name:"headless regression",passed:true},
        Gate{name:"floor-machine frame times",passed:false},
        Gate{name:"native package smoke tests",passed:true},
        Gate{name:"complete-save recovery",passed:true}];
    match ready(&gates) {
        Ok(())=>println!("candidate ready for explicit publication review"),
        Err(missing)=>println!("release blocked: {}",missing.join(", ")),
    }
}

Read what each part does

  1. This experiment does not publish, tag, upload or run external checks. It demonstrates how a readiness claim follows its required evidence.
  2. A production report should represent not-run distinctly from false, retain report paths and bind results to the candidate revision.
  3. Required gates cannot be made optional just to turn the final message green; any scope change needs an explicit updated requirement.

Expected result

release blocked: floor-machine frame times

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Make a missing report visible

Add a visual-approval gate that has never run.

Need a hint?

Not-run is not the same as passed.

Worked solution

Represent it as Pending in a richer enum, or false with an explicit not-run reason in this small model. It must appear among release blockers until the comparison assets, conditions and approval actually exist.

How to verify your result

A candidate cannot claim approval from an absent report.

02

Change source after checking

Fix one release bug after generating package hashes. What must be repeated?

Need a hint?

Evidence refers to a revision and bytes.

Worked solution

Rebuild the affected artifacts, rerun relevant gates, run final smoke tests and recompute hashes after final packaging/signing. Preserve the earlier report as history rather than relabelling it as the new result.

How to verify your result

The manifest and reports identify the same final candidate.

03

Explain one feature unaided

Choose a falling, fire, save or undo fixture and change one rule from memory.

Need a hint?

Trace the state owner, mutation boundary and proving test.

Worked solution

For example, change the teaching fall limit from three to two cells, update the displacement assertion and explain why the moved marker still prevents a second update. If you cannot derive the consequence, revisit that lesson before claiming mastery.

How to verify your result

You predict, implement and verify a change without copying a complete solution.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Release notes claim a failed feature

What is happening: The readiness list is detached from acceptance evidence.

Try this: Link each claim to its actual passing report or state the limitation.

Users report a different package than tested

What is happening: Artifacts were rebuilt or modified after checksums/smoke tests.

Try this: Bind revision, final bytes and final test results in one manifest.

The next build cannot reproduce the world

What is happening: Uncommitted source/assets or hidden local state were required.

Try this: Document the starting revision and deterministic fixture inputs before running the demonstration.

Explain it without the example

What evidence separates release-ready from merely builds on my machine?

Reasoning to compare

Repeatable tests, target-hardware measurements, native package smoke tests, save recovery/compatibility checks, approved visuals and documented known limitations support the release claim.

Self-check only: test a prediction or ask your tutor if anything still feels arbitrary.

Finish with evidence

The game is release-ready on the claimed platforms, or the remaining blockers are named. Publish/tag/push only when explicitly requested.

Make one small variation without copying: predict it, run it and explain any difference. On another day, repeat one exercise from memory before starting the next lesson. Ask your tutor about any step you can execute but cannot explain.
