Keep generator and save versions distinct

Load an old world using its original generator even when the current default generator changes.

Previously: Commit a complete save generation. Keep that working result available before starting this lesson.

Why we need this now

An unchanged chunk is usually regenerated rather than stored. That saves disk space only if the game remembers which generation rules originally produced it. Otherwise the edge of explored terrain can become a permanent seam after an update.

Your result: Load an old world using its original generator even when the current default generator changes.

01Separate bytes from terrain identity

A format version explains how saved bytes are decoded. A generator version explains how absent terrain is produced from seed and position. The same format can store worlds created by several generators; the same generator can survive a storage format upgrade. Conflating them forces unrelated changes together.

Draw a world with saved chunk A and absent chunk B. Upgrade the default hill formula, then regenerate B with the new formula. A remains old terrain while B changes. The save loaded without a parse error, yet the world continuity promise was broken.

02Dispatch from the world, not the application default

The world metadata owns generator_version. Opening the world selects its generator implementation, and all future unsaved chunks use that implementation. A new-world screen may default to the latest generator, but that default must not leak into an already loaded world.

Use a small version enum parsed from explicit IDs. Unsupported IDs return an error. Never map unknown IDs to latest; that replaces a helpful incompatibility message with silent geometry corruption.

03Freeze released generation contracts

A generator contract includes seed interpretation, noise algorithm/version, biome thresholds, feature order and material placement details. Changing an indirect dependency can alter output even if your own function name remains v1. Pin dependencies and keep small expected-coordinate fixtures that detect changes.

Before first release the project may intentionally invalidate temporary worlds, with a clear message. After release either retain old implementations or design a deliberate migration. A migration must decide what happens at the seam between edited saved chunks and newly generated data; it cannot simply erase the player’s edits.

04Test absence as well as saved data

Round-trip fixtures generally cover stored chunks. Add a fixture where one known chunk is deliberately absent, then load using the old generator and request it. Verify its terrain hash and shared border against the historical expectation. This tests the part of persistence that has no payload to decode.

The worked example uses tiny height functions so the difference is obvious. In the real world pass generator identity through worker requests too; an old-world background result must not be installed after switching to a new world.

#[derive(Clone, Copy)]
enum Generator { V1, V2 }
fn parse_version(id: u16) -> Result<Generator,&'static str> {
    match id {1=>Ok(Generator::V1),2=>Ok(Generator::V2),_=>Err("unsupported generator")}
}
fn height(version: Generator,x:i32) -> i32 {
    match version {
        Generator::V1 => 20+x.rem_euclid(4),
        Generator::V2 => 40+x.rem_euclid(8),
    }
}
fn main() {
    let world_generator=parse_version(1).unwrap();
    let new_default=Generator::V2;
    assert_eq!(height(world_generator,64),20);
    assert_eq!(height(new_default,64),40);
    assert!(parse_version(99).is_err());
    println!("old world keeps its generator; new worlds may use v2");
}

Read what each part does

  1. These simple periodic heights isolate version dispatch; they are not the production noise algorithm.
  2. The world retains V1 even when the application default is V2.
  3. unwrap is confined to the controlled known-ID demo; real file parsing propagates the unsupported-version error.

Expected result

old world keeps its generator; new worlds may use v2

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

01

Find the hidden seam

A saved old chunk ends at height 20, while the adjacent regenerated chunk starts at 40. Which version should be checked?

Need a hint?

Successful byte decoding does not settle generation.

Worked solution

Check the world-owned generator version used for the absent chunk. The format can be correct while generator selection is wrong.

How to verify your result

Requesting the absent chunk uses the historical function.

02

Reject rather than guess

Replace metadata with generator ID 99.

Need a hint?

Latest is a new-world preference, not an error recovery policy.

Worked solution

Return unsupported generator and preserve the world untouched. Ask for a compatible reader or migration rather than regenerating with V2.

How to verify your result

No chunks are generated or saved after the rejection.

03

Protect a released version

A noise dependency update changes V1 output. What test should fail?

Need a hint?

Use a golden coordinate/output fixture, not only same-run equality.

Worked solution

Keep known seed/coordinate outputs or hashes from the released generator. Their mismatch detects algorithm drift even if two fresh runs agree with each other.

How to verify your result

Historical fixtures remain unchanged across unrelated updates.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Old worlds gain terrain seams

What is happening: Default generator replaced the world-owned generator.

Try this: Dispatch from saved generator identity for every absent chunk.

Determinism tests pass but historical terrain changed

What is happening: Only fresh-run comparisons exist.

Try this: Retain released generator output fixtures.

Unknown version opens with strange geometry

What is happening: The loader silently maps unknown IDs to latest.

Try this: Reject unsupported versions before generation or mutation.

Explain it without the example

Why can a readable old save still develop seams after a generator update?

Reasoning to compare

Saved chunks retain old terrain while unchanged chunks regenerate with new rules unless the world's generator version is preserved.
