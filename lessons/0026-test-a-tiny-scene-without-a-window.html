Test a tiny scene without a window

Write headless tests that detect a movement regression and distinguish compilation from behavioral proof.

Previously: Give modules narrow jobs. Keep that working result available before starting this lesson.

Why we need this now

cargo check tells us that code satisfies Rust’s static rules, not that sand stops at the right place. A tiny deterministic fixture can express the game behavior we want and catch a later regression automatically without opening a window.

Your result: Write headless tests that detect a movement regression and distinguish compilation from behavioral proof.

01Specify a visible promise as an assertion

Choose one concrete rule: a grain above the floor falls, a grain at the floor stays, and no step crosses the floor. Construct the smallest state that could violate it. Run the helper, then assert the resulting row. The test’s value comes from the counterexample it can reject, not from the number of assertions.

Avoid a test that simply reproduces the implementation arithmetic line-for-line and compares the same formula to itself. Use expected outcomes chosen from the behavior contract. For movement in a grid, also count conserved materials because a correct destination can coexist with a duplicated source.

02Use Rust’s test harness

A function marked #[test] is run by cargo test. Assertions panic when their condition fails, which the test harness reports as a failure. Put a tests module behind #[cfg(test)] so the tests belong to the relevant code without becoming the program’s entry behavior.

The worked example is a small library-style source file. Put it in src/lib.rs or the appropriate simulation module, then run cargo test. There is no graphical main or context. A passing test produces a concise test summary; it does not need to print a celebratory message from the game.

03Prove the test can catch the bug

Temporarily remove the destination clamp or change the floor offset, then run the relevant test by name. The expected failure demonstrates that the test is connected to the promise. Restore the implementation and rerun. A test suite that never fails under a known broken rule may be asserting the wrong observation.

Keep the deliberate failure out of the final working state. For a YouTube episode, the red-to-green moment makes the reason for testing concrete: the test protects an actual visible bug rather than satisfying a code-style ritual.

04Separate headless, visual and performance evidence

A headless assertion can verify exact positions, counts and deadlines in ticks. It cannot establish whether the effect is readable in a tiny muted-palette frame or whether it runs smoothly on the floor GPU. Those need their own manual and measured checks.

Use fixtures repeatedly across the course: controlled inputs, specified tick count, expected result. Later multi-seed reliability checks and cross-thread hashes will extend this foundation. Do not broaden tests simply to mirror every helper; keep meaningful behavioral invariants tied to the game’s acceptance conditions.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

fn next_row(row:i32,floor_row:i32)->i32 {
    if row<floor_row-1 {(row+3).min(floor_row-1)} else {row}
}
#[cfg(test)]
mod tests {
    use super::next_row;
    #[test]
    fn falls_and_stops_without_crossing_floor() {
        assert_eq!(next_row(5,160),8);
        assert_eq!(next_row(158,160),159);
        assert_eq!(next_row(159,160),159);
    }
}

Read what each part does

  1. The example intentionally has no main because it is a testable library module.
  2. One test covers ordinary, overshoot and resting cases.
  3. A passing suite is one evidence type, not complete release approval.

Expected result

cargo test reports the named test passed. This example is intended for src/lib.rs or a tested module, not a standalone main executable.

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

01

Make the test fail on purpose

Remove min from the helper and run the test.

Need a hint?

The shortened final-step case is the counterexample.

Worked solution

The row158 expectation fails because the broken implementation returns161. Restore clamping. The failure demonstrates which promise the assertion protects.

How to verify your result

The suite is red for the known bug and green after repair.

02

Add an invalid-coordinate contract

Write tests for -1 and exact-width coordinates using the checked index helper.

Need a hint?

The expected result is None, not a panic.

Worked solution

Import the actual helper used by painting and assert None at each invalid edge. Do not write a separate “test-only” mapper with different logic.

How to verify your result

The production boundary operation is under test.

03

Describe a missing kind of evidence

What cannot this floor test tell us about the finished game?

Need a hint?

Think about image readability and hardware.

Worked solution

It cannot prove the scene looks approved, the grain is visible, or frame time meets the target. Those claims require visual review and hardware measurements in addition to headless correctness.

How to verify your result

The evidence is stated with its limits.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

running0 tests

What is happening: No test function is in the compiled test target or the attribute/module path is wrong.

Try this: Check #[test], #[cfg(test)] and Cargo’s selected package.

A known bug still passes

What is happening: The assertion may observe an unrelated value or duplicate the broken formula.

Try this: Use a concrete behavioral counterexample.

Test requires a graphics context

What is happening: Simulation logic is coupled to window initialization.

Try this: Extract the rule into a headless module and keep rendering separate.

Explain it without the example

Why count material in addition to checking the final grain location?

Reasoning to compare

A grain may arrive at the correct destination while leaving a duplicate behind. Position alone does not prove conservation.
