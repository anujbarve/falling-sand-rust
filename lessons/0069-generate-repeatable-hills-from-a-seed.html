Generate repeatable hills from a seed

Shared borders match and generation order does not alter terrain. Seed and generator-version inputs are explicit.

Previously: Separate world altitude from screen rows. Keep that working result available before starting this lesson.

Why we need this now

Exploration should reveal the same hillside regardless of the route taken to reach it. A single mutable RNG consumed while loading chunks makes terrain depend on visit order. A coordinate-addressed height function instead lets any chunk ask for its columns independently.

Your result: Shared borders match and generation order does not alter terrain. Seed and generator-version inputs are explicit.

01Define the generation key

Terrain generation takes world seed, generator version and world coordinate. It returns the same result for that tuple. The version is as important as the seed because changing a formula changes absent chunks in an old save. Begin with a simple one-dimensional height function before adding caves and climate. This keeps the first border test small: evaluate adjacent columns directly and compare them with the values embedded in separately generated chunks.

02Make broad variation continuous

Independent random heights at every column create white-noise spikes rather than calm hills. Sample a deterministic value at widely spaced lattice points, then blend between them. A smoothstep blend eases the slope near endpoints. Add a lower-amplitude, shorter-scale component only after broad shape works. The lab uses a tiny deterministic hash and one smooth scale to show the mechanism; it is not a recommendation that this particular hash is the final generator’s quality choice.

03Treat negative positions as ordinary world coordinates

Find the lattice interval with Euclidean division and a nonnegative remainder. That makes x=-1 blend between the correct lattice centres instead of joining the wrong interval at zero. Coordinate hashing should use explicitly chosen wrapping integer operations, so debug builds and release builds do not differ because of overflow checks. Do not use the standard randomized hash-map hasher as an unspecified persistent terrain generator. Pin the algorithm/configuration if worlds must regenerate across versions.

04Test order independence and borders

Generate chunk A then B, record their heights, then generate B then A in a fresh world. The values should match because no mutable visit sequence is consumed. Check the exact shared boundary and a run across negative coordinates. Later rest guarantees may modify material placement based on slopes, but should still be deterministic functions of bounded neighbourhood data. A beautiful random-looking picture is not evidence that regeneration or old-world compatibility works.

fn hash(seed:u64, x:i64)->f64 {
    let mut z=seed ^ (x as u64).wrapping_mul(0x9e3779b97f4a7c15);
    z=(z^(z>>30)).wrapping_mul(0xbf58476d1ce4e5b9);
    z=(z^(z>>27)).wrapping_mul(0x94d049bb133111eb);
    z ^= z>>31;
    (z>>11) as f64 / ((1_u64<<53) as f64)
}
fn height(seed:u64,x:i64)->f64 {
    let cell=x.div_euclid(64);
    let t=x.rem_euclid(64) as f64/64.0;
    let eased=t*t*(3.0-2.0*t);
    let a=hash(seed,cell); let b=hash(seed,cell+1);
    100.0+40.0*(a+(b-a)*eased)
}
#[test]
fn terrain_is_addressed_by_coordinate() {
    let forward:Vec<_>=(-65..65).map(|x|height(7,x)).collect();
    let mut reverse:Vec<_>=(-65..65).rev().map(|x|height(7,x)).collect();
    reverse.reverse();
    assert_eq!(forward,reverse);
    assert!(height(7,-1).is_finite());
}

01

Spot visit-order dependence

Why would calling rng.next() for each newly visited chunk violate this fixture?

Need a hint?

The next value depends on how much was consumed before.

Worked solution

Visiting B before A assigns different sequence positions to each chunk. Coordinate hashing lets A and B request their own inputs without depending on traversal history.

How to verify your result

The generator can evaluate a chunk without advancing shared RNG state.

02

Change the seed

Must every sampled column differ for a different seed?

Need a hint?

Different input does not imply every output is different.

Worked solution

No. The useful tests check reproducibility for one seed and meaningful overall variation across a chosen set. Requiring every individual output to differ is stronger than necessary and may reject valid collisions/quantization.

How to verify your result

Tests avoid an impossible universal no-collision promise.

03

Add small detail

How can a second scale avoid dominating the main hill?

Need a hint?

Use a smaller amplitude on the shorter wavelength.

Worked solution

Add an independently keyed smooth component, for example amplitude 4 at a shorter lattice spacing, to the amplitude-40 broad hill. Then re-run slope/rest and border checks.

How to verify your result

Broad shape remains readable and local detail is bounded.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Terrain changes after panning away

What is happening: Generation consumes mutable visit-order randomness.

Try this: Address samples by seed/version/coordinate.

Sharp seam appears at x=0

What is happening: Negative lattice division is inconsistent.

Try this: Use Euclidean quotient/remainder throughout the noise coordinate mapping.

Debug build panics in the hash

What is happening: Intentional integer mixing used ordinary overflowing multiplication.

Try this: Use wrapping operations explicitly and test both build modes.

Explain it without the example

Reasoning to compare
