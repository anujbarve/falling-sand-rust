Count days and seasons with integers

Day and season transitions are exact at their documented boundaries. Simulation step count is not silently substituted for calendar time.

Previously: Verify the fire weather and structure slice. Keep that working result available before starting this lesson.

M3 starts here. Review this milestone’s implementation plan against the current spec. The lessons teach the work; they do not silently approve new game behavior.

Why we need this now

We want a day to have an exact boundary, even when the computer cannot execute every desired physics update. One counter cannot represent both “updates actually performed” and “calendar time requested by fast-forward.” Two integer counters make that distinction visible and testable.

Your result: Day and season transitions are exact at their documented boundaries. Simulation step count is not silently substituted for calendar time.

01Name what each counter counts

step_tick increases once after a completed simulation update. It identifies update order and participates in deterministic random choices. world_tick advances by that update’s assigned multiplier and drives day, season, cooldowns and climate. At normal speed the increments are both one, which can hide the distinction. At fast-forward a single executed step may advance several calendar units. Give every timer a name tied to one of these clocks so a fuse cannot accidentally age like a season.

02Derive the calendar by division

One day contains 24000 world ticks. Integer division yields the completed-day count and the remainder yields position within the day. Three days make a 72000-tick season; twelve days make a 288000-tick year. To display day one at startup, add one in the UI rather than changing the underlying zero-based counter. This avoids an off-by-one disagreement between calculations and labels. A calendar function can remain pure: it only reads the counter and returns derived fields.

03Test the boundaries, not only the middle

Values just before, exactly at and just after 24000 or 72000 expose errors in division and modulo. A season can be represented as an enum selected by completed_seasons modulo four. The year count comes from division by 288000. Pausing freezes both advances under the current scheduler policy. Do not ask the OS date/time what season the simulated world is in; that would make saves and replays depend on when the game is launched.

04Plan for long-running storage

u64 is large enough for ordinary play, but arithmetic should still have a declared overflow policy. Checked addition can surface a corrupted/extreme counter instead of wrapping the year backward. Save both counters because world_tick alone cannot reproduce which random picks occurred. Also decide how scheduler remainder/debt is persisted or reset; those are not the same as completed integer time. The lab isolates exact calendar conversion before scheduler budgeting is added in the next lessons.

const DAY:u64=24_000;
const SEASON:u64=3*DAY;
const YEAR:u64=4*SEASON;
fn calendar(tick:u64)->(u64,u64,u64) {
    (tick/YEAR, (tick/SEASON)%4, tick%DAY)
}
#[test]
fn exact_calendar_boundaries() {
    assert_eq!(calendar(0),(0,0,0));
    assert_eq!(calendar(SEASON-1),(0,0,DAY-1));
    assert_eq!(calendar(SEASON),(0,1,0));
    assert_eq!(calendar(YEAR),(1,0,0));
}

01

Convert real duration

At 20 baseline TPS, how long is 24000 ticks?

Need a hint?

Divide ticks by ticks per second.

Worked solution

1200 real seconds at 1x, or 20 minutes, assuming the baseline rate is actually maintained. If the world is deliberately slowed under overload, measured real duration can differ.

How to verify your result

The conversion names its maintained-rate assumption.

02

Display day one

How can UI show Day 1 while world_tick starts at zero?

Need a hint?

Display labels can be one-based.

Worked solution

Display world_tick / DAY + 1. Keep internal time zero-based so modulo and boundaries remain simple.

How to verify your result

Startup displays Day 1 without shifting season transitions.

03

Advance a capped step

An update has M=16. How do the two counters change?

Need a hint?

Executed updates and represented time are different.

Worked solution

Increment step_tick by one and world_tick by sixteen. Use checked arithmetic according to the counter policy and record the multiplier for deterministic replay.

How to verify your result

The fixture asserts both increments separately.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Day skips at startup

What is happening: UI one-based labels leaked into stored time.

Try this: Keep stored counters zero-based and offset only the label.

Replays change after load

What is happening: step_tick was not serialized.

Try this: Save the executed-update counter with calendar time.

Bomb fuses expire seasonally fast

What is happening: The timer reads world_tick unintentionally.

Try this: Name and test the intended physics/calendar clock.

Explain it without the example

Why keep step_tick when world_tick already exists?

Reasoning to compare

The executed update count seeds deterministic choices and measures physics progress. Calendar time may advance by more than one unit per executed step.
