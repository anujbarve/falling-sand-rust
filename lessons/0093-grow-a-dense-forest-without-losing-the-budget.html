Grow a dense forest without losing the budget

Grow a dense forest using existing plant rules while measuring and bounding its burst workloads.

Previously: Erode island shores with an explicit water policy. Keep that working result available before starting this lesson.

Why we need this now

Sparse plains may pass the frame budget while one forest fire queues thousands of support and growth updates. Reusing the same materials does not preserve the same worst-case workload.

Your result: Grow a dense forest using existing plant rules while measuring and bounding its burst workloads.

01Density changes interactions, not only appearance

A tree template adds wood and attached leaves. Doubling tree count can increase contact, fire propagation, falling leaves, wetness traffic, shadow/exposure invalidations and support searches together. That is why a new forest biome needs a stress fixture even when no new material is introduced.

Generate a small approved-density forest with deterministic positions. Keep its seed and placement configuration fixed while testing. First run a calm wet forest to establish a resting baseline, then ignite one edge during a dry wind and observe both the visible front and the number of secondary jobs requested per tick.

02Measure work where it is generated

Counters should distinguish cell updates, changed columns, support requests, particle emissions, growth edits and draw submissions. A single total tick duration tells you that a frame was slow but not why. Place counters at request sites and report a per-tick maximum alongside the time measurement.

Repeated changes to one structure can request the same support group many times before the support pass runs. Coalescing identical pending keys removes redundant work without pretending the group is already supported. The worked queue holds unique pending IDs and takes only a chosen batch. Its limit is work dispatch capacity, not permission to silently delete the unprocessed requests.

03Bound queue memory and service latency

A per-frame service budget alone does not bound a queue if incoming work exceeds it indefinitely. Decide how requests are merged spatially, how many unique requests can exist, and what overload behavior is visible. For example, represent one dirty region once and enlarge its bounds instead of appending the same cell thousands of times.

Do not defer an unsupported roof forever merely to keep a green FPS number. The accepted design may lower vegetation density, reduce the active view, simplify the support workload or slow the entire simulation uniformly. Record maximum service latency as well as queue length. Forest density is a tunable content cap, not a reason to violate visible behavior.

04Test the complete forest cycle

Use three runs: wet season, dry fire and spring recovery. Wet leaves should resist burning under the approved moisture rule. Dry fire should spread with the same rules used on plains. Regrowth should not overwrite existing structures and should remain blocked where occupancy requires. Inspect canopy drips and leaf litter as well as the silhouette.

Repeat the v1 plains benchmark after the new template variants and material settings are added. Shared tables can regress old scenes. Finally capture the forest at actual cell size; filling every ground pixel with needles or per-cell variation would violate the sparse silhouette style even if the engine can render it.

use std::collections::{BTreeSet, VecDeque};
#[derive(Default)]
struct Pending { order: VecDeque<u32>, keys: BTreeSet<u32> }
impl Pending {
    fn request(&mut self, id: u32) {
        if self.keys.insert(id) { self.order.push_back(id); }
    }
    fn batch(&mut self, limit: usize) -> Vec<u32> {
        let mut out=Vec::new();
        while out.len()<limit {
            let Some(id)=self.order.pop_front() else { break; };
            self.keys.remove(&id);
            out.push(id);
        }
        out
    }
}
fn main() {
    let mut q=Pending::default();
    for _ in 0..1000 { q.request(7); }
    q.request(8); q.request(9);
    assert_eq!(q.order.len(),3);
    assert_eq!(q.batch(2),vec![7,8]);
    assert_eq!(q.batch(2),vec![9]);
    println!("1002 requests became 3 unique pending jobs");
}

Read what each part does

  1. The BTreeSet tracks membership; VecDeque preserves first-request order.
  2. This example deduplicates IDs, not arbitrary overlapping world rectangles. The production key must match the work being coalesced.
  3. A request may be submitted again after service; per-tick group markers and changed-state checks prevent redundant rechecks as needed.

Expected result

1002 requests became 3 unique pending jobs

01

Service only one job

Change batch capacity to1 and drain the queue.

Need a hint?

Unprocessed jobs remain owned by the queue.

Worked solution

The batches are [7], [8], [9], then empty. No unique request is silently discarded to enforce the per-batch bound.

How to verify your result

The union of drained IDs equals the requested unique set.

02

Create a sustained overload

Submit100 unique new IDs per tick and service10.

Need a hint?

Deduplication cannot merge genuinely different IDs.

Worked solution

The queue grows by90 per tick. Add an explicit capacity/overload policy or reduce content/work. Calling the queue bounded merely because batch is bounded would be false.

How to verify your result

A counterexample demonstrates growth and motivates the chosen policy.

03

Review the silhouette

Double tree placement density while keeping the material palette fixed.

Need a hint?

Performance and approved appearance are separate gates.

Worked solution

Measure cost and compare the frame to the sparse silhouette reference. Even a performant dense arrangement may require a lower approved density. Keep the final content value in biome configuration.

How to verify your result

Both the visual review and benchmark report the selected density.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

A forest fire creates frame spikes

What is happening: Many cells request the same expensive derived work.

Try this: Instrument requests and coalesce genuine duplicates before adding threads.

Queue never catches up

What is happening: Unique arrivals exceed service capacity.

Try this: Bound content or revise overload behavior; do not hide infinite debt.

Forest looks noisy despite flat colours

What is happening: Template density or internal detail overwhelms silhouettes.

Try this: Review actual-size frames and simplify shape/density.
