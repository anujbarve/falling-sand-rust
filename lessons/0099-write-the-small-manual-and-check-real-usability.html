Write the small manual and check real usability

Write a concise player-facing quick start and observe whether a new player can perform the core loop without coaching.

Previously: Package a runnable game for Mac Windows and Linux. Keep that working result available before starting this lesson.

Why we need this now

The project promises a world whose cause and effect can be seen without a manual. A manual can support recovery and controls, but it cannot compensate for an unreadable brush selection or invisible save failure.

Your result: Write a concise player-facing quick start and observe whether a new player can perform the core loop without coaching.

01Write for actions the player wants to take

Begin the quick start with one observable loop: choose a material, paint it, stop interacting and watch it respond. Then name the controls for erase, brush size, pan, pause, speed and material/tool pages. Use the actual final bindings from the approved settings rather than copying early proposals that have since changed.

Keep recovery and limitations easy to find. Explain where worlds are saved, how autosave/manual saves behave, how to select a backup and what an unsupported-version message means. State the frozen off-screen rule and the fast-forward approximation plainly; hiding them produces confusing expectations about a house left alone for a season.

02Test discoverability before showing the manual

Give a fresh consenting tester the packaged build and a small task sheet. Ask them to place sand, make a water pool, pause, change a material page, save and reload. Do not explain the controls first: that would measure how well they follow your coaching rather than what the interface communicates. Ask them to think aloud only if comfortable.

Record task success, wrong turns and the exact feedback missing at each point. Avoid collecting personal data or publishing a recording without permission. The useful artifact is an actionable observation such as tester painted behind the material bar or could not tell that speed was physics-limited, not a judgement about the tester’s ability.

03Separate interface repair from documentation repair

If selecting a swatch does not visibly change selection, improve the selection indicator. If saving fails silently, add a clear recoverable message. A paragraph in README explaining these hidden states is not a substitute. Documentation is appropriate for less discoverable but important facts such as backup layout or supported hardware.

Check text at actual physical size and multiple UI scales. Verify that UI scaling does not alter the world-cell footprint. Test mute and rebind/conflict handling if adopted. A no-flash option needs an implementation/approval decision; if offered, it must alter lightning/explosion presentation without removing the simulation event or its audible/other feedback unexpectedly.

04Create a reusable observation record

A compact record includes task, expected observable outcome, actual behavior, time or attempts, and a reproducible issue. Show the original confusion, the interface change and the repeated task result, with the tester’s permission where relevant. This teaches why software feedback matters while keeping the game’s release documentation small and useful rather than turning it into a textbook the player must read.

# Rusty quick start

Choose a material in the bottom bar, paint, then watch the world respond.

| Action | Default control |
| --- | --- |
| Paint / use selected tool | Left mouse button |
| Erase | Right mouse button |
| Paint only empty cells | Alt + left mouse button |
| Brush size | Mouse wheel or [ and ] |
| Select slot | 1–9, then 0 |
| Change bar page | Q / E |
| Pan | Middle drag or WASD |
| Pause / resume | Space |
| Slower / faster | , and . |
| Undo eligible paint edits | Ctrl+Z or Cmd+Z |
| Save / load | F5 / F9 |
| Hide material bar | Tab |
| Mute | M |
| Settings | Escape |

Only the active view and its margin are simulated; off-screen material freezes.
Fast-forward may advance seasons faster than physical motion when limited.
Undo is a local revert: cells changed by the simulation may be skipped.

Find the current world's save location and backup/recovery actions in Settings.
Keep a copy of the world folder before manual recovery or migration.
If loading reports an unsupported version, preserve the files and use a
compatible build; do not delete the world to make the error disappear.

If a save fails, keep the game open and use the shown recovery choices before
quitting. Report the game version, OS and the visible error when asking for help.

Read what each part does

  1. The control table comes from the current design and must be reconciled with the final implemented/rebound controls.
  2. The proposed Settings save-location/recovery entry must exist before this text can claim it; otherwise document the actual implemented path clearly.
  3. The manual names important approximations without dumping engine internals into normal play.

Expected result

A player can locate every core action and the real recovery path; the fresh-tester exercise establishes discoverability separately.

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Observe one uncoached task

Ask a tester to select wood, paint a small shelter and pause.

Need a hint?

Do not announce the shortcut before they try.

Worked solution

Record whether selection is visible, whether painting hits the intended cells and whether pause state is obvious. Turn each failure into one reproducible issue with an observed outcome and desired feedback.

How to verify your result

The report describes interface behavior, not the tester’s intelligence.

02

Remove an implementation detail

Find one manual sentence that only explains internal storage rather than a player decision.

Need a hint?

Ask whether the player can act differently because of it.

Worked solution

A sentence about chunk hash-map layout can be removed. A sentence explaining that off-screen houses stop aging should stay, because it changes what a player expects after panning away.

How to verify your result

The manual is shorter without hiding a meaningful limitation.

03

Test reduced-flash presentation

If a no-flash setting is adopted, trigger lightning with it on.

Need a hint?

Physics and decoration must stay separable.

Worked solution

The target cell still receives the approved heat/ignition effect. The visual flash follows the reduced-flash policy, and other feedback keeps the event understandable. Compare the world result between modes.

How to verify your result

The preference does not secretly disable gameplay reactions.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Tester needs repeated coaching

What is happening: Core controls or feedback are not discoverable.

Try this: Fix the interface and repeat the same task before adding manual paragraphs.

Manual controls disagree with the build

What is happening: The table was copied from an older proposal.

Try this: Generate or review bindings against the actual final configuration.

Accessibility setting changes physics

What is happening: Presentation and simulation events share one boolean path.

Try this: Route the same world event through separate presentation preferences.

Explain it without the example

Why watch a fresh tester instead of explaining every control first?

Reasoning to compare

Coaching hides discoverability problems. Observing unprompted behavior reveals which controls or feedback need improvement.

Self-check only: test a prediction or ask your tutor if anything still feels arbitrary.

Finish with evidence

A tester completes the core actions without developer coaching. Documented limitations match observed behavior.

Make one small variation without copying: predict it, run it and explain any difference. On another day, repeat one exercise from memory before starting the next lesson. Ask your tutor about any step you can execute but cannot explain.
