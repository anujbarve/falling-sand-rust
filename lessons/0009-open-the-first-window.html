Why we need this now

Our program can already hold and update state, but it only speaks through terminal lines. macroquad provides a window and drawing API so the same Rust code can begin showing the world. We will inspect the minimal frame loop instead of pasting an unexplained game engine.

Your result: Launch a responsive 1280×720 window with the game’s dark-sky base colour.

01Add the dependency in the manifest

Open game/Cargo.toml. Under its existing [dependencies] heading, add macroquad = "=0.4.16". The leading equals sign pins this direct dependency to the version used by the design. Do not add a second dependencies heading. Save the manifest and source before running Cargo.

The first build downloads and compiles dependencies, so it can take longer than our terminal-only examples. Cargo.lock records resolved dependency versions and should be kept with this application. A downloaded crate is library code available to the package; it does not replace Rust’s compiler or create a window until our program calls into it.

02Read the configuration as data

The window_conf function returns a Conf value with named settings. Width and height choose the teaching window’s size. high_dpi:false and window_resizable:false deliberately simplify the first pixel mapping. sample_count:1 avoids multisample edge smoothing in this example. The remaining fields come from Default::default().

The title uses .to_owned() to provide the owned string expected by the configuration. Treat that as a named conversion at the API boundary for now; ownership will be explored directly in the next few modules. These restrictions are scaffolding, not changes to the final game’s resizable, DPI-aware design.

03Follow one complete frame

The attribute above main connects our entry point to macroquad and supplies the configuration function. Inside main, loop repeats the frame body. First clear_background fills the new frame. Then next_frame().await yields control to the framework so the frame can be presented and events processed.

Without that yield, a tight endless loop would prevent normal progression. The async spelling belongs to macroquad’s entry API; full asynchronous Rust is not a prerequisite for drawing the first frame. Learn the narrow contract: this awaited call hands control back between frames. We will keep simulation timing separate later rather than assuming one loop iteration equals a fixed amount of game time.

04Run and observe the boundary between code and operating system

Replace src/main.rs with the worked example, run cargo check, then cargo run. A dark window should open. Move it, close it through the operating system, and verify the terminal returns. Change only the title, rebuild, and confirm the visible change.

The colour channels 15,26,51 encode the reference night colour #0f1a33; alpha 255 makes it fully opaque. This is a flat teaching background, not the final sky ramp. If the native window fails, preserve the actual error and OS details. A successful compilation does not prove that every GPU, driver or display mode can create the graphics context; the M0 hardware gate exists for that reason.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

use macroquad::prelude::*;

fn window_conf() -> Conf {
    Conf {
        window_title: "Rusty — learning".to_owned(),
        window_width: 1280,
        window_height: 720,
        high_dpi: false,
        window_resizable: false,
        sample_count: 1,
        ..Default::default()
    }
}

#[macroquad::main(window_conf)]
async fn main() {
    loop {
        clear_background(Color::from_rgba(15, 26, 51, 255));
        next_frame().await;
    }
}

Read what each part does

  1. The prelude import makes the drawing names available.
  2. Configuration is returned before the frame loop starts.
  3. Every loop iteration clears and yields; there is no simulation yet.

Expected result

A responsive dark-blue window opens with the configured title. Closing it ends the program and returns the terminal prompt.

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Change one visible property

Change the title and then one colour channel in separate runs.

Need a hint?

Configuration and per-frame drawing are different parts of the example.

Worked solution

Edit window_title to change the operating-system title. Edit one RGB value in clear_background to change the frame. Restore the approved base colour afterwards so later comparisons have a stable background.

How to verify your result

You can identify which change affects configuration and which affects drawing.

02

Explain the redraw

Why call clear_background inside the loop instead of only once before it?

Need a hint?

Each presented frame is built again through the frame API.

Worked solution

The frame loop explicitly redraws the current scene. Clearing establishes that frame’s background before objects are drawn. Relying on old frame contents is not the rendering contract we are using.

How to verify your result

You can narrate clear, draw, yield as separate operations.

03

Inspect dependency setup

Temporarily misspell macroquad in the import and read the first error.

Need a hint?

Manifest package names and source imports must agree with available crates.

Worked solution

Restore use macroquad::prelude::*;. Do not add random dependencies to satisfy a typo. The prelude brings commonly used macroquad names into scope for this small example.

How to verify your result

The repaired program checks and launches again.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

unresolved crate macroquad

What is happening: The dependency is missing, unsaved, or added to the wrong manifest.

Try this: Check game/Cargo.toml and run Cargo from game/.

A black or frozen unresponsive window

What is happening: The frame loop may not reach next_frame().await.

Try this: Compare loop structure and restore the yield; preserve any actual graphics error.

Physical pixel size differs on another display

What is happening: DPI and drawing units can differ.

Try this: Keep the low-DPI teaching restriction now; production art-buffer/DPI handling is a later lesson.

Explain it without the example

What job does next_frame().await serve in this macroquad loop?

Reasoning to compare

It yields control to the framework for the next frame. A tight loop without that yield prevents normal frame progression and event handling.
