Paint materials into the world

Convert cursor positions into cell edits and prevent painting outside the world view.

Previously: Build piles and level water. Keep that working result available before starting this lesson.

Why we need this now

The sandbox begins when the player can place matter. Mouse input lives in drawing coordinates, while world storage uses cell coordinates. A careful conversion and input ownership rule keep a click from painting the wrong slot or leaking through UI panels.

Your result: Convert cursor positions into cell edits and prevent painting outside the world view.

01Read input as a request, not direct world mutation

macroquad provides mouse_position and button state queries. A held button means the player may want repeated paint actions; a just-pressed query means an event begins once. Choose the query according to the tool: continuous painting differs from a one-shot command.

First log the drawing coordinates or show a simple cursor marker. Do not immediately cast them into vector indices. A position outside the world, including negative values or UI borders, is a normal input case and must be rejected or consumed before reaching storage.

02Invert the drawing transform

If drawing a cell uses screen_x=view_origin_x+(world_x-camera_x)*cell_size, picking reverses that relationship. Subtract the view origin, divide by cell size, take the appropriate floor, then add the camera coordinate. In the initial no-camera window, that reduces to floor(mouse_x/4).

Check that the cursor is inside the view rectangle before converting. Truncating a small negative float toward zero can otherwise paint column0 even though the cursor lies outside the world. The focused helper validates first, then floors. Production physical-pixel/DPI conversion is another boundary, not a reason to mix raw framebuffer and logical mouse units.

03Use one paint command for input and tests

Define a paint operation receiving validated coordinates, selected material and brush settings. Both the mouse handler and headless fixtures should call that operation. This prevents tests from bypassing the actual edit policy. Normal paint replaces the covered cells; the later Alt mode fills air only.

For the first one-cell brush, left hold paints sand and right hold paints air. Decide priority if both buttons are held. Ignore events consumed by UI before sending a world command. Even before the final HUD exists, keep this ordering explicit so the first swatch click does not also modify the world underneath.

04Check continuity and boundaries

A mouse can move several cells between frames. Painting only the current point leaves gaps during fast drags; the later brush stroke should rasterize the segment between successive sampled points. Start by documenting that limitation, then add a bounded line traversal rather than increasing frame rate to hide it.

Test every view edge, a negative position, a coordinate exactly at width and a click over a mock UI rectangle. The result should be a predictable brush footprint with no edits outside the intended region. Cursor display is feedback; it should use the same conversion as the actual paint operation.

fn pick(mouse_x:f32,mouse_y:f32,view_w:f32,view_h:f32)->Option<(i32,i32)> {
    if !mouse_x.is_finite() || !mouse_y.is_finite() || mouse_x<0.0
        || mouse_y<0.0 || mouse_x>=view_w || mouse_y>=view_h {return None;}
    Some(((mouse_x/4.0).floor() as i32,(mouse_y/4.0).floor() as i32))
}
fn main() {
    assert_eq!(pick(48.5,20.1,1280.0,720.0),Some((12,5)));
    assert_eq!(pick(-0.1,20.0,1280.0,720.0),None);
    assert_eq!(pick(1280.0,20.0,1280.0,720.0),None);
    println!("view picking checks passed");
}

Read what each part does

  1. The example isolates picking from live mouse APIs so edges are testable.
  2. Half-open bounds match the grid’s valid coordinate range.
  3. No external input library beyond macroquad is needed.

01

Test all edges

Add top, bottom and right-edge tests, including exact equality.

Need a hint?

The view is half-open: its far edge is outside.

Worked solution

For height720, y719.9 is inside and y720 is outside. Negative y is outside. Use these values to confirm the same convention on both axes.

How to verify your result

No edge coordinate wraps into a valid cell unexpectedly.

02

Add a view offset

Assume the world rectangle starts at x100,y50 and invert that offset before picking.

Need a hint?

Subtract the rectangle origin before dividing.

Worked solution

Validate mouse against the shifted rectangle, then call the local picker with mouse_x-100 and mouse_y-50. A click at148.5,70.1 should still select12,5.

How to verify your result

The same cell is picked after moving the view rectangle.

03

Block UI clicks

Place a mock panel over part of the view and consume its click.

Need a hint?

Dispatch UI before world editing.

Worked solution

If the panel handles the event, return without painting. Verify that selecting a material changes selection but leaves the underlying cells untouched.

How to verify your result

One click has one intended consumer.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Outside-left clicks paint cell0

What is happening: Negative drawing coordinates were truncated before bounds validation.

Try this: Validate the view first, then floor the local coordinate.

Painting drifts after camera pan

What is happening: The inverse transform omitted camera or view origin.

Try this: Write the draw equation and algebraically invert it.

Fast drags leave gaps

What is happening: Only sampled points are painted.

Try this: Rasterize the segment between input samples using a bounded stroke operation.

Explain it without the example

Why must a mouse position be converted before indexing the world?

Reasoning to compare

Mouse and world coordinates use different units and may have different origins. Indexing expects valid cell coordinates, not raw display pixels.
