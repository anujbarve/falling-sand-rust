Build a small readable material and time bar

Route one click either to the material bar or to the world, and make the selected material visibly unambiguous.

Previously: Draw weather without changing its physics. Keep that working result available before starting this lesson.

Why we need this now

A beautiful material bar is broken if clicking Wood also paints a wood block behind the button. Input ownership is a behavior problem before it is a styling problem.

Your result: Route one click either to the material bar or to the world, and make the selected material visibly unambiguous.

01Start with one click and two possible consumers

The application receives mouse position and button state. UI hit testing should decide whether that event belongs to a bar/control before any world paint command is emitted. Treat input as a command-routing step; drawing a panel over the world does not automatically stop the underlying code from reacting.

Choose coordinate units explicitly. The material bar is laid out in drawing/UI coordinates, while world picking also needs the physical viewport origin, DPI conversion and cell scale. Convert at named boundaries instead of mixing raw mouse numbers with chunk positions.

02Make pages data-driven

There are more materials/tools than ten number slots. Represent pages as arrays of entries with label, swatch, key slot and action. Q/E changes page; number keys select within that page. A slot’s index is not automatically a Material ID because the Tools page holds commands instead.

Use an enum for an entry action such as SelectMaterial or SelectTool. Keep selected state in one place so a key press and a UI click use the same selection function. Greyed/unavailable tool feedback must explain the actual cooldown/state, not merely look disabled.

03Keep selection and hints readable

A muted UI still needs a clear selection boundary and readable text. Use the approved panel/text/selection palette and independent UI scaling. At native four-pixel cells, excessively tiny HUD text can undermine an otherwise calm frame. Test the actual display sizes instead of reviewing only a zoomed screenshot.

Show day, season, clock speed and physics-limited/slowed state consistently. The player should be able to tell when seasons are accelerated beyond physical updates. Hints may fade after use, but key labels and current selection should not become ambiguous when time changes.

04Separate the hit-test model from drawing

The worked terminal function checks a simple row of ten slots. It returns a slot or no slot using a half-open rectangle: left/top inclusive, right/bottom exclusive. That convention prevents a boundary pixel belonging to two adjacent controls.

In the real frame first compute ui_consumed. If true, dispatch the UI action and skip world painting for that event. Otherwise convert to a valid world position and paint. Test gaps, edges, clicks while dragging from the bar, and hidden-UI behavior deliberately; dragging capture policy should not be accidental.

fn material_slot(x:i32,y:i32,left:i32,top:i32)->Option<usize> {
    const SLOT:i32=32;
    const COUNT:i32=10;
    if x<left || y<top || y>=top+SLOT || x>=left+COUNT*SLOT {return None;}
    Some(((x-left)/SLOT) as usize)
}
fn main() {
    assert_eq!(material_slot(100,200,100,200),Some(0));
    assert_eq!(material_slot(132,200,100,200),Some(1));
    assert_eq!(material_slot(420,200,100,200),None);
    assert_eq!(material_slot(100,232,100,200),None);
    let clicked_slot=material_slot(140,210,100,200);
    let paint_world=clicked_slot.is_none();
    assert!(!paint_world);
    println!("UI click selects slot {:?}; world paint={paint_world}",clicked_slot);
}

Read what each part does

  1. The rectangle is half-open so its far edge belongs to outside/gap handling.
  2. The helper returns a slot index, not a material ID; page data maps that slot to an action.
  3. Production layout may contain padding/gaps, which must be included in hit-testing instead of pretending the visual and hit rectangles match automatically.

Expected result

UI click selects slot Some(1); world paint=false

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

01

Find the boundary

For left=100 and slot width=32, which slot owns x=132?

Need a hint?

Use a half-open first slot [100,132).

Worked solution

Slot 1 owns x=132; slot 0 ends just before it. The boundary is not a double click target.

How to verify your result

Tests agree exactly at each adjacent-slot boundary.

02

Prevent paint-through

The UI reports a valid slot but world input still paints. Where is the ordering wrong?

Need a hint?

Drawing order does not control event consumption.

Worked solution

Handle selection first and suppress the world command for that consumed event. Both mouse and keyboard selection should update one shared selected-action state.

How to verify your result

A click test changes selection and no world cells.

03

Test page semantics

On Tools page slot 0 means Fire starter. Should pressing 1 paint Material ID 0?

Need a hint?

The page defines the action, not the key digit.

Worked solution

No. Resolve slot 0 through the active page’s entry action. A SelectTool action routes to tool use rather than painting an unrelated material.

How to verify your result

Number-key and click selection choose the same visible tool.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Selecting a material paints behind the bar

What is happening: World command is emitted before UI consumption.

Try this: Route input through UI first and skip painting for consumed events.

Number keys disagree with selected page

What is happening: Slot index is cast directly to Material ID.

Try this: Map the current page’s slot to a typed action.

Bar looks clickable where nothing happens

What is happening: Hit boxes and scaled visual layout differ.

Try this: Derive both drawing and hit rectangles from the same layout data.

Explain it without the example

Why resolve UI input ownership before sending paint commands?

Reasoning to compare

The same click can otherwise select a tool and modify the world underneath it. Input needs one intended consumer.
