Store chunks by coordinate with a map

Use a coordinate-keyed map for sparse chunk storage while keeping update order explicit.

Previously: Test a tiny scene without a window. Keep that working result available before starting this lesson.

Why we need this now

An explored world may contain far-apart regions. A giant vector spanning every coordinate between them would allocate empty space unnecessarily. A map stores only resident chunk keys, but its container iteration order must not accidentally become the simulation’s update order.

Your result: Use a coordinate-keyed map for sparse chunk storage while keeping update order explicit.

01Choose a key that names the storage unit

A chunk key can begin as a pair of signed integer coordinates, such as (chunk_x,chunk_y). The map associates that key with an owned Chunk value. Querying a missing key returns Option because absence is expected in a sparse procedural world. It does not automatically mean corruption or an error.

Start with a tiny payload such as a vector length or identifier before storing full chunks. This isolates insertion, lookup and removal from the movement rules. Then connect the same interface to real Chunk storage. Storage choices should not rewrite gravity or material identities.

02Understand ownership of entries

Inserting an owned Chunk transfers that value into the map. get lends shared access; get_mut lends mutable access to one existing value. Removing an entry returns ownership so it can be saved, discarded or transferred to a background job under the chosen policy.

A borrowed entry cannot remain live while you arbitrarily restructure the same map. Plan the operation in phases: identify keys, borrow the needed data, finish that access, then perform structural changes. Copying a small coordinate key is cheap and often clarifies this boundary; cloning every chunk to avoid borrows is not the same thing.

03Separate lookup structure from deterministic traversal

HashMap does not promise the stable iteration order required by our simulation contract. Collect active keys and sort them according to the explicit phase/scan plan before updating. Alternatively an ordered map may help for some traversal needs, but it still does not substitute for the specified four-phase ordering.

The focused example inserts keys in one order and prints them after sorting. A repeatable output demonstrates that update order can be defined independently of insertion order. Later the phase selector groups by coordinate parity, while per-chunk scan order follows the movement contract.

04Check sparse behavior and eviction readiness

Insert chunks at0,0 and100000,0. The map should contain two entries, not allocate the entire distance between them. Remove one and inspect the returned value. Before persistent saving exists, only unchanged regenerable chunks may be discarded; edited chunks must remain resident under the temporary M0 policy.

This lesson is about data organization, not a promise of infinite memory. The cache lesson will enforce a resident budget and the saving milestone will make edited eviction recoverable. A sparse map makes those policies possible but does not implement them by itself.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

use std::collections::HashMap;
fn main() {
    let mut chunks:HashMap<(i32,i32),usize>=HashMap::new();
    chunks.insert((100_000,0),4096);
    chunks.insert((0,0),4096);
    assert_eq!(chunks.len(),2);
    assert_eq!(chunks.get(&(1,0)),None);
    let mut keys:Vec<_>=chunks.keys().copied().collect();
    keys.sort_unstable();
    println!("ordered keys: {keys:?}");
    assert_eq!(chunks.remove(&(100_000,0)),Some(4096));
}

Read what each part does

  1. The usize payload stands in for a chunk only to isolate map mechanics.
  2. Sorted keys are an explicit traversal input.
  3. Sparse storage is not itself a cache or save system.

Expected result

ordered keys: [(0, 0), (100000, 0)]

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Reject accidental insertion

Use get on a missing key and show that map length stays unchanged.

Need a hint?

A lookup and an insertion are different operations.

Worked solution

Record len before and after get. Missing lookup returns None without allocating a chunk. Generation should happen through an explicit loading policy, not an unexpected observation side effect.

How to verify your result

The map still contains the original number of entries.

02

Mutate an existing entry

Use get_mut to change one payload from4096 to2048.

Need a hint?

The mutable reference belongs to that stored value.

Worked solution

if let Some(size)=chunks.get_mut(&(0,0)) { *size=2048; }

This fragment belongs before removal in main.

How to verify your result

A later shared lookup observes2048.

03

Change insertion order

Insert the two keys in the opposite order and compare sorted output.

Need a hint?

The explicit traversal should not depend on how storage was filled.

Worked solution

The sorted key list remains the same. This protects only ordering; full deterministic physics additionally needs identical state, inputs, rules and RNG choices.

How to verify your result

The demonstration’s printed ordering is reproducible.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Physics changes after map growth

What is happening: Container iteration order may be driving updates.

Try this: Build explicit ordered phase keys before simulation.

Missing lookups create chunks

What is happening: An entry-insertion API was used where observation was intended.

Try this: Use get for lookup and a deliberate generation/loading path for creation.

Cannot mutate map while borrowing an entry

What is happening: A structural operation overlaps an active borrow.

Try this: Finish the entry operation, then mutate the map structure in a separate phase.

Explain it without the example

Why not let hash-map iteration order define the simulation scan order?

Reasoning to compare

That order is not the game’s specified update order. An explicit ordering prevents container details from changing results.
