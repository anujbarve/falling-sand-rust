Package a runnable game for Mac Windows and Linux

Prepare native game packages containing the executable, assets and licences, and prove they launch outside the source checkout.

Previously: Automate gates on each target platform. Keep that working result available before starting this lesson.

Why we need this now

cargo run is a development convenience. A player should not need Cargo, your repository layout or your current working directory to find a sound file and start a world.

Your result: Prepare native game packages containing the executable, assets and licences, and prove they launch outside the source checkout.

01Distinguish building from distributing

From game/, cargo build --locked --release --bin game creates the optimized native executable for the host target, assuming the package binary is named game. On macOS/Linux it normally appears at target/release/game; on Windows it is game.exe. If the package has another binary name or a configured target directory, use that actual output rather than copying a nonexistent assumed path.

cargo package is different: it creates a source crate archive for Cargo distribution. It does not assemble an end-user desktop application. A native desktop package also needs the runtime resources, notices and any non-system dynamic dependencies selected by your backend. Test on a machine without the source tree to discover assumptions that a developer’s environment hides.

02Choose an explicit package layout

For a first Linux or Windows portable build, use a folder containing game or game.exe, assets/, LICENSE and THIRD-PARTY-NOTICES.txt. On macOS, a conventional app bundle places the binary under Rusty.app/Contents/MacOS/game and resources under Contents/Resources/assets, with Contents/Info.plist identifying the executable and bundle. Use your chosen actual application identifier and version before signing; the product name is still a proposal.

On macOS the folder creation/copy sequence can begin with mkdir -p dist/Rusty.app/Contents/MacOS dist/Rusty.app/Contents/Resources, cp target/release/game dist/Rusty.app/Contents/MacOS/game, and cp -R assets dist/Rusty.app/Contents/Resources/assets. These commands assume game/assets already contains the licensed runtime assets, not the HTML course assets at repository root. Add the property list and notices before calling the bundle complete.

03Resolve resources relative to a known installation root

A relative path such as assets/rain.wav is interpreted relative to the process working directory. Launching from Finder or a shortcut may choose a different directory than cargo run. Use an explicit runtime resource root appropriate to the selected package layout, and pass the resulting paths into loaders. The worked function derives a root from an executable path for the two layouts above.

current_exe can fail and has platform-specific behavior, so propagate its Result. A macOS signed/distributed bundle may need platform bundle-resource lookup or a documented robust equivalent for its deployment environment; verify that during the native packaging check. Saves and preferences belong in a writable user-data location, not inside a potentially read-only app bundle.

04Validate on the intended platform and channel

Build and test each native artifact on its OS first. Cross-compiling Rust code does not by itself supply every linker, SDK and runtime dependency. Record CPU architecture, OS version and binary target; an Apple-silicon artifact is not automatically an Intel Mac artifact. Recheck signing/notarization/store requirements against the actual distribution channel before release.

For each package, copy it to a clean test directory, launch without the repository as the working directory, paint, hear or gracefully disable sound, save, quit and reload. Inspect linked-library dependencies with available native tools and verify licence files. Keep a checksummed artifact manifest so the package reviewed is the package eventually distributed. This lesson prepares local artifacts; it does not upload or publish them.

use std::path::{Path,PathBuf};
fn asset_root(executable:&Path,mac_bundle:bool)->Result<PathBuf,String> {
    let parent=executable.parent().ok_or("executable has no parent")?;
    if mac_bundle {
        let contents=parent.parent().ok_or("missing Contents directory")?;
        Ok(contents.join("Resources").join("assets"))
    } else { Ok(parent.join("assets")) }
}
fn main() {
    let flat=asset_root(Path::new("dist/rusty-linux/game"),false).unwrap();
    let app=asset_root(Path::new("dist/Rusty.app/Contents/MacOS/game"),true).unwrap();
    assert_eq!(flat,PathBuf::from("dist/rusty-linux/assets"));
    assert_eq!(app,PathBuf::from("dist/Rusty.app/Contents/Resources/assets"));
    println!("flat: {}",flat.display());
    println!("app: {}",app.display());
}

Read what each part does

  1. PathBuf preserves path components without manually concatenating slash strings.
  2. The function is a layout contract, not a filesystem existence check. Validate required resources and recover from missing ones separately.
  3. The sample executable paths are fixtures. Production obtains and validates its actual runtime location.

Expected result

Two asset paths print, matching the flat portable folder and macOS bundle resource layout.

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

01

Break the working directory assumption

Launch a packaged build from a different directory.

Need a hint?

Do not copy the source checkout into the test folder.

Worked solution

A loader based only on assets/rain.wav may fail. The resource-root implementation should still resolve the bundled clip. Verify both launch and actual playback, since the audio feature and asset presence are separate requirements.

How to verify your result

No resource path depends on the developer’s current directory.

02

Inspect the package inventory

List files in the native package and compare with runtime lookups.

Need a hint?

An unused source directory is not a required runtime resource.

Worked solution

Include the executable, referenced assets, licence/notice files and required non-system libraries. Exclude build caches and personal saves. Every loader path should resolve inside the selected resource root or an intentional user-data root.

How to verify your result

The inventory contains all used assets and no accidental private world data.

03

Test a fresh save location

Run the package from a read-only installation folder.

Need a hint?

Writable user data is not application resources.

Worked solution

The game should create and recover saves in its documented writable user location. If it tries writing inside Contents/Resources or next to the executable, change the data-root policy before release.

How to verify your result

Saving works without modifying the installed package.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Works with cargo run but not double-click

What is happening: Resources are relative to the checkout working directory.

Try this: Use and test an explicit package resource root.

Package runs only on the build Mac

What is happening: Architecture/OS/runtime dependencies were not recorded.

Try this: Build and smoke-test native artifacts for each claimed target.

Users cannot save after installation

What is happening: Save paths point inside a read-only app location.

Try this: Separate writable user data from bundled read-only resources.

Explain it without the example

Why test launching outside the repository working directory?

Reasoning to compare

Relative development asset paths can accidentally depend on the source checkout. A distributable must locate its assets in the installed package.
