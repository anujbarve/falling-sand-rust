Automate gates on each target platform

Run formatting, linting and headless regression suites on native Mac, Windows and Linux CI jobs without confusing them with hardware certification.

Previously: Keep releases compatible and saves recoverable. Keep that working result available before starting this lesson.

Why we need this now

A local green test run can miss path, compiler and platform differences. CI repeats automated checks on clean machines, but it cannot stand in for playing the game on the actual minimum GPU and CPU.

Your result: Run formatting, linting and headless regression suites on native Mac, Windows and Linux CI jobs without confusing them with hardware certification.

01Choose what can genuinely run unattended

Start with deterministic headless simulation tests, save fixtures, formatting and linting. These do not need a game window. Keep real graphics/audio checks as separate jobs or manual reports with explicit requirements rather than launching a window on a runner that has no display server and calling the resulting failure a physics bug.

Use cargo test --lib when the production simulation is in a library and graphical startup is in the binary. Do not hide all tests behind an ignored annotation just to get a green pipeline. The purpose of the architecture lessons was to make the core state/rules independently executable.

02A matrix repeats one contract on several operating systems

A GitHub Actions matrix creates a job for each listed OS. The YAML below checks out source, selects the stable toolchain with required components, then invokes the same commands in game/. A local developer can run those commands too. Add a separate minimum-supported-Rust-version job only after choosing and recording that supported version.

Pin action revisions according to the project’s dependency policy when preparing the real workflow. The example uses a documented major action reference as readable teaching syntax, not a claim that major tags are immutable. Maintain permissions narrowly and never print secrets as a debugging shortcut.

03Keep random reliability deterministic enough to diagnose

The fixed-seed regression suite should always report its seed and multiplier configuration. The32-seed reliability suite uses a stored seed list so a failure can be repeated locally. Avoid replacing the seed list with a new wall-clock random value on every CI run: that creates a moving target before you have characterized the failure.

Long-running soak tests may run in a separate scheduled or manually triggered job, but their results still belong to release evidence. Do not remove a slow required gate silently because it lengthens pull-request checks. State which tests run on each change and which must pass before a release candidate is accepted.

04Read the first failure and reproduce it

A pipeline log is another compiler/test transcript. Read the earliest relevant error, identify OS/toolchain/test/seed, and run the same command locally where possible. If a Windows path test fails while Linux passes, check path assumptions before altering physics. If a clippy warning appears only on a newer toolchain, decide whether to fix it or pin the toolchain intentionally.

The workflow does not prove60FPS on an i3 or visual alignment with approved references. Store those raw target-hardware reports and capture conditions alongside the candidate revision. Automated and manual evidence can complement each other without pretending they are interchangeable. No workflow is uploaded or run by this lesson until you commit and explicitly use the repository’s CI process.

Read → predict → run → change

Walk through the working example

Create .github/workflows/check.yml at the repository root after agreeing the CI plan. This example is a complete workflow, not a command to run inside Rust.

Download this worked example ↧

name: Rust checks
on:
  pull_request:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  headless:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
    runs-on: ${{ matrix.os }}
    defaults:
      run:
        working-directory: game
    steps:
      - uses: actions/checkout@v4
      - name: Select Rust tools
        run: |
          rustup toolchain install stable --profile minimal --component rustfmt --component clippy
          rustup default stable
      - name: Formatting
        run: cargo fmt --all -- --check
      - name: Compile
        run: cargo check --locked --all-targets
      - name: Lints
        run: cargo clippy --locked --all-targets -- -D warnings
      - name: Headless tests
        run: cargo test --locked --lib

Read what each part does

  1. The working-directory is game because Cargo.toml belongs to the learner-created package, not the course root.
  2. --locked rejects unintended lockfile changes in CI rather than silently resolving a different dependency graph.
  3. The runner may need platform-native system libraries for the chosen backend; verify those requirements on actual runner failures instead of guessing a universal install command.

Expected result

Three native headless jobs run the listed checks; graphics/performance reports remain separate evidence.

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Prove the red path

Introduce a harmless formatting deviation on a temporary local edit.

Need a hint?

A useful gate must fail when its contract is broken.

Worked solution

cargo fmt --all -- --check exits nonzero. Run cargo fmt to repair the source and rerun the check. Do not commit the deliberate error.

How to verify your result

You observe both failure and repair using the same command as CI.

02

Reproduce a random failure

A log reports seed17 and multiplier32. What must your local command reproduce?

Need a hint?

Both the fixture and schedule matter.

Worked solution

Run the same fixture with seed17, multiplier32, initial state and relevant input sequence. Matching only the terrain seed is insufficient if the tick sequence differs.

How to verify your result

The local failure is the same counterexample.

03

Separate platform evidence

All cloud jobs pass. Can the release claim minimum i3 support now?

Need a hint?

The runner is not the floor machine.

Worked solution

No. Record an actual floor-machine run at the specified active count/resolution, graphics startup and frame-time conditions. CI proves the contracts it executed, not unexecuted hardware behavior.

How to verify your result

The release report names each claim and its evidence source.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

CI cannot find Cargo.toml

What is happening: Commands run from repository root instead of game/.

Try this: Set the working directory or use the manifest path consistently.

Tests try to open a window

What is happening: Graphical startup leaked into the headless test target.

Try this: Keep simulation in a library and explicitly test that target.

A green job hides skipped reliability tests

What is happening: The job runs a smaller suite than release acceptance.

Try this: List and verify actual test selection in logs and release gates.

Explain it without the example

Why can't a successful cloud CI run certify performance on the target i3?

Reasoning to compare

The runner is different hardware and may lack the relevant graphics path. Performance and compatibility claims need evidence on the actual target.
