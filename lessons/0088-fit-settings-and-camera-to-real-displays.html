Fit settings and camera to real displays

Calculate a centred, whole-cell view that fits the active-cell budget and map input into it at different physical display sizes.

Previously: Mix sound from simulation state. Keep that working result available before starting this lesson.

Why we need this now

A fixed four-pixel cell cannot fit arbitrarily many cells on slow hardware. The view must shrink inside a panel instead of stretching the pixels or freezing a strip of world.

Your result: Calculate a centred, whole-cell view that fits the active-cell budget and map input into it at different physical display sizes.

01Name the three sizes before doing arithmetic

Window drawing dimensions, physical framebuffer dimensions and simulation-cell dimensions are not interchangeable. macroquad screen_width and screen_height are DPI-adjusted drawing values. The art buffer must be sized from the intended physical rectangle, with a consistent conversion back to drawing coordinates for presentation and pointer input. In a low-DPI prototype the numbers may coincide, which hides this distinction.

For a physical 1280 by 720 view, integer division by four gives 320 by 180 visible cells. Add 16 cells on each side before applying the simulation budget: (320+32)*(180+32)=74,624 active cells. A budget check using only visible cells is too optimistic.

02Choose a fitting rectangle without stretching cells

Find the largest rectangle approximately matching the window aspect ratio whose active count fits the machine cap. Whole-cell rounding means an exact aspect match may be impossible; leave odd edge pixels in the surrounding panel. The example scans candidate widths, derives a height from the target ratio, and checks the active count. This is a startup/resize operation, not a loop to run per simulated cell.

It uses floating-point ratio calculation only for layout. Cell counts and budgets remain integers. For production, document the tie-break for near-equal candidates and test extremely narrow windows. A rectangle with zero visible cells is not a meaningful game view; show a minimum-size message rather than attempting to index it.

03Centre first, then convert input

If the fitted physical view is width V inside a physical window width W, its left origin is (W-V)/2, rounded to a physical pixel. Mouse positions must first enter the same coordinate space. Subtract that origin and divide by four to locate a visible cell. Reject a pointer outside the view before adding camera coordinates.

A click on a capped side panel must not paint a hidden cell. Likewise UI scaling may enlarge text independently without changing the world rectangle or four-physical-pixel cell footprint. Treat the panel, UI hit boxes and world mapping as three explicit rectangles rather than a single screen-wide coordinate assumption.

04Persist preferences, not stale geometry

Save the requested graphics preset, UI scale and camera world position. Recompute the actual fitting rectangle on startup because a different monitor, DPI or machine budget can change it. Storing a previously computed pixel rectangle and reusing it blindly produces off-screen UI and wrong input conversion.

The example proves a budget-fitting kernel with no window. Integrate its result into the art-buffer allocation, presentation viewport and input conversion together. Inspect 720p, Retina/native fullscreen, a tall window and an odd-width window. A successful integer calculation cannot establish that the graphics backend used the same physical dimensions, so include an actual pixel-footprint check in the manual capture.

fn fit(window_w: u32, window_h: u32, budget: u64) -> (u32, u32) {
    if window_w < 4 || window_h < 4 { return (0, 0); }
    let max_w = window_w / 4;
    let max_h = window_h / 4;
    let ratio = window_h as f64 / window_w as f64;
    let mut best = (0, 0);
    for w in 1..=max_w {
        let h = ((w as f64 * ratio).round() as u32).clamp(1, max_h);
        let active = u64::from(w + 32) * u64::from(h + 32);
        if active <= budget && u64::from(w)*u64::from(h) >
            u64::from(best.0)*u64::from(best.1) { best = (w, h); }
    }
    best
}
fn main() {
    assert_eq!(fit(1280, 720, 74_624), (320, 180));
    let (w,h) = fit(1920,1080,74_624);
    assert_eq!((w,h),(320,180));
    assert!(u64::from(w+32)*u64::from(h+32) <= 74_624);
    println!("1920x1080 window: {}x{} physical world pixels",w*4,h*4);
}

Read what each part does

  1. The 32 added cells represent two 16-cell margins, not a 32-cell margin on every side.
  2. The sample chooses the nearest integer height for each candidate width; it is a documented layout policy, not a universal optimizer for every aspect tolerance.
  3. The example rejects tiny windows but production also needs a chosen minimum readable viewport.

Expected result

1920x1080 window: 1280x720 physical world pixels

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

02

Pick inside a capped view

A 1280-pixel world rectangle is centred in a 1920-pixel window. Convert physical pointer x=360 into a cell column relative to the view.

Need a hint?

The left panel is 320 pixels wide.

Worked solution

Subtract 320 to get x=40 within the view. Divide by four to get local column 10. Pointer x=300 lies outside and must be rejected.

How to verify your result

03

Restore on another display

Load settings saved on Retina into a 1280 by 720 low-DPI window. Which values should be recalculated?

Need a hint?

User intent and derived geometry are different.

Worked solution

Retain valid camera/preset preferences, recompute physical dimensions, view bounds, art-buffer size and input transforms. Clamp unsupported preferences explicitly rather than stretching cells.

How to verify your result

A cell under the pointer remains the same cell the renderer shows.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Cells double in physical size on Retina

What is happening: Logical drawing units were treated as framebuffer pixels.

Try this: Make the DPI conversion explicit at presentation and input boundaries.

Paint is offset by a side panel

What is happening: Pointer conversion used screen origin instead of world-view origin.

Try this: Subtract the fitted rectangle origin before cell conversion.

Budget passes but frame time fails

What is happening: Active-cell count is a proxy, not a timing guarantee.

Try this: Measure real tick/frame costs and retain the watchdog policy.

Explain it without the example

Why can UI scale change while world-cell size remains fixed?

Reasoning to compare

UI legibility and world extent are separate concerns. The design fixes physical cell size but may choose independent integer text/panel scaling.
