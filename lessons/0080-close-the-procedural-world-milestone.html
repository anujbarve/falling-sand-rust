Why we need this now

Finishing the procedural world means its parts work together under repetition. A single pleasant pan or successful load cannot reveal every boundary, activation or persistence failure.

Your result: Produce a reproducible M4 acceptance report for generation, rest, streaming, memory and exact reload.

01Turn milestone words into fixtures

The M4 gate promises long seeded exploration, rest and memory tests, and exact save/load. Give each promise a named fixture with seed, generator version, starting camera, input sequence and measured duration. Use the same fixtures after future changes so “still works” means comparable evidence.

For the rest fixture, generate 1000 chunks across the v1 biomes, run 600 ticks and count moved cells under the documented tolerance. Keep temperature/moisture initialization compatible with the generator so normal startup does not create avoidable motion.

02Separate logical clocks from wall-clock measurements

Simulation fixtures should inject ticks, not sleep for ten seconds hoping the scheduler happened to run the right count. Performance tests measure real elapsed time in optimized builds; behavior tests control world state and update count. They answer different questions.

Record hardware model, build profile, active-cell count, display size and thread count with timings. A faster developer machine cannot certify the floor machine. Include combined frame work, not only mean cell-update duration.

03Use exact comparisons only where promised

A save round-trip compares the agreed complete state, including the chosen particle/group and scheduler policy. A compressed byte stream can differ while decoded world state is equal; comparing only file bytes is not the semantic test. Conversely, comparing only visible colours can miss temperatures and cooldowns that affect the next tick.

For long-pan memory, track high-water marks and queue bytes in addition to ending memory. A run may finish under the cap after a large transient spike. Capture the largest observed resident/pending state and foreground stall, with a reason for each exception.

04Write a report another person can reproduce

Use a small table with fixture, command, expected result, observed result, hardware and pass/fail. Attach logs and one short clip showing a cross-border edit followed by save/load. State unresolved visual approvals separately; M4 is not M5 art sign-off.

Read what each part does

  1. Test filters select real test names; no tests is not a passing fixture. Check the runner reports the expected nonzero count.
  2. Use --release for the measured stress run, while keeping behavior tests deterministic and headless.
  3. The manual part records actual observations. Comments in a command block are not proof that those observations occurred.

Expected result

A report with actual fixture counts, rest tolerance, exact state comparison, memory high-water marks and unresolved failures—not just successful command exit codes.

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Catch a false green run

cargo test rest_generated_world reports zero tests. Did the rest gate pass?

Need a hint?

Read the test count as well as the exit code.

Worked solution

No. The filter did not execute the intended fixture. Fix the name/module path and require a nonzero expected count before accepting the result.

How to verify your result

The report records the exact executed fixture count.

02

Choose the right hash

A screenshot matches after load, but the water temperature differs.

Need a hint?

Future state depends on more than current colour.

Worked solution

The semantic world hash must include temperature and all agreed future-affecting fields. The round-trip fails even though the screenshot looks right.

How to verify your result

The comparison reports the differing field or complete-state mismatch.

03

Report a spike honestly

The cache ends at 60 MB but peaks at 400 MB during panning.

Need a hint?

A final sample is not a high-water measurement.

Worked solution

Record the 400 MB peak and queue contribution. The bounded-memory gate fails or requires an explicitly approved higher bound; the final value cannot hide the spike.

How to verify your result

The report includes the maximum observed total, not just the ending cache.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Rest gate passes on one seed only

What is happening: The fixture does not cover the required generated sample.

Try this: Record and execute the full chunk/biome set.

Reload looks right but later diverges

What is happening: The state comparison omits future-affecting fields.

Try this: Hash and compare the complete agreed inventory and subsequent fixed-input steps.

Performance report cannot be reproduced

What is happening: Seed, hardware, profile or input path is missing.

Try this: Store the full fixture identity and commands with the observed output.

Explain it without the example

Why measure actual compressed save size rather than promise a few kilobytes per chunk?

Reasoning to compare

Temperature, moisture and edits change entropy. Compression effectiveness is a measurement of real scenes, not a fixed property of chunk dimensions.

Self-check only: test a prediction or ask your tutor if anything still feels arbitrary.

Finish with evidence

Rest movement stays within the specified tolerance, changed state reloads exactly, and resident memory stays bounded.
