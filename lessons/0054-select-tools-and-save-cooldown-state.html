Select tools and save cooldown state

Unavailable tools give feedback and do not fire. Fuse and cooldown behavior is documented against the two clocks.

Previously: Strike the actual world surface. Keep that working result available before starting this lesson.

Why we need this now

Painting Wood places material; selecting Lightning requests an event. The input bar needs to express that difference, while tests should be able to request the same event without a mouse. A command enum and explicit clock ownership make the tools small and reproducible.

Your result: Unavailable tools give feedback and do not fire. Fuse and cooldown behavior is documented against the two clocks.

01Convert input into commands

Define commands such as Paint, Erase, Ignite, PlaceBomb, AddRain and Strike. The input layer maps cursor coordinates and selected page to one command; the simulation validates and executes it. UI hit testing happens first so clicking a tool swatch does not also paint behind the bar. Tests construct commands directly, which makes invalid targets and repeated presses easy to reproduce. Record command application tick and coordinates for later replay.

02Choose a clock for every duration

The rain/lightning tool cooldown is one in-game day, so it reads world_tick. A three-second bomb fuse should name whether it measures physics ticks or calendar time; the course uses a physics-tick fuse as a proposed readable rule unless the milestone approves otherwise. At high fast-forward those clocks diverge. A duration stored as an unlabeled integer “60” is not enough: name the field next_ready_world_tick or fuse_steps_remaining so its units are visible in code.

03Store a deadline instead of decrementing every frame

For cooldowns, compute ready_at = current_world_tick + duration once, then compare current time against it. This works across frame rate changes and does not require visiting every unavailable tool each render frame. Use checked or saturating arithmetic under the application’s long-run policy so an extreme counter does not wrap into immediate availability. Saving the deadline preserves cooldowns after load. A fuse tied to executed ticks remains separate and pauses with the simulation.

04Give rejected actions visible feedback

An unavailable tool should not silently fire, reset its deadline or consume a charge. Return a small result such as Applied, CoolingDown(remaining) or InvalidTarget. The UI can show that result without owning the rule. Test exactly at ready_at as well as one tick before it. Repeated held input should obey the intended press/hold policy and not enqueue sixty charges per second merely because rendering repeats.

fn try_use(now: u64, ready_at: &mut u64, cooldown: u64) -> bool {
    if now < *ready_at { return false; }
    *ready_at = now.saturating_add(cooldown);
    true
}
#[test]
fn cooldown_uses_a_world_tick_deadline() {
    let mut ready=0;
    assert!(try_use(10,&mut ready,24_000));
    assert_eq!(ready,24_010);
    assert!(!try_use(24_009,&mut ready,24_000));
    assert!(try_use(24_010,&mut ready,24_000));
}

01

Pause the game

Should a world-tick cooldown expire while the simulation is paused?

Need a hint?

The paused clock does not advance.

Worked solution

No. If world_tick remains fixed, the deadline comparison remains fixed too. A wall-clock cooldown would be a different explicitly chosen rule.

How to verify your result

Paused time produces no cooldown progress.

02

Store a bomb fuse

At 20 physics TPS, how many executed steps represent a three-second fuse?

Need a hint?

Use the fuse’s chosen clock.

Worked solution

Sixty executed steps at 1x. Name it fuse_steps_remaining and decrement once per executed tick, not once per frame or by an unrelated seasonal multiplier.

How to verify your result

A 60-step fixture detonates once at the chosen boundary.

03

Reject an invalid target

Should a failed rain-tool request on an invalid target start its cooldown?

Need a hint?

Separate validation from applying the command.

Worked solution

Under a no-consumption-on-failure policy, validate first and update ready_at only after a valid event is accepted. Test the deadline remains unchanged after rejection.

How to verify your result

Invalid actions do not silently consume availability.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Cooldown changes with monitor refresh

What is happening: It decrements in the draw loop.

Try this: Compare world_tick to a stored deadline.

A held bomb key spawns hundreds of charges

What is happening: Press/hold handling is unspecified.

Try this: Use edge-triggered input or an explicit repeat period.

Loading restores tools as immediately ready

What is happening: Tool deadlines were not saved.

Try this: Include cooldown state in the snapshot inventory.

Explain it without the example

Why must a bomb fuse and a seasonal cooldown name their clock?

Reasoning to compare

Physics and calendar ticks can diverge in fast-forward. An unnamed duration becomes ambiguous and may change behavior across machines.
