Handle failures as normal outcomes

Report useful load/config failures without panicking or destroying the live world, and keep the original error available for diagnosis.

Previously: Integrate optional events and close biome expansion. Keep that working result available before starting this lesson.

M7 starts here. Review this milestone’s implementation plan against the current spec. The lessons teach the work; they do not silently approve new game behavior.

Why we need this now

A user can run out of disk space, choose a corrupt file or launch without one sound asset. These are ordinary operating conditions. Recoverable errors need an ownership and recovery path just as material movement does.

Your result: Report useful load/config failures without panicking or destroying the live world, and keep the original error available for diagnosis.

01Place errors at boundaries, not inside every cell

The simulation should not ask the filesystem whether every cell update succeeded. External boundaries—configuration, asset loading, saves, window initialization—are where fallible operations belong. Return a Result containing either the requested value or enough information to explain why it was unavailable. The caller decides whether to show a message, try a backup, use a safe default or return to a menu.

Keep a valid world in memory while loading a replacement. Decode into separate validated storage and install it only after the whole load succeeds. Clearing the current world first and then discovering a corrupt region turns a recoverable input error into avoidable data loss.

02Keep operation, path and underlying cause

An error saying file failed tells the player little. A useful message names what was attempted and which path, then includes the operating-system or decoding cause. A typed error can retain std::io::Error as a source instead of flattening everything into an opaque string. That helps logs distinguish not-found from permission failures without parsing English messages.

For malformed content, report the expected domain and the observed invalid field. Avoid dumping entire private file contents into the interface or logs. The example parses one numeric budget: it proves the mechanism without pretending that a full settings format has been introduced.

03Use question-mark propagation intentionally

Inside a Result-returning helper, ? returns early on Err. It does not show a popup, choose a backup or retry. map_err converts the low-level error into the application context at the point where that context is known. At the top, match determines the recovery behavior.

Do not replace every unwrap mechanically with a silent default. Falling back from a missing optional audio clip may be fine; falling back from a corrupt save to an empty world without telling the player is not. Classify errors by the consequence of recovery. Impossible internal states may still indicate bugs, but external files must be validated before becoming trusted state.

04Make failure fixtures ordinary tests

Use a missing path, truncated header, invalid material ID, oversized length and unwritable destination as separate fixtures. Each should assert both the reported error and unchanged prior state. Test failures after one region write as well as before the first; the transactional save policy exists for those partial-operation cases.

For a YouTube episode, show a deliberate corrupt file, the clear recovery message, and the still-running world. Then open the error type and trace the path from the original operation to the caller. This makes Result a practical tool for protecting the player’s work, rather than an abstract enum lesson repeated late in the course.

use std::{fmt, fs, io, path::{Path, PathBuf}};
#[derive(Debug)]
enum ConfigError {
    Read { path: PathBuf, source: io::Error },
    Invalid { path: PathBuf, message: String },
}
impl fmt::Display for ConfigError {
    fn fmt(&self,f:&mut fmt::Formatter<'_>)->fmt::Result {
        match self {
            Self::Read{path,source}=>write!(f,"read {}: {}",path.display(),source),
            Self::Invalid{path,message}=>write!(f,"decode {}: {}",path.display(),message),
        }
    }
}
impl std::error::Error for ConfigError {
    fn source(&self)->Option<&(dyn std::error::Error+'static)> {
        match self { Self::Read{source,..}=>Some(source), _=>None }
    }
}
fn parse_budget(text:&str,path:&Path)->Result<u32,ConfigError> {
    text.trim().parse::<u32>().ok().filter(|n|*n>0)
        .ok_or_else(||ConfigError::Invalid{path:path.to_owned(),
            message:"expected a positive active-cell budget".to_owned()})
}
fn load_budget(path:&Path)->Result<u32,ConfigError> {
    let text=fs::read_to_string(path)
        .map_err(|source|ConfigError::Read{path:path.to_owned(),source})?;
    parse_budget(&text,path)
}
fn main() {
    let path=Path::new("settings.txt");
    assert_eq!(parse_budget("74624",path).unwrap(),74_624);
    let error=parse_budget("zero",path).unwrap_err();
    println!("{error}");
    let _loader:fn(&Path)->Result<u32,ConfigError>=load_budget;
}

Read what each part does

  1. The main experiment is deterministic and does not write or require a settings file.
  2. Display is the user-facing description; Error::source retains an underlying I/O cause when present.
  3. load_budget is a focused example for a small trusted-size test file; production must also bound config input sizes before allocation.

Expected result

decode settings.txt: expected a positive active-cell budget

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Reject zero

Pass the text0 to parse_budget.

Need a hint?

Parsing a u32 is not the complete domain check.

Worked solution

The parse succeeds numerically but filter rejects zero, returning Invalid. Assert both zero and negative input reject while74624 succeeds.

How to verify your result

No zero active budget reaches the renderer.

02

Preserve the current world

Try loading a malformed snapshot into a running fixture.

Need a hint?

Install new state only after successful validation.

Worked solution

Decode into a temporary value; match the Result. On Err keep the original World and expose recovery choices. Compare the original world hash before/after the failed load.

How to verify your result

The hash stays unchanged and the message names the failure.

03

Classify a missing sound

Should a missing optional rain clip use the same recovery as a missing world-region file?

Need a hint?

The consequences differ.

Worked solution

No. Optional audio can disable that source with feedback. Missing required world data invalidates the snapshot and should select a complete backup or stop loading; it must not silently paint air into missing chunks.

How to verify your result

Each boundary test asserts its documented recovery policy.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

The message loses the filename

What is happening: The low-level error was propagated without boundary context.

Try this: Wrap it where the path and operation are known.

Bad settings become mysterious defaults

What is happening: The code turns every error into fallback values.

Try this: Separate missing optional configuration from malformed required data and report the choice.

Failed loading wipes edits

What is happening: The existing world was replaced before decode completed.

Try this: Validate a separate candidate state, then commit the replacement.

Explain it without the example

Why is unwrap inappropriate for an ordinary missing save file?

Reasoning to compare

A missing file is a recoverable external condition. Panicking discards the normal error path and can lose unsaved play state.
