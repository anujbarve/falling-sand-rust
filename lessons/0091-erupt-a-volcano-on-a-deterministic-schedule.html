Erupt a volcano on a deterministic schedule

Schedule a reproducible eruption without replaying a season of missed activity when an off-screen volcano returns.

Previously: Add desert climate and moving sand. Keep that working result available before starting this lesson.

Why we need this now

A global calendar advances while off-screen material is frozen. Eruption timing must say what that combination means. Otherwise returning to a quiet volcano can release an accidental backlog of lava and particles.

Your result: Schedule a reproducible eruption without replaying a season of missed activity when an off-screen volcano returns.

01Define an event from identity and calendar time

Give each generated volcano a stable feature ID derived from its world-coordinate placement. Combine that ID with the world seed to choose an offset inside a fixed seasonal period. The next eruption is then a function of seed, feature ID and calendar time. Loading the right-hand chunk first must not choose a different eruption than loading the left-hand chunk first.

For the teaching schedule, one period is 72,000 world ticks. Each volcano receives one deterministic offset inside the period. This spreads events without maintaining an off-screen timer for every feature. The chosen mixing function only needs reproducibility for this purpose; do not present it as cryptographic randomness or as a replacement for the approved terrain hash.

02Resolve the off-screen policy explicitly

The spec freezes off-screen material. A natural extension is to skip eruption events whose active time was never simulated, then schedule the next future event when the feature becomes active. This is a proposed policy to confirm at the milestone, not a hidden interpretation. An alternative may produce a visibly active volcano on entry, but it still needs a bounded rule rather than replaying hundreds of historical events.

Keep event selection separate from material output. Finding that an event is due does not immediately allocate particles. The eruption command requests bounded lava/ash emission through the existing event and particle budgets. If capacity is full, the policy must say whether excess output is skipped, delayed within a strict bound, or represented another way.

03Handle large calendar steps without repeated blasts

At high fast-forward, one executed tick can cross an eruption timestamp. Detect crossing of the scheduled timestamp rather than exact equality with world_tick. Consume the event once, then compute the first future event after the new calendar time. If one multiplier spans multiple periods, a maximum-one-event-per-executed-tick policy bounds work but skips historical events; document that approximation.

Use the production event ID to prevent a saved/reloaded volcano from consuming the same event twice. This may be an explicit next-event/cycle record or a deterministic schedule combined with a saved consumed-cycle index. Do not rely on a UI message disappearing to mark the event handled.

04Build the cone and prove its output

Generate the cone as normal supported terrain, with a documented vent position and a lava source policy. Decide whether eruption lava is an intentional material source or drawn from a reservoir; otherwise conservation tests will disagree with the visual goal. Ash still has its material kind and wind behavior, even when emitted dramatically.

Run a tiny eruption fixture at the particle cap before a large volcano. Count emitted, retained, destroyed and deferred material under the chosen policy. Then test the off-screen interval: advance the calendar, reactivate the same feature and assert no unbounded catch-up queue.

fn next_eruption(seed: u64, feature: u64, now: u64) -> Option<u64> {
    const PERIOD: u64 = 72_000;
    let offset = (seed ^ feature.wrapping_mul(0x9E3779B97F4A7C15)) % PERIOD;
    let start = (now / PERIOD).checked_mul(PERIOD)?;
    let candidate = start.checked_add(offset)?;
    if candidate > now { Some(candidate) }
    else { candidate.checked_add(PERIOD) }
}
fn main() {
    let seed = 17;
    let id = 42;
    let first = next_eruption(seed,id,0).unwrap();
    let after_absence = next_eruption(seed,id,72_000 * 10).unwrap();
    assert!(after_absence > 72_000 * 10);
    assert_eq!(next_eruption(seed,id,0),Some(first));
    assert_eq!(next_eruption(seed,id,first),first.checked_add(72_000));
    println!("one stable schedule; no historical eruption queue");
}

Read what each part does

  1. checked arithmetic makes extreme calendar overflow a handled absence rather than an unchecked wrap.
  2. The function selects a strictly future timestamp; crossing and consumed-event state belong to the caller.
  3. The seed/feature mixer is a small deterministic teaching function. Keep the production hash and event identity versioned with the world policy.

Expected result

one stable schedule; no historical eruption queue

01

Return after ten seasons

Evaluate the feature at ten periods after the start. How many old eruptions are queued?

Need a hint?

The function computes a future event, not an event history.

Worked solution

Zero old events are queued under the proposed skip policy. Only the next future timestamp is selected. Assert it exceeds now and is at most one period away.

How to verify your result

Reactivation work does not grow with absence length.

02

Cross instead of equal

Advance from one tick before an eruption to three ticks after it.

Need a hint?

Calendar multipliers may skip exact timestamps.

Worked solution

Dispatch once when before < due and due <= now, then replace due with next_eruption(seed,id,now). Calling again at the same now must not repeat the consumed event.

How to verify your result

A crossing test sees exactly one event.

03

Account for new lava

Choose reservoir or explicit source behavior and write a count assertion.

Need a hint?

An eruption may intentionally introduce matter, but only explicitly.

Worked solution

A reservoir policy subtracts emitted cells from storage. A source policy records emitted mass as a source term. In either case total change equals the documented source minus destruction; it is not an unexplained failed conservation test.

How to verify your result

Every emitted cell belongs to one accounted outcome.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Volcano fires every frame at one date

What is happening: The due event was not consumed.

Try this: Advance the scheduled event or save its consumed cycle.

Returning causes hundreds of bursts

What is happening: Missed off-screen events were replayed without a bound.

Try this: Use the approved skip/coalescing policy at activation.

Same seed produces different timing

What is happening: Event offset consumes a mutable exploration RNG.

Try this: Derive it from stable feature identity and calendar period.

Explain it without the example

Why define off-screen eruption behavior before implementing its timer?

Reasoning to compare

World time advances while material is frozen. Without a policy, returning could silently catch up many events or contradict the frozen-world promise.
