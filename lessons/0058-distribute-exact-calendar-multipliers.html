Distribute exact calendar multipliers

For every completed allocation, spent plus retained world ticks equals the accumulated budget. No early stop loses unspent calendar ticks.

Why we need this now

Suppose the calendar owes ten ticks but only three physics updates fit. Assigning multiplier three to each loses one; assigning four to all creates two. Quotient and remainder give an exact integer distribution. Early stops then test whether the unspent time stays owned somewhere.

Your result: For every completed allocation, spent plus retained world ticks equals the accumulated budget. No early stop loses unspent calendar ticks.

01Derive the allocation from a sum

The invariant is simple: assigned calendar increments plus unspent calendar budget equals the initial whole budget. For W=10 and k=3, divide ten into three nearly equal integer pieces. The current spec repeatedly takes the ceiling of remaining W divided by remaining k, giving 4,3,3. This is not a new kind of fractional simulation tick; each completed physics update receives an integer multiplier. Fractional accepted calendar time stays in a separate fixed-point remainder.

02Avoid overflow in ceiling division

A common formula (W+k-1)/k can overflow for very large W even when the final quotient fits. Compute W/k plus one when W%k is nonzero, or use a suitable integer div_ceil API supported by the pinned toolchain. Reject k=0 before dividing. In production W is selected so each planned update receives at least one; the helper below checks W>=k rather than silently inventing negative debt. All arithmetic choices need to match the actual accumulator representation.

03Spend only completed work

If the first planned update gets four calendar ticks and then exceeds the frame budget, only those four are spent. Six remain in world_tick_accum. Do not pre-subtract the entire ten when planning three updates, because the remaining two may never run. A small allocation function can return a schedule for testing, while the live loop must commit each multiplier only after its update completes. Save/load or speed-reset policy must say what happens to unspent remainder.

04Keep exactness claims scoped

The scheduler clamps long elapsed intervals and resets debt on pause/speed changes by design. Therefore exact conservation describes the accepted budget between those policy boundaries, not an unconditional promise to reproduce all external wall time. At high multipliers, calendar events and slow-process approximation can still differ from uncapped physics; exact sums do not make trajectories equivalent. Prove the arithmetic invariant separately from the visual/behavior tests at different speeds.

fn ceil_div(a:u64,b:u64)->u64 { a/b + u64::from(a%b != 0) }
fn allocation(mut world:u64, mut ticks:u64)->Vec<u64> {
    assert!(ticks>0 && world>=ticks);
    let mut result=Vec::new();
    while ticks>0 {
        let m=ceil_div(world,ticks);
        result.push(m); world-=m; ticks-=1;
    }
    result
}
#[test]
fn integer_allocations_preserve_the_sum() {
    assert_eq!(allocation(10,3),vec![4,3,3]);
    assert_eq!(allocation(3,3),vec![1,1,1]);
    let plan=allocation(10,3);
    let spent=plan[0];
    assert_eq!(10-spent,6);
}

01

Try another remainder

Allocate 17 whole calendar units over five updates.

Need a hint?

Recompute ceiling on the remaining budget each time.

Worked solution

The sequence is 4,4,3,3,3. Its sum is 17 and all values are positive. Verify by tracing remaining W and k after each assignment.

How to verify your result

The plan sums exactly to 17.

02

Interrupt the plan

For [4,3,3], stop after two updates. What debt remains?

Need a hint?

Spend only the first two values.

Worked solution

Seven has been spent and three remains. Keep that three with the world accumulator, not the discarded physics backlog.

How to verify your result

Spent plus retained remains ten.

03

Protect a zero frame

No physics tick is due this frame. Should allocation run with k=0?

Need a hint?

Division requires a nonzero divisor.

Worked solution

No. Keep accumulated calendar fraction/debt until an update can consume it under the scheduler policy. The allocation helper is called only when a positive number of updates is actually planned.

How to verify your result

The zero-due path cannot divide by zero.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Calendar runs slightly too fast

What is happening: Every update uses the same rounded-up multiplier.

Try this: Distribute the remainder and test total sum.

Calendar time vanishes after a slow tick

What is happening: The full plan was deducted before completion.

Try this: Commit each multiplier only after completed work.

Accumulator underflows

What is happening: W and planned k violate the positive-multiplier invariant.

Try this: Validate shared scheduler inputs and keep one authoritative debt calculation.
