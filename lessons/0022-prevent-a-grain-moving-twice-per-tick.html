Prevent a grain moving twice per tick

Guarantee a grain receives at most one movement update per simulation tick.

Previously: Iterate and inspect a grid without moving it. Keep that working result available before starting this lesson.

Why we need this now

An in-place scan changes the collection it is still traversing. A moved grain may land in a slot the scan has not visited yet and move again immediately. The bug is about update order, so we will make that order visible in a tiny column before adding chunks.

Your result: Guarantee a grain receives at most one movement update per simulation tick.

01Construct the counterexample

Place one grain at the top of a six-cell column and scan from top to bottom. At row0 it moves to1; the scan next reaches row1 and sees the same grain again. It may fall through the entire column in one tick even though the rule promised one step. Counting grains does not catch this because mass is conserved while timing is wrong.

Trace the occupied row after every scan position. The problem is not gravity strength or elapsed-time scheduling; it is that a single material instance is being selected repeatedly during one update. This distinction prevents tuning a speed constant to conceal an update-order bug.

02Reverse the falling scan

For downward movement, scan bottom to top. A grain moves into a slot that was already visited during this pass, so the simple one-row example cannot be encountered again. In a flat row-major buffer, visit higher row indices first.

This is helpful but not the final guarantee. Multiple phases, horizontal movement and chunk boundaries can still allow a later traversal to see the moved cell. The game therefore also needs a moved-this-tick marker with a precisely defined reset policy. The marker belongs to material state and must travel with the grain during a swap.

03Define marker ownership and reset

For the focused experiment use a Cell with occupied and moved fields. Clear moved at the start of the tick, then mark the destination after a transfer. Any later attempt skips a moved cell. In production, an update parity bit can avoid clearing every field, but parity must be handled carefully when frozen cells return and must not accidentally mark newborn or reactivated cells forever.

The code below demonstrates a single pass explicitly. Do not optimize marker storage before proving the once-per-tick property. A tiny test can record the grain’s displacement and catch repeated moves even when the final image still looks plausible.

04Extend the assertion across boundaries

When chunks are introduced, place the source on the last row or column of a chunk and run the same movement limit assertion across the neighbour boundary. Retain the marker across all phases in a tick, not reset independently when each chunk starts.

The acceptance promise is about one logical update, not one function call or one storage object. A bottom-to-top scan is a strategy; a traveled-distance/marker test checks the actual promise. Keep both location and conservation assertions because they protect different bugs.

Walk through the working example

Download this worked example ↧

#[derive(Clone,Copy,Default)]
struct Cell { sand: bool, moved: bool }
fn tick(column:&mut [Cell]) {
    for cell in column.iter_mut() { cell.moved=false; }
    for row in (0..column.len().saturating_sub(1)).rev() {
        if column[row].sand && !column[row].moved && !column[row+1].sand {
            column.swap(row,row+1);
            column[row+1].moved=true;
        }
    }
}
fn main() {
    let mut column=[Cell::default();6];
    column[0].sand=true;
    tick(&mut column);
    assert!(column[1].sand);
    assert_eq!(column.iter().filter(|c|c.sand).count(),1);
    println!("one tick, one row");
}

Read what each part does

  1. The one-row experiment isolates traversal from the production three-row rule.
  2. A material-count assertion alone would miss the repeated-update bug.
  3. saturating_sub handles an empty or single-slot test column without underflow.

02

Check marker transport

Explain why a moved flag attached only to the old source index is wrong.

Need a hint?

After swapping, the grain is at the destination.

Worked solution

A marker describes whether that material instance was updated, not whether an empty location was visited. Move/assign the marker with the destination material so later phases can see it.

How to verify your result

03

Prepare a boundary fixture

Place a source immediately above a planned chunk boundary.

Need a hint?

The later chunk pass must see the existing marker.

Worked solution

Run both chunk phases under one logical tick and assert no extra movement occurs after crossing. Do not reset markers separately for each chunk.

How to verify your result

A cross-boundary source obeys the same per-tick distance contract.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

A grain falls many rows in one tick

What is happening: The in-place scan revisits its destination.

Try this: Use appropriate scan order and a marker that survives every pass in the tick.

Crossing chunks increases speed

What is happening: Each chunk resets or ignores the moved marker.

Try this: Define the marker over the whole logical tick.

Frozen cells never move after return

What is happening: Parity/reset semantics do not account for reactivation.

Try this: Add a reactivation fixture and choose a marker policy that cannot confuse stale state with a current update.

Explain it without the example

Why is bottom-to-top order alone not the final cross-chunk solution?

Reasoning to compare

It helps within one scan, but a later chunk or phase can encounter a moved cell. The update marker protects the once-per-tick rule across those boundaries.
