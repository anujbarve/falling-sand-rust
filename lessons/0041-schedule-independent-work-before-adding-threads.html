Schedule independent work before adding threads

Single-threaded and threaded paths share rules. No unsafe shared mutation is introduced to bypass an unproven partition.

Previously: Borrow disjoint slices before parallel work. Keep that working result available before starting this lesson.

Why we need this now

The engine already has a sequential rule set. We want to use more CPU cores only if the measured workload needs them. A correct scheduling design starts by identifying jobs that cannot interfere; creating threads first and hoping the race disappears is not a performance plan.

Your result: Single-threaded and threaded paths share rules. No unsafe shared mutation is introduced to bypass an unproven partition.

01Separate schedule from rule semantics

A chunk phase determines which jobs may run together. The same movement and heat helpers should work under a sequential dispatcher and a parallel dispatcher. This gives a reference implementation: if adding threads changes the world hash under identical inputs, dispatch or access is wrong. Avoid copying physics code into two independent implementations just to use threads, because every later fix would need to be kept synchronized.

02Calculate the complete footprint

The proposed four-phase schedule groups chunks by x and y parity. Same-phase chunks are separated, but a job can read and write into a neighbouring chunk. Count the maximum displacement plus every destination/neighbour read. The spec limits moves to 31 cells and adds a one-cell check. That still needs a proof for each actual helper and all metadata. State the intervals and verify their intersection is empty for simultaneous jobs; do not infer safety from chunk centres alone.

03Use a safe ownership strategy

The worked example uses disjoint slices so Rust can enforce exclusive access. Real cross-chunk updates may need a snapshot-read/owned-output strategy, staged boundary commands or another safe partition. A snapshot lets workers read the same old state while they own separate output ranges; the serial merge resolves boundary commands in a fixed order. These alternatives trade memory or merge cost for a simpler proof. Choose from measurements and explicit semantics, not from the desire to silence compiler errors.

04Budget serial work as well

Falling groups, particles and support fills run serially after chunk phases because they can span many chunks. Threads do not accelerate those operations automatically. Record both phase timings and serial tail time in the profiler. A fast parallel cell pass can still produce a slow frame if an explosion triggers hundreds of support searches. Keep a sequential fallback and compare full tick duration, not just the threaded region that looks impressive in isolation.

fn increment(values: &mut [u32]) {
    for value in values { *value += 1; }
}
#[test]
fn disjoint_jobs_match_sequential_reference() {
    let mut expected = vec![0_u32; 128];
    increment(&mut expected);
    let mut actual = vec![0_u32; 128];
    let (left, right) = actual.split_at_mut(64);
    std::thread::scope(|scope| {
        scope.spawn(|| increment(left));
        scope.spawn(|| increment(right));
    });
    assert_eq!(actual, expected);
}

01

Include a neighbour read

A job moves 31 cells and inspects one additional destination neighbour. What reach must the proof allow?

Need a hint?

Movement distance is not the complete read footprint.

Worked solution

Allow 32 cells from the relevant boundary for that rule. Then calculate the actual intervals for simultaneous jobs; the number alone is not a proof for unrelated metadata writes.

How to verify your result

The read bound includes the destination check.

02

Keep the serial reference

Run the same lab using four smaller disjoint jobs.

Need a hint?

chunks_mut can create nonoverlapping slices.

Worked solution

Iterate actual.chunks_mut(32) inside a thread scope and spawn one increment job per slice. Compare the entire resulting vector with the sequential buffer.

How to verify your result

All buffer elements match, not only a checksum.

03

Detect tail work

Suppose phases take 4 ms but group/support work takes 14 ms. Did threading meet a 12 ms simulation budget?

Need a hint?

Add the phases that happen in the same frame.

Worked solution

No. The full simulation work is at least 18 ms. Profile and bound support/event work or revise the accepted workload rather than reporting only the 4 ms phase time.

How to verify your result

The report includes complete tick and frame duration.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Parallel output changes across runs

What is happening: Concurrent jobs share writes or merge order is unstable.

Try this: Return to the sequential reference and audit every write footprint.

Scoped closure fails Send bounds

What is happening: Captured types are not safe for cross-thread transfer/access.

Try this: Keep graphics resources on the render thread and send plain simulation work.

Two threads are slower

What is happening: Dispatch and synchronization exceed the useful work.

Try this: Keep the sequential path and enable parallel work only when measured beneficial.

Reasoning to compare
