Stop a falling grain at a floor

Land one falling cell exactly above a floor without crossing it, even on a larger final step.

Previously: Run movement on a 20 TPS clock. Keep that working result available before starting this lesson.

Why we need this now

We have a timed update and a visible cell, but movement must respect geometry. A flat floor is the smallest collision fixture that reveals why checking the starting position is not enough: a three-row step can begin legally and end inside the obstacle.

Your result: Land one falling cell exactly above a floor without crossing it, even on a larger final step.

01Derive the legal destination

If the floor begins at row 160 and the grain occupies one cell row, its top row may reach 159. Suppose it begins at 158 and proposes moving three rows: the unconstrained destination is 161, which overlaps the floor. The legal result is the smaller of the proposed destination and the last free row.

That gives (cell.row + 3).min(floor_row - 1). The condition before it keeps already-resting grains from moving again. This rule is intentionally constant-speed downward motion, matching the current game-design baseline; it is not an acceleration simulation. A physically named word such as gravity does not require pretending this simple rule is Newtonian integration.

02Make one function own the update rule

Put the mutation in tick_cell(&mut Cell, floor_row). Rendering receives only &Cell; tick_cell receives mutable access because it changes row. main keeps ownership. This connects the borrowing lesson to a concrete simulation boundary rather than introducing a new architecture vocabulary.

The same floor_row should determine both collision and the drawn floor position. If the visual floor uses an unrelated hardcoded y value, the grain may appear to hover or sink despite correct row arithmetic. One source of truth makes the relation between simulation and image inspectable.

03Test boundaries before looking at motion

Try rows 5,158 and159 with floor160. One tick should produce 8,159 and159 respectively. Those cases cover ordinary motion, a shortened final move and already-resting state. An invalid start such as row161 needs a separate rejection or recovery policy; do not silently call it a successful collision test.

The complete example below runs these cases through assertions. Then integrate it into the timed graphical program: draw the floor at floor_row times4, draw the grain from its current row, and use R to reset row5 and the teaching accumulator. A row5 to row159 fall needs 52 ticks because 51 full three-row moves reach158 and the final tick clamps to159.

04Know what this collision rule does not cover

Clamping against one horizontal floor works because we know the nearest relevant obstacle analytically. It does not prove safe movement through a general material world. If a stone occupies row157 and a grain starts at155, a three-row move must inspect the traversed path rather than only the floor or endpoint. The grid lesson will introduce those occupancy checks.

For the episode, show the failure by first allowing an unclamped step and placing the grain two rows above the floor. Then derive the fix from the last legal row. The visual is useful because it exposes the exact off-by-one boundary; the code should follow the picture, not appear as an unexplained min call.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

struct Cell { row: i32 }
fn tick_cell(cell: &mut Cell, floor_row: i32) {
    if cell.row < floor_row - 1 {
        cell.row = (cell.row + 3).min(floor_row - 1);
    }
}
fn main() {
    for (start, expected) in [(5, 8), (158, 159), (159, 159)] {
        let mut cell = Cell { row: start };
        tick_cell(&mut cell, 160);
        assert_eq!(cell.row, expected);
        println!("{start} -> {}", cell.row);
    }
}

  2. The helper mutates a borrowed cell without taking ownership.
  3. Assertions cover ordinary, shortened and resting updates.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

The grain rests one row too low

What is happening: The top-row footprint or floor offset is wrong.

Try this: Use floor_row-1 as the last legal top row for a one-row grain.

The grain looks buried despite passing assertions

What is happening: Drawn floor and collision floor use different values or units.

Try this: Derive drawing y from the same floor_row times cell size.

The grain crosses a thin obstacle

What is happening: Only the final destination or flat floor was tested.

Try this: Inspect the full movement path once arbitrary grid obstacles exist.

Explain it without the example

Why is checking only whether the grain starts above the floor insufficient?

Reasoning to compare

A three-row move can overshoot. The destination must be constrained too; arbitrary obstacles will later require inspecting the entire path.
