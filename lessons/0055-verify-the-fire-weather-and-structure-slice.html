Why we need this now

Individual fire, rain and support tests are necessary, but the hillside scene is where their ordering becomes visible. A wet beam might burn if rain arrives after ignition; a roof may vanish from a stale support cache. This milestone assembles a small story while retaining enough instrumentation to diagnose it.

01Build one repeatable scene, not a random showcase

Use a fixed hand-built hillside with a small house, dry grass, wet wood and a water basin. The M4 generator does not exist yet, so do not make this gate depend on generated lakes or biomes. Store fixture construction in code with a seed and initial climate context. That shared fixture makes an observed problem easier to reproduce outside the video.

02Assert the sequence of causes and effects

First dry grass catches and spreads under the chosen heat rule. Next scripted rain hits exposed fuel and stops the fire within two seconds. Wet wood resists ignition, the roof shelters its interior and a deliberately removed support makes a small floating roof fall. These are separate checks with first-observed timestamps. Do not treat a final screenshot of ash as evidence that all intermediate deadlines were met. Log enough state to distinguish ignition failure from material that already burned away.

03Include the moving observer

Pan so a fire approaches the active margin, then return. The frozen policy stops off-region updates, but the visible frame should not contain an obviously stopped front under the accepted margin behavior. This manual check cannot prove unrestricted camera independence; it tests a scoped visual promise. Record camera positions and active rectangles so a regression can reproduce the same event. If the margin is insufficient, revise its measured cost and visibility tradeoff openly.

04Measure total event bursts

An explosion may create particles, remove support, change heightmap entries and emit sound/visual events in one tick. Measure the complete synchronous tick and frame, including serial tails. A bounded 4096-cell fill repeated 100 times is still expensive. Record average and worst observed durations, event counts and resident memory with hardware/resolution. If the floor machine fails, reduce or redesign work before adding seasons, rather than relying on a later optimization miracle.

#[derive(Default)]
struct Evidence { fire_spread: bool, rain_stopped: bool,
    wet_wood_resisted: bool, roof_fell: bool, tick_ms: f32 }
fn gate(e: &Evidence) -> bool {
    e.fire_spread && e.rain_stopped && e.wet_wood_resisted &&
    e.roof_fell && e.tick_ms <= 10.0
}
#[test]
fn every_required_result_matters() {
    let mut e=Evidence { fire_spread:true, rain_stopped:true,
        wet_wood_resisted:true, roof_fell:false, tick_ms:8.0 };
    assert!(!gate(&e));
    e.roof_fell=true;
    assert!(gate(&e));
}

02

Isolate a failed wet beam

Rain works in the open but wet wood burns under a roof. What should you inspect first?

Need a hint?

Shelter changes rain access, not all moisture history.

Worked solution

Inspect initial wetness, drying rate, heat-drying order and ignition threshold. A sheltered beam may never receive new rain; the wet-control fixture must initialize it deliberately.

How to verify your result

A minimal fixture identifies the failed prerequisite.

03

Report a spike

A blast tick takes 24 ms while ordinary ticks take 5 ms. What goes in the report?

Need a hint?

The worst case matters to frame smoothness.

Worked solution

Report both. Profile support searches, particle reinsertion and event application for the spike. Do not average it away in a claim of smooth 60 FPS.

How to verify your result

The report retains worst observed tick and frame costs.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Manual scene cannot reproduce a failure

What is happening: Fixture inputs or camera history were not recorded.

Try this: Make the scene and event script deterministic.

Tests pass but rain looks ineffective

What is happening: The visible fire state does not communicate internal extinguishing promptly.

Try this: Review timing and visual state together.

Performance regresses only during collapse

What is happening: Serial group/support work was excluded from profiling.

Try this: Measure the complete tick including event-driven tails.

Explain it without the example

Why recheck performance after adding bounded support searches?

Reasoning to compare

One bounded search can still be repeated many times after an explosion. Total per-tick work depends on event count as well as each search cap.
