Keep resident storage bounded

Evict unchanged resident chunks under a memory budget without losing edited world state.

Previously: Pan a camera and clip the active rectangle. Keep that working result available before starting this lesson.

Why we need this now

Chunking prevents one giant allocation, but keeping every visited chunk forever still grows memory. A resident cache needs a discard policy that respects which data can be regenerated and which data contains the player’s work.

Your result: Evict unchanged resident chunks under a memory budget without losing edited world state.

01Classify what can be recovered

An unchanged chunk can be reconstructed from seed, coordinates and generator version. An edited or simulated changed chunk differs from that baseline. Before saving exists, discarding the latter loses information. Therefore M0 may drop only unchanged resident chunks; changed chunks stay resident under an explicitly documented temporary limitation.

This is a tradeoff, not the final bounded-memory design. M4 adds persistence so changed chunks can be evicted after a safe write. A cache policy must never silently redefine changed as “not currently visible” just to meet a memory cap.

02Track recency separately from activity

Active chunks are currently needed by the simulation rectangle and should not be eviction candidates. Resident inactive chunks are frozen and can be considered. A last-active sequence counter gives a deterministic recency ordering; least-recently-active unchanged chunks are the first candidates under the temporary policy.

Do not use wall-clock timestamps if a simple monotonic sequence expresses the needed order. Tie-break by chunk key so fixture results are stable. The focused example chooses one victim from metadata rather than mutating actual chunks, which isolates the policy from disk I/O and borrowing complexity.

03Budget bytes rather than guessing from count

A chunk’s cell payload has a measurable size, but the process also owns map entries, metadata, vectors, rendering resources and pending work. A nominal64MB chunk-data cap is not a promise that the whole application uses64MB. Record what the cap includes and measure total resident memory separately.

When no safe unchanged victim remains, report the temporary limitation during development instead of deleting edited state. That scenario belongs in a test because it is inevitable under sustained editing before persistence is implemented. A memory watchdog cannot substitute for a data-loss policy.

04Verify regeneration and preserve changed chunks

Pan through unchanged terrain and count resident chunks under a chosen small fixture budget. Revisit an evicted coordinate and verify deterministic regeneration. Then mark a chunk changed, make it least recent, and confirm it is not chosen by the M0 victim selector.

The final cache will coordinate with the single-writer save queue, but do not invent that mechanism before the persistence lessons. A good incremental course names temporary restrictions clearly so the learner understands what is finished, what is safe, and which later module removes the limitation.

Walk through the working example

Download this worked example ↧

#[derive(Clone,Copy)]
struct Meta { key:(i32,i32),active:bool,changed:bool,last_active:u64 }
fn victim(chunks:&[Meta])->Option<(i32,i32)> {
    chunks.iter().filter(|c|!c.active && !c.changed)
        .min_by_key(|c|(c.last_active,c.key)).map(|c|c.key)
}
fn main() {
    let chunks=[
        Meta{key:(0,0),active:false,changed:true,last_active:1},
        Meta{key:(1,0),active:false,changed:false,last_active:2},
        Meta{key:(2,0),active:true,changed:false,last_active:0},
    ];
    assert_eq!(victim(&chunks),Some((1,0)));
    println!("edited and active chunks retained");
}

Read what each part does

  1. Metadata selection is tested without actual eviction.
  2. None must be handled as a policy constraint.
  3. The later writer integration changes the available safe actions.

01

No safe victim

Mark every inactive chunk changed and run the selector.

Need a hint?

None is a meaningful policy outcome.

Worked solution

The selector returns None. The caller must retain data and report or enforce a temporary editing/exploration limit; it must not choose an unsafe victim anyway.

How to verify your result

No edited chunk is discarded to satisfy the budget.

02

Tie-break recency

Give two unchanged inactive chunks the same last_active counter.

Need a hint?

A stable key tie-break makes the fixture deterministic.

Worked solution

The tuple ordering selects the smaller key for equal recency. Document that ordering so tests do not depend on map iteration.

How to verify your result

Repeated runs choose the same safe candidate.

03

Estimate the payload

Calculate4096 cells times8 bytes, then compare it to actual allocation metadata.

Need a hint?

The payload is only part of process memory.

Worked solution

The cell payload is32768 bytes, or32KiB. Map/vector overhead, loaded chunks, rendering buffers and pending jobs add more. Measure the real high-water mark rather than multiplying payload alone and declaring the process budget met.

How to verify your result

The report separates chunk-data budget from total process memory.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Player edits disappear after panning

What is happening: Changed chunks were treated as regenerable.

Try this: Retain them before M4; later evict only after safe persistence.

Memory still grows during heavy editing

What is happening: M0 has no persistent eviction for changed state yet.

Try this: Record and enforce the temporary limitation rather than claiming full bounded residency.

Victim selection changes between runs

What is happening: Hash-map iteration order is resolving ties.

Try this: Sort or compare explicit recency/key tuples.

Explain it without the example

Why not discard an edited chunk just because it is off-screen?

Reasoning to compare

Its state differs from deterministic generation. Without saving it, discarding it loses the player's changes.
