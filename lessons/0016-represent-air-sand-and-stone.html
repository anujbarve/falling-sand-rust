Represent air, sand and stone

Represent every valid prototype material with an enum and handle each case explicitly.

Why we need this now

The world is about to contain air, sand and stone rather than one special grain. Raw numbers could label them, but numbers permit meaningless states and hide intent. An enum gives the domain a vocabulary the compiler can check.

Your result: Represent every valid prototype material with an enum and handle each case explicitly.

01Replace implicit numeric meaning with named alternatives

Define Material with Air,Sand,Stone. Each variant is a valid alternative of the same type. A grid slot can hold one of these values; it cannot accidentally hold material17 unless we deliberately add such a representation. The benefit is not decorative naming: functions can demand Material rather than accepting every integer as potentially meaningful.

A custom enum can derive Copy,Clone,Debug,PartialEq,Eq when its contents support them. Here the variants carry no owned heap data, so those derived capabilities are appropriate. Deriving Copy is a deliberate modeling choice for a small material identity, unlike cloning an entire world to escape ownership design.

02Use match as a complete decision table

A match expression inspects the variant and selects its arm. Our example maps each material to a printable label. Later the same structure can select colour or movement kind. Because we list the variants explicitly, adding Water makes the compiler reveal match expressions that need another case.

Avoid adding a wildcard arm merely to silence that feedback when every known material needs intentional handling. A wildcard is useful when all remaining alternatives genuinely share one behavior, but it can also conceal an incomplete rule. Decide based on the domain contract, not on the shortest way to make a diagnostic disappear.

03Keep identity separate from state

Material::Sand identifies the kind of matter; a cell’s moisture and temperature describe its current state. We will not create a separate enum variant for every possible temperature. That would combine independent axes into an unmanageable list. A later cell struct stores identity and state separately.

For today, keep the enum small enough to enumerate in a terminal fixture. Draw each variant with one flat colour after the match behavior is understood. Air means an empty simulation slot, not an invisible solid; its visual background comes from the sky/interior rendering layer.

04Grow the table by observing a missing case

Add Water temporarily and run cargo check before implementing its label or colour. The non-exhaustive-match error is evidence that the compiler noticed a new domain alternative. Add an intentional arm and rerun. Then use equality to compare two Material values and Debug formatting to inspect them.

This gives us three useful tools: a closed set of names, exhaustive behavior selection, and simple diagnostics. The material table will grow, but the underlying reason stays the same: invalid combinations should be harder to represent, and missing behavior should be visible during development.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Material { Air, Sand, Stone }
fn label(material: Material) -> &'static str {
    match material {
        Material::Air => "air",
        Material::Sand => "sand",
        Material::Stone => "stone",
    }
}
fn main() {
    for material in [Material::Air, Material::Sand, Material::Stone] {
        println!("{:?}: {}", material, label(material));
    }
}

Read what each part does

  1. The enum variants are values of Material.
  2. The static string return borrows string literals embedded in the program.
  3. The explicit match supplies one outcome per variant.

Expected result

Air: air
Sand: sand
Stone: stone

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

How to verify your result

02

Select a colour

Return an RGB tuple from a material_colour function.

Need a hint?

A tuple can hold three channel values.

Worked solution

fn material_colour(m: Material) -> (u8,u8,u8) {
    match m {
        Material::Air => (15,26,51),
        Material::Sand => (226,182,121),
        Material::Stone => (121,128,135),
    }
}

Air’s tuple is only a teaching background choice; the production background is not stored as solid air material.

How to verify your result

Each prototype material has an explicit colour.

03

Explain Copy here

Why can material identities be copied cheaply without cloning the whole world?

Need a hint?

A small enum identity is not the collection that stores every cell.

Worked solution

The enum is a small value representing a kind. Copying that identity does not duplicate world ownership. The collection remains owned by World, and later state fields can still have their own semantics.

How to verify your result

The explanation does not generalize Copy to all structs or resources.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

non-exhaustive patterns

What is happening: A new variant is unhandled.

Try this: Add a deliberate match arm or justify a shared fallback.

Equality comparison fails

What is happening: The enum has not implemented PartialEq.

Try this: Derive PartialEq and Eq when appropriate for the identity type.

Copy appears to duplicate the world

What is happening: Only the small identity is Copy in this example.

Try this: Keep collection ownership and material identity conceptually separate.

Explain it without the example

Why use an enum instead of magic numbers for materials?

Reasoning to compare

Variants name the valid states. Exhaustive matching helps expose missing handling when a material is added.
