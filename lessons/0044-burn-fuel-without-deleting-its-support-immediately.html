Burn fuel without deleting its support immediately

A wall burns over time instead of vanishing at ignition. Wet and dry wood fixtures behave differently.

Previously: Prove deterministic water and heat. Keep that working result available before starting this lesson.

M2 starts here. Review this milestone’s implementation plan against the current spec. The lessons teach the work; they do not silently approve new game behavior.

Why we need this now

A burning beam should support its roof while it still exists as wood. Replacing the beam with gas at ignition makes the house collapse in a single update, even if the intended fire should take seconds. The solution is to model burning as state of the fuel, with visible flames as a separate product.

Your result: A wall burns over time instead of vanishing at ignition. Wet and dry wood fixtures behave differently.

01Keep identity until fuel is consumed

A Wood cell remains Wood while its burning flag is set. Its support and collision rules continue to treat it as rigid. A short-lived timer represents remaining fuel; the heat pass reads its burning temperature policy. When fuel reaches zero, replace the material with Ash or Air according to the chosen rule. That removal is the moment support needs reevaluation. This separates ignition, burning duration and structural failure into events you can observe independently.

02Treat flames as emitted gas, not the fuel itself

A burning cell may emit a Flame into an available neighbouring air slot, preferably upward and biased by wind. Flame has its own brief lifetime and carries heat as it moves. If there is no free slot, the fuel can still burn; failure to draw a new flame should not suspend its timer. Conversely, drawing an orange overlay cannot itself spread heat unless it corresponds to the actual flame/fuel rule. Rendering reads state; it does not manufacture an extra combustion simulation.

03Choose the order of wetting and burning

Rain and water affect whether fuel ignites, how it dries and whether an active fire goes out. Write the tick order explicitly: for example, apply precipitation/wetness before testing ignition, then update burning timers and emissions. Other orders are possible but produce different edge behavior. Test rain arriving on the same tick that dry wood reaches ignition. The game demands wet wood resist and rain stop fire within two seconds; those are interaction tests, not just colour choices.

04Observe a beam rather than a whole forest first

Build a short beam supporting one small roof group. Ignite the centre beam cell and track material, burning flag, timer and support outcome. It should remain rigid during positive fuel and become an ordinary conversion result when consumed. Then run the same fixture wet. This scene is small enough to explain every event on video and strong enough to catch the original instant-collapse bug. Only after it passes should the rule be tested in a hillside fire front.

#[derive(Clone, Copy, Debug, PartialEq)]
enum Material { Wood, Ash }
struct Cell { material: Material, burning: bool, fuel: u8 }
fn burn_tick(cell: &mut Cell) {
    if !cell.burning { return; }
    cell.fuel = cell.fuel.saturating_sub(1);
    if cell.fuel == 0 {
        cell.material = Material::Ash;
        cell.burning = false;
    }
}
#[test]
fn wood_remains_wood_until_consumed() {
    let mut beam = Cell { material: Material::Wood, burning: true, fuel: 2 };
    burn_tick(&mut beam);
    assert_eq!(beam.material, Material::Wood);
    burn_tick(&mut beam);
    assert_eq!(beam.material, Material::Ash);
    assert!(!beam.burning);
}

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Prevent underflow

Why use saturating_sub instead of fuel -= 1 on an unsigned counter?

Need a hint?

Consider an already-zero timer.

Worked solution

Subtracting below zero is invalid for the intended counter and can panic in checked builds. Saturation keeps zero at zero, then the exhausted-state branch performs the conversion.

How to verify your result

A zero-fuel burning fixture safely becomes Ash.

02

Add extinguishing

What should rain change before the next burn update?

Need a hint?

Fuel and burning state need not be the same thing.

Worked solution

Set burning=false under the approved extinguishing condition and preserve remaining fuel if the design allows later reignition. The timer should no longer decrement while unlit. Test a partially burned wet beam.

How to verify your result

Extinguished wood remains structurally present.

03

Notify support

When should the support system be told about the beam?

Need a hint?

Ignition alone did not remove its solid material.

Worked solution

Queue a support-dirty event when the Wood→Ash/Air conversion removes the rigid cell. Do not trigger collapse simply when burning becomes true.

How to verify your result

Support changes at consumption, not ignition.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Roof falls immediately at ignition

What is happening: Fuel was replaced by Flame or support ignores burning Wood.

Try this: Keep original material and use a burning flag.

Fire lasts forever

What is happening: Timer update is conditional on successful flame emission.

Try this: Consume fuel independently of empty visual slots.

Cold ash remains a heat source

What is happening: Burning/source flags survive conversion.

Try this: Clear source state explicitly when fuel is exhausted.

Explain it without the example

Why should a burning beam not immediately become a gas cell?

Reasoning to compare

It would lose solid support as soon as ignition occurs. Keeping the material until fuel is consumed lets structural loss follow burning duration.
