Return and propagate recoverable errors

Propagate a recoverable file error to a caller that prints a useful message and keeps running.

Previously: Transfer background jobs with channels. Keep that working result available before starting this lesson.

Why we need this now

A missing save is an expected external condition. It should lead to a useful choice—new world, backup or another path—not a panic that throws away the current session.

Your result: Propagate a recoverable file error to a caller that prints a useful message and keeps running.

01Begin with two possible outcomes

An integer-returning parser cannot say both “the value is zero” and “there was no valid value” using zero alone. Result keeps those outcomes separate. Its Ok variant contains the successful value; Err contains failure information. Which action follows belongs to the caller, not automatically to the low-level parser.

For a save header reader, success means validated metadata. Failure might mean the file cannot be read, the bytes are invalid or the version is unsupported. Preserve enough context to distinguish them. Do not turn every error into “save missing.”

02Follow the question mark through one function

The ? operator on a Result unwraps the success path for continued processing, or returns the error early through a compatible Result-returning function. It does not log, retry, choose a backup or repair data. Those decisions remain visible at the boundary where the operation is presented to the player.

First write the function using match on fs::read_to_string. Then replace the early-return pattern with ?. Compare the two versions. The shorter syntax is valuable only after the control flow is understood.

03Validate after reading

A successful read proves bytes were obtained, not that they form a valid world. Trim text in this teaching experiment, parse the number and map parser failure into an io::Error with InvalidData. A binary loader will later validate magic bytes, versions, lengths and material identifiers in the same logical order.

Keep this terminal experiment separate from real world saves. Its small text format is not the production format. We are learning failure flow before coupling it to chunks and background writers.

04Handle failure where context is available

The main function knows which path the user requested. It can print that path with the underlying error and leave the current world untouched. In production attach operation context, preserve the prior save and offer recovery. A low-level decoder should not reach into the UI to display a dialog.

Test both success and failure intentionally. A happy-path demonstration alone leaves the useful half of this lesson untested. Missing files, invalid text and permission failures may require different recovery messages even though all return Err.

use std::{fs, io};
fn read_seed(path: &str) -> io::Result<u64> {
    let text = fs::read_to_string(path)?;
    text.trim().parse().map_err(|error| {
        io::Error::new(io::ErrorKind::InvalidData, format!("invalid seed: {error}"))
    })
}
fn main() {
    let path = "lesson-seed.txt";
    match read_seed(path) {
        Ok(seed) => println!("seed = {seed}"),
        Err(error) => eprintln!("Could not read {path}: {error}"),
    }
}

Read what each part does

  1. Run with no lesson-seed.txt first; failure is part of the exercise, not a broken installation.
  2. Create the file containing 42 and run again to see the success branch.
  3. A failed parse becomes InvalidData; a failed read keeps the filesystem error kind.

Expected result

With a file containing 42: seed = 42. With no file: a contextual missing-file message; no panic.

Exact version numbers, paths and compiler wording may differ. Compare the behavior and file locations, not incidental output formatting.

01

Make both branches real

Run once without the file, once with 42, and once with sand as its contents.

Need a hint?

The current working directory determines this teaching path.

Worked solution

The first run returns an I/O error, the second returns Ok(42), and the third returns InvalidData. Only the caller prints the operation and path.

How to verify your result

Capture all three distinct outcomes.

02

Expand the control flow

Rewrite the first ? using match without changing behavior.

Need a hint?

Err must return from read_seed, not only print.

Worked solution

Use let text = match fs::read_to_string(path) { Ok(text) => text, Err(error) => return Err(error) }; and leave parsing unchanged.

How to verify your result

The three fixtures produce equivalent success/error kinds.

03

Protect existing state

A world with seed 7 is live. Loading seed text fails. What must remain unchanged?

Need a hint?

Do not assign partially loaded data into the world.

Worked solution

Retain seed 7 and all live world state. Construct and validate replacement state first; install it only after the load operation succeeds.

How to verify your result

A failed load fixture compares the live world hash before and after.
