M6 / World expansionLesson 94 of 100 · ~6 min reading + build time

Integrate optional events and close biome expansion

Route optional tools and natural events through one bounded command interface, then prove expansion has not broken the v1 world.

Previously: Grow a dense forest without losing the budget. Keep that working result available before starting this lesson.

Why we need this now

Two ways of starting rain should not produce two incompatible rain systems. An event command is a shared boundary between input, schedules, tests and simulation effects.

Your result: Route optional tools and natural events through one bounded command interface, then prove expansion has not broken the v1 world.

01Name intent before applying effects

An input event says what the player requested: ignite this coordinate, start rain in this weather column, or trigger this volcano. A command value captures that intent. The simulation validates it against current world state and applies one defined rule. Natural event schedules can submit the same command shape without pretending to be mouse input.

Use an enum with explicit coordinates/IDs instead of a string such as "eruption" interpreted independently by several modules. The command carries enough data to identify its target, while the world owns validation and consequences. Invalid targets return a normal rejection; a tool click over a panel should have been filtered earlier by input ownership.

02Put cooldowns at the correct boundary

Cooldown state belongs to the command source policy, not to the physical lava or rain cells. The player may have a one-day tool cooldown while a natural volcano uses a seasonal schedule. Share the effect executor, but do not accidentally force natural weather through the player’s toolbar cooldown.

The sample demonstrates that distinction with a Player/Nature source. It uses saturating addition for an extreme calendar value and stores the next player-ready tick. Whether pause permits editing tools is a separate approved control rule; tests should name it rather than inherit whatever event-loop order happened first.

03Bound execution, not only command creation

A single command can produce a large amount of work. Eruption must still obey particle capacity; rain edits weather humidity instead of touching every column in an infinite region; lightning uses bounded connected-metal handling. Queue capacity and per-frame dispatch are therefore only one layer of the budget.

Assign commands stable identifiers when recording replays or saving pending state. Decide which commands are already consumed at a snapshot boundary. A command applied immediately before a save must not be accidentally replayed from the pending queue after load and produce a second explosion.

04Close M6 with a regression matrix

Build rows for plains, mountain, sea/beach, desert, volcano, island and forest. For each, record rest behavior, intended disturbance, material accounting, active-boundary behavior, memory and frame-time results. The v1 rows remain required even if the new volcano clip looks excellent. A shared material property changed for ash or wood can alter an old beach or house fixture.

Keep optional event controls clearly labelled and verify their page/number-key mapping. Update the asset ledger for new biome sounds and images, and document any revised density cap. The M6 result is a set of passed contracts and known accepted exceptions, not an assertion that every conceivable world is stable.

#[derive(Clone, Copy)]
enum Source { Player, Nature }
#[derive(Clone, Copy)]
enum Command { Rain { column: i32 } }
fn accept(command: Command, source: Source, now: u64,
          ready: &mut u64, applied: &mut Vec<i32>) -> bool {
    if matches!(source,Source::Player) && now<*ready { return false; }
    match command { Command::Rain { column } => applied.push(column) }
    if matches!(source,Source::Player) { *ready=now.saturating_add(24_000); }
    true
}
fn main() {
    let (mut ready,mut applied)=(0,Vec::new());
    assert!(accept(Command::Rain{column:2},Source::Player,0,&mut ready,&mut applied));
    assert!(!accept(Command::Rain{column:2},Source::Player,1,&mut ready,&mut applied));
    assert!(accept(Command::Rain{column:3},Source::Nature,1,&mut ready,&mut applied));
    assert_eq!(applied,vec![2,3]);
    println!("shared effect path; distinct scheduling policies");
}

Read what each part does

  1. The example records accepted effects as column IDs so the source policy can be tested without weather simulation.
  2. The natural scheduler still has its own rate and capacity constraints; bypassing player cooldown does not mean unlimited work.
  3. Production validates the target before consuming cooldown or changing state, using the chosen invalid-request semantics.

01

Reach the cooldown boundary

Try the second player request exactly at24,000 ticks.

Need a hint?

The rejection condition is strictly before ready.

Worked solution

The request is accepted when now equals ready. Test ready−1, ready and ready+1 explicitly; a boundary error otherwise adds or removes a whole tick.

How to verify your result

Only the before-boundary case rejects.

02

Reject an invalid target

Add validation that disallows a target outside your bounded test world. Should it spend cooldown?

Need a hint?

Choose semantics before changing state.

Worked solution

A reasonable proposal rejects without spending cooldown. Validate first, then apply and update readiness. If the game chooses another policy, document and test it visibly.

How to verify your result

The failed request leaves effect state and readiness unchanged under that policy.

03

Regression after a new eruption

Need a hint?

Shared rules remain shared.

Worked solution

Run the v1 foundation, reaction, save and performance fixtures as well as expansion rows. At minimum retain plains fire/rain, water density, terrain rest, save round-trip and the target-load benchmark.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Tool rain behaves differently from natural rain

What is happening: Two code paths mutate weather independently.

Try this: Submit shared effect commands and keep only source scheduling distinct.

Saving doubles the next explosion

What is happening: Consumed and pending command state overlaps.

Try this: Define a snapshot boundary for command ownership.

New biome raises baseline cost

What is happening: Expansion changed shared defaults globally.

Try this: Separate biome configuration and rerun v1 performance gates.

Explain it without the example

Why test old plains scenes after adding new biome variants?

Reasoning to compare

Shared material tables and rules may change globally. New content can regress earlier behavior even when its own scene looks correct.
