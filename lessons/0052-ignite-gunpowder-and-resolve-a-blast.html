Ignite gunpowder and resolve a blast

Gunpowder explodes within the one-second deadline and the explosion fixture shows a crater and outward motion. Destroyed material is counted as an explicit exception.

Previously: Throw material as budgeted particles. Keep that working result available before starting this lesson.

Why we need this now

A particle engine does not create an explosion by itself. A charge needs an ignition/fuse trigger, one consumed event, a bounded selection of affected material, heat and outward motion. This lesson joins those pieces without leaving hot gunpowder as an infinite energy source.

Your result: Gunpowder explodes within the one-second deadline and the explosion fixture shows a crater and outward motion. Destroyed material is counted as an explicit exception.

01Turn ignition into one event

When eligible gunpowder ignites, remove or mark the charge consumed and enqueue a Blast command with a world centre and declared strength/radius. Process it once in a deterministic event phase. A bomb fuse can enqueue the same command when it expires. Natural ignition and player tools therefore reuse the blast mechanism. If you simply test “hot gunpowder exists” every tick without consuming it, one charge detonates repeatedly and adds unlimited heat and destruction.

02Bound the affected coordinates first

A circular blast of radius r only inspects the square from centre-r to centre+r, then accepts cells whose squared distance is at most r². Clip that rectangle to the active region and valid storage. Squared distance avoids a square root for selection, but its integer type must accommodate the maximum radius. The radius and strength caps are design/performance choices. Never let a malformed command or a giant brush request allocate an unbounded event list.

03Use hardness and ownership deliberately

For each selected cell, decide whether it is untouched, destroyed or thrown based on the approved strength falloff and hardness rule. Thrown cells transfer into the particle list with outward velocity; destroyed cells are counted explicitly. The central cell needs a defined direction because normalizing a zero vector is invalid. Heat is another output of the blast and can trigger nearby fuel later. Keep these outcomes staged so a cell is not simultaneously thrown, destroyed and left in the grid.

04Test the required visible effects separately

The one-second requirement applies to ignition and explosion effects at 1x. A fixture should assert the event is emitted once, a crater appears, material gains outward motion and nearby flammable matter receives heat/ignition under the selected rule. The flash and sound are readable decoration, not substitutes for a crater. At the particle cap, verify the designed destruction fallback rather than expecting strict mass conservation. A quiet closed fixture without destruction remains useful for ownership tests.

fn inside_blast(dx: i32, dy: i32, radius: i32) -> bool {
    let dx=i64::from(dx); let dy=i64::from(dy); let r=i64::from(radius);
    radius >= 0 && dx*dx + dy*dy <= r*r
}
fn consume_trigger(armed: &mut bool) -> bool {
    if !*armed { return false; }
    *armed=false;
    true
}
#[test]
fn selection_is_bounded_and_trigger_is_single_use() {
    assert!(inside_blast(3,4,5));
    assert!(!inside_blast(4,4,5));
    let mut armed=true;
    assert!(consume_trigger(&mut armed));
    assert!(!consume_trigger(&mut armed));
}

Exercises you actually do

Write a prediction or make an attempt before opening a solution. Use the hint if stuck; then compare reasoning and verify with the stated check. A different implementation is fine when it satisfies the same contract.

01

Check the centre

What velocity direction should a parcel exactly at the blast centre receive?

Need a hint?

Its radial vector has length zero.

Worked solution

Choose an explicit deterministic fallback such as straight upward or a seed-derived unit direction. Do not divide by zero while normalizing the radial vector.

How to verify your result

The central-particle fixture produces finite velocity values.

02

Avoid repeated chains

Two charges ignite each other. How do you prevent one charge from being queued twice in one event phase?

Need a hint?

Consumption/queued state must change before processing neighbours.

Worked solution

Mark or replace each charge immediately when its explosion is queued, or deduplicate events by a stable consumed charge identity. A second contact sees it as already consumed.

How to verify your result

Each initial charge produces at most its intended one event.

03

Test the cap

What remains true when only two particle slots are free but ten cells are selected for throwing?

Need a hint?

The spec has an explicit overflow exception.

Worked solution

At most two particles are created; additional selected cells follow the declared destruction rule. Count destroyed cells so the sum of grid, particles and explicit destruction balances the input selection.

How to verify your result

The list never exceeds capacity and all outcomes are accounted.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

One charge explodes every tick

What is happening: The trigger is never consumed.

Try this: Change charge state before queuing the event.

NaN debris appears at the centre

What is happening: A zero radial vector was normalized.

Try this: Use the explicit centre fallback and test finite outputs.

Blast work grows unexpectedly

What is happening: The radius or event chain has no bound.

Try this: Cap radius/event count and inspect total selected cells per tick.

Explain it without the example

Why enqueue a single explosion instead of treating hot gunpowder as an endlessly active blast source?

Reasoning to compare

An event should be consumed once. Re-triggering each tick repeats energy and destruction beyond the specified charge.
