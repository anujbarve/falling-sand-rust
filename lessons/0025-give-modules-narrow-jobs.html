Give modules narrow jobs

Separate world storage, simulation and rendering into modules with narrow interfaces.

Previously: Paint materials into the world. Keep that working result available before starting this lesson.

Why we need this now

Our main file now contains unrelated reasons to change: storage layout, falling rules, mouse handling and drawing. Modules let us separate those responsibilities so a physics test can run without opening a window and a visual change cannot casually rewrite state.

Your result: Separate world storage, simulation and rendering into modules with narrow interfaces.

01Begin with dependencies, not folder decoration

World stores material state. Simulation reads and updates it. Rendering reads it. Main coordinates input, scheduling and presentation. Draw these relationships before moving files: the useful boundary is which operations need ownership or mutation, not how many folders look professional.

A module is a namespace and visibility boundary. Splitting code into files without changing who can touch what can merely scatter the same coupling. Start with world.rs, simulation.rs and render.rs only because those jobs already exist in the program.

02Expose operations rather than every field

Rust items are private by default in the relevant module context. Use pub on the small interfaces another module genuinely needs. A render function may accept &World, a tick function &mut World. The rest of the crate should not require direct mutable access to every allocation detail.

Early teaching code may temporarily expose fields while we learn the mechanics, but record that as a convenience rather than a final design principle. A checked query and paint/move operation can preserve invariants better than callers independently calculating unchecked indices.

03Move one responsibility and compile

Create world.rs with the material/world definitions, declare mod world; in the crate root, and import the needed public type. Compile before moving the next responsibility. This isolates missing visibility and path errors. A huge simultaneous file shuffle makes it harder to distinguish an architecture mistake from a simple import typo.

The worked terminal example below demonstrates a nested module in one file so it can be compiled independently. The same module body can move to src/world.rs when the crate root declares mod world. File location follows Rust’s module rules; a file merely existing in src does not automatically make its items available.

04Protect the headless path

Keep window initialization in main and graphical drawing in render. A test of World or tick should not invoke macroquad’s main attribute or create a native context. This reduces setup cost and lets CI exercise behavior without a display.

Do not introduce traits or generics at every boundary just because modules exist. A small concrete function can be a strong interface. We will add a trait later where interchangeable deterministic choice sources create a real testing need. End the episode with one headless test importing the simulation path and one working window using the same state model.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

mod world {
    #[derive(Clone,Copy,Debug,PartialEq,Eq)]
    pub enum Material { Air, Sand, Stone }
    pub struct World { cells: Vec<Material> }
    impl World {
        pub fn new(size:usize)->Self {Self{cells:vec![Material::Air;size]}}
        pub fn len(&self)->usize {self.cells.len()}
    }
}
use world::World;
fn main() {
    let world=World::new(32);
    println!("world slots={}",world.len());
}

Read what each part does

  1. The focused example keeps module mechanics separate from macroquad.
  2. A method can observe private state through a public interface.
  3. Moving files should preserve behavior before new features are added.

Expected result

world slots=32. The nested module is a complete demonstration; move its body into src/world.rs during integration.

01

Split the demonstration

Move the world module body to src/world.rs.

Need a hint?

The crate root declares mod world without repeating the body.

Worked solution

Replace the inline module block with mod world;, keep the use statement, and place the previous module contents in src/world.rs. Run cargo check before changing behavior.

How to verify your result

The output stays unchanged after the structural move.

02

Keep storage private

Try accessing world.cells from main.

Need a hint?

The field deliberately has no pub.

Worked solution

The compiler rejects direct private-field access. Use the public len method for this observation. Add a narrow operation only when another responsibility actually needs it.

How to verify your result

The program uses its interface rather than exposing all storage.

03

Name a dependency direction

Should World::new need a graphics window to allocate cells?

Need a hint?

Storage initialization should be usable by headless tests.

Worked solution

No. It should construct data without a native context. Render can depend on World, while World should not depend on opening the display.

How to verify your result

A terminal or unit test can construct the same World.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

unresolved import after file move

What is happening: The module was not declared or the path changed.

Try this: Check mod world and the use path in the crate root.

field is private

What is happening: Another module is bypassing the chosen interface.

Try this: Use or add a narrow operation instead of indiscriminately making fields public.

Tests open a window

What is happening: Graphics initialization leaked into storage or simulation setup.

Try this: Keep context creation in the executable orchestration path.

Explain it without the example

What should decide whether a helper becomes pub?

Reasoning to compare

Whether another module needs the interface. Making every field and helper public weakens the boundary without helping the game.
