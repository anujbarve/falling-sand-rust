Repeat a small update

Trace a finite loop and identify exactly what makes it terminate.

Previously: Decide whether a cell may fall. Keep that working result available before starting this lesson.

Why we need this now

A frame loop will repeat while the game window exists. Before that, we need a repeatable experiment small enough to trace completely. A finite while loop lets us see how a condition and a state update cooperate to produce several steps rather than one.

Your result: Trace a finite loop and identify exactly what makes it terminate.

01Replace repeated typing with a rule

We could write row += 1 three times, but the structure would hide the condition that decides how many steps are needed. A while loop expresses “repeat while this condition is true.” Starting at row 5 and continuing while row < 8 produces updates to 6,7,8. The body runs only after the condition is checked.

This order matters. If row already starts at 8, the body runs zero times. A loop is not a promise to perform at least one update; that depends on the construct and condition. Trace the initial check as well as the body when predicting output.

02Keep a state table beside the code

Before running, make three columns: row before the condition, condition result, and row after the body. The first row is 5,true,6; next 6,true,7; next 7,true,8; finally 8,false,no body. The printed lines appear after the increment, so they are 6,7,8 rather than 5,6,7.

This table is an execution trace. It is a way to discover where a mistaken prediction came from instead of randomly changing code. The same method later explains why an in-place grid scan can update one grain twice: track the state before each iteration, not merely the list of source statements.

03Remove the progress and observe the consequence

Temporarily remove row += 1. The condition remains true forever because row never changes. The terminal prints repeatedly and cargo run does not return. Stop the process with Ctrl+C. This experiment is intentionally small; do not leave an uncontrolled printing loop running while changing unrelated settings.

Restore the increment and verify termination. A loop generally needs some reason its condition will eventually become false, or a deliberate external exit policy. A game’s main loop is intentionally ongoing, but it must yield to the window framework so input and closing events can be processed. That is the next lesson’s different kind of repetition.

04Separate an update loop from elapsed time

The finite loop below runs as quickly as the CPU executes it. It does not mean one step per second, one tick per frame, or a physically meaningful falling rate. Repetition and timing are separate problems. We will later add an accumulator that decides when an update is due.

For now, the win is being able to predict iteration count and state changes. Try a different starting row and a step of two. Ask what happens when the step jumps past the limit. These variations prepare you to reason about clamping and overshoot without needing a graphical debugger.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

fn main() {
    let mut row = 5;
    while row < 8 {
        row += 1;
        println!("{row}");
    }
    println!("finished at {row}");
}

Read what each part does

  1. while reevaluates the condition before every body execution.
  2. The last print is outside the loop and runs once after termination.
  3. No timing policy has been introduced yet.

Exercises you actually do

01

Move the print

Print before the increment rather than after it.

Need a hint?

The observed value depends on statement order.

Worked solution

while row < 8 {
    println!("{row}");
    row += 1;
}

Starting at 5, the loop prints 5,6,7. The final row is still 8. Moving an observation can change output without changing final state.

How to verify your result

You predict both printed sequence and final state.

02

Change the step

Start at 5, add 2 per iteration, and keep the condition row < 8.

Need a hint?

Trace 5,7,9 rather than assuming exact landing.

Worked solution

The body runs twice: row becomes 7, then 9. The next condition is false. The loop condition alone does not clamp the destination to 8; collision code must handle that separately.

How to verify your result

You explain why overshoot is possible despite a bounded condition.

03

No iterations

Start at 8 and run the original loop.

Need a hint?

while checks its condition before entering the body.

Worked solution

Only the final finished message appears. The loop body runs zero times because the first condition is already false.

How to verify your result

The observed output matches the zero-iteration prediction.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

The terminal never returns

What is happening: The body fails to move state toward a false condition.

Try this: Use Ctrl+C, then restore or repair the progress update.

The printed sequence is one step off

What is happening: Print and mutation order were confused.

Try this: Trace the value at the exact println! statement.

The loop reaches 9 rather than 8

What is happening: A larger step overshot the threshold.

Try this: Do not confuse a loop-entry condition with destination clamping.

Explain it without the example

What makes this while loop terminate?

Reasoning to compare

Each iteration changes row toward the limit. The condition is rechecked before the next iteration and eventually becomes false.
