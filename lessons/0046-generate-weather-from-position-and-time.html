Generate weather from position and time

Panning across a weather boundary changes conditions smoothly. Returning to the same coordinate/time reproduces baseline values.

Previously: Separate absorbed moisture and surface wetness. Keep that working result available before starting this lesson.

Why we need this now

Weather is a property of the world at a time, not a random choice made when the camera enters a chunk. We want two observations of the same place and calendar instant to agree. That requirement leads naturally to a functional baseline plus a small stored record of what the player changed.

Your result: Panning across a weather boundary changes conditions smoothly. Returning to the same coordinate/time reproduces baseline values.

01Choose the independent coordinates

Divide horizontal world space into weather columns 512 cells wide. Their centres hold baseline humidity, cover, wind and temperature-offset values derived from seed and world time. The camera coordinate is absent from this function. You can evaluate a far column without running its material cells, which fits frozen off-screen simulation. This is not the same as freezing the climate forever: world time still selects the current baseline when that region is observed again.

02Interpolate instead of creating a border wall

A hard assignment of one weather value per column creates a visible jump at every 512-cell boundary. For a position between neighbouring centres, calculate a fraction from 0 to 1 and blend their values. Humidity and cloud cover can blend directly; wind direction should be represented as a vector or a carefully defined scalar to avoid angular wrap surprises. The lab uses a linear scalar blend so its meaning can be checked before adding seeded noise.

03Store only deviations that need history

A rain-cloud tool or evaporation changes local humidity in a way the baseline function cannot reproduce from seed and time alone. Store that as a delta, then evaluate actual humidity as bounded baseline plus delta. The delta decays toward zero under a documented calendar rule. If decay is evaluated lazily when a column is used, record the time needed to compute that decay; do not quietly forget a player effect simply because its chunk unloaded. This weather state is saved separately from frozen material state.

04Test the field without waiting for a storm

The function should accept world position and integer world time as parameters. Use fixed neighbour values to test interpolation endpoints, midpoint and clamping. Then add deterministic baseline variation and compare repeated evaluations. A developer-only inspector can show baseline, delta and final value separately. That distinction makes it clear whether a sudden change came from seeded climate, a tool event or a bug in border interpolation.

fn blend(left: f32, right: f32, fraction: f32) -> f32 {
    left + (right-left) * fraction.clamp(0.0, 1.0)
}
fn humidity(baseline: f32, delta: f32) -> f32 {
    (baseline + delta).clamp(0.0, 1.0)
}
#[test]
fn weather_blends_and_bounds() {
    assert!((blend(0.2, 0.8, 0.5)-0.5).abs() < 0.0001);
    assert_eq!(blend(0.2, 0.8, -1.0), 0.2);
    assert_eq!(humidity(0.8, 0.5), 1.0);
    assert_eq!(humidity(0.1, -0.5), 0.0);
}

01

Trace a border

Blend humidity 0.3 and 0.7 at fractions 0,0.25,0.5,1.

Need a hint?

Write left + difference times fraction.

Worked solution

The values are 0.3,0.4,0.5,0.7. This continuous progression removes an abrupt state jump, though thresholding rain on/off may still need visual/intensity tuning.

How to verify your result

Endpoint and midpoint assertions pass within float tolerance.

02

Separate the delta

A tool adds 0.4 to baseline 0.2. Later baseline becomes 0.3 while the delta remains 0.4. What changes?

Need a hint?

The two contributions are evaluated independently.

Worked solution

Actual humidity changes from 0.6 to 0.7 before clamping or delta decay. Saving only the final 0.6 would lose the distinction needed to evaluate future climate correctly.

How to verify your result

A fixture retains delta independently of baseline.

03

Prove camera absence

Evaluate one weather coordinate before and after changing only the camera.

Need a hint?

The weather function should not accept the camera.

Worked solution

Call the same function with identical seed, world x and world_tick. The result should be identical. Camera history only affects active material processing, not this baseline field.

How to verify your result

Weather baseline evaluation is invariant to camera changes.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Rain changes sharply at a region edge

What is happening: The code selects one column without interpolation.

Try this: Blend values between centres and inspect the fraction.

Tool rain disappears after unloading

What is happening: The humidity delta was held only in a disposable chunk.

Try this: Persist weather deltas with their weather-column identity.

Weather advances while paused

What is happening: The field reads wall-clock time.

Try this: Use the paused integer world clock as its input.

Explain it without the example

Why separate a functional baseline from a stored humidity delta?

Reasoning to compare

The baseline can be evaluated without off-screen simulation. The delta preserves player and simulation effects that cannot be regenerated from seed and time alone.
