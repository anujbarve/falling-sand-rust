Pan a camera and clip the active rectangle

Pan the visible world while simulating only the cell-clipped view plus its16-cell margin.

Previously: Split storage into 64 by 64 chunks. Keep that working result available before starting this lesson.

Why we need this now

A camera changes which part of the world is visible, not the stored size of a grain. The active simulation region is the visible rectangle plus a small margin. Selecting overlapping chunks alone is too broad, so we will compute exact per-cell intersections.

Your result: Pan the visible world while simulating only the cell-clipped view plus its16-cell margin.

01Write the camera transform in units

A camera origin identifies the world coordinate displayed at the view’s origin. Drawing subtracts that origin before multiplying by cell size. Picking reverses the transform. Use one shared conversion contract so moving the camera cannot separate cursor targeting from the image.

In this prototype, rows still increase downward; the later altitude lesson converts to the final upward-world convention. Keep that limitation visible. Camera easing may use fractional presentation state, but grid edits must resolve to explicit cell coordinates and drawing must preserve hard pixel edges.

02Define half-open rectangles

Represent a rectangle as left,top,right,bottom with right and bottom excluded. Its width is right-left and height bottom-top. Expanding the view by16 cells subtracts16 from left/top and adds16 to right/bottom. Intersection takes the greater lower bounds and smaller upper bounds.

Half-open ranges match Rust iteration and avoid double-updating a boundary cell shared by adjacent rectangles. Empty intersections are ordinary: if left>=right or top>=bottom, there are no cells to visit. The focused example computes these bounds independently of world storage so edge cases remain easy to test.

03Clip inside every overlapping chunk

A64-cell chunk that overlaps the active rectangle may extend63 extra cells beyond it. Updating that entire chunk reintroduces a much larger margin than the design budgets. First select candidate chunks, then intersect each chunk rectangle with the active rectangle and iterate only that clipped part.

The distinction between storage unit and simulation unit is crucial. A resident chunk can be partly active and partly frozen. Its allocation exists as a whole, but only the selected cells receive movement, heat and slow work under the current active-region policy.

04Test what remains frozen

Build a fixture whose active edge cuts through the middle of a chunk. Snapshot cells just outside it, run several ticks, and assert they remain unchanged. Also verify that the16-cell margin updates while cells beyond it do not. Panning should reactivate the new rectangle according to the documented frozen-world semantics.

Boundary walls and gas absorption still make edge behavior camera-dependent by design. Do not claim that every overlapping cell always produces identical future state under arbitrary camera histories. Compare only within the accepted scope and keep the margin approximation visible in tests.

#[derive(Clone,Copy,Debug,PartialEq,Eq)]
struct Rect { left:i32,top:i32,right:i32,bottom:i32 }
fn intersect(a:Rect,b:Rect)->Option<Rect> {
    let r=Rect{left:a.left.max(b.left),top:a.top.max(b.top),
        right:a.right.min(b.right),bottom:a.bottom.min(b.bottom)};
    if r.left<r.right && r.top<r.bottom {Some(r)} else {None}
}
fn main() {
    let chunk=Rect{left:0,top:0,right:64,bottom:64};
    let active=Rect{left:20,top:10,right:80,bottom:40};
    let clip=intersect(chunk,active).unwrap();
    assert_eq!(clip,Rect{left:20,top:10,right:64,bottom:40});
    println!("{} active cells in this chunk",(clip.right-clip.left)*(clip.bottom-clip.top));
}

Read what each part does

  1. The fixture measures clipped work independently of rendering.
  2. The unwrap is valid only because this known fixture guarantees an overlap.
  3. Production missing intersections should be handled without assuming presence.

02

Test touching rectangles

Intersect[0,64) and[64,128) on one axis.

Need a hint?

The shared boundary has no width.

Worked solution

The intersection is empty. Treating both ends as inclusive would double-count or invent a boundary column.

How to verify your result

No cell is visited twice because of a touching edge.

03

Freeze a partial chunk

Select only rows10..20 in a chunk and run a changing rule.

Need a hint?

Allocation does not imply activity.

Worked solution

Assert rows outside the clip are unchanged. This test fails if the updater simply loops over every cell in an overlapping chunk.

How to verify your result

Off-region cells in the same allocated chunk remain frozen.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Active count is unexpectedly large

What is happening: Whole overlapping chunks are simulated.

Try this: Intersect at cell granularity inside each candidate chunk.

Picking drifts while panning

What is happening: Mouse inverse and drawing transform use different camera origins.

Try this: Share the transform definitions and test round trips.

Edge cells update twice

What is happening: Inclusive and exclusive boundaries were mixed.

Try this: Use one half-open rectangle convention everywhere.

Explain it without the example

Why is overlapping-chunk selection insufficient to enforce a 16-cell margin?

Reasoning to compare

An overlapping chunk may extend up to 63 cells beyond the rectangle. Per-cell clipping is needed inside each selected chunk.
