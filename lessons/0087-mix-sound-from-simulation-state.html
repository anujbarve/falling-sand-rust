Mix sound from simulation state

Drive a small, bounded set of audio loops from rain, wind and fire activity, with immediate mute and a recoverable missing-audio path.

Previously: Implement bounded local-revert undo. Keep that working result available before starting this lesson.

Why we need this now

A thousand burning cells do not require a thousand crackle voices. The simulation already contains activity signals; a mixer compresses those signals into a few intentional sound sources.

Your result: Drive a small, bounded set of audio loops from rain, wind and fire activity, with immediate mute and a recoverable missing-audio path.

01Separate the world, mixer and playback

Start with three layers. Simulation reports counts or rates, such as burning cells and rainfall intensity. A pure mixer maps those numbers into target gains. The audio backend loads clips and applies the gains. This makes the useful part testable without speakers and avoids putting audio calls into every cell update.

Choose bounded normalizers rather than raw counts. For instance, map zero through 200 burning cells to fire gain zero through a chosen maximum, clamping above 200. The number 200 is a tuning choice, not physics. A soft ramp avoids a one-cell fire sounding as loud as an entire forest.

02Enable the real audio backend explicitly

macroquad0.4.16 does not enable audio in its default feature set. Replace the existing dependency entry with macroquad = { version = "=0.4.16", features = ["audio"] }. Keep one dependency entry, not a second duplicate. Without that feature, the audio module can expose dummy operations that compile without producing sound, so compilation alone is not the test.

After selecting the dependency feature in your actual game milestone, perform the native build and a single known-clip playback test. Native backend prerequisites vary by platform; use the actual error and pinned crate documentation to choose any needed setup. This course-generation task does not install or change your machine’s packages.

03A loop is started once, then controlled

With macroquad, load_sound is asynchronous and returns a Result. play_sound accepts a borrowed Sound and PlaySoundParams, including looped and volume. Start a persistent loop once after successful loading. Update it with set_sound_volume as activity changes. Calling play_sound every rendered frame restarts or overlaps playback rather than smoothly adjusting the existing source.

When mute changes, apply zero output immediately. Keep the simulation and mixer state running, so unmuting can restore the current scene instead of replaying stale events. Do not pause fire, rain or the world clock because audio is muted. These are independent user preferences.

04Smooth noisy signals and duck around events

Counts may jump when the camera crosses chunks. A simple first-order smoothing step moves current gain toward target over elapsed real time: current += alpha * (target-current), with alpha clamped to the range zero through one. Derive alpha from a chosen smoothing speed and frame delta; clamp large deltas so window dragging cannot create an overshoot. The pure target function below remains separate from that temporal smoothing.

An explosion may temporarily reduce the ambient bed while its one-shot plays. Store an event-duck timer and compute the bed multiplier from it. Cap concurrent event voices and choose whether excess events merge, replace a quieter voice or are skipped. This cap makes a chain reaction bounded rather than a sound-card stress test.

05Handle assets and failure deliberately

Keep clip paths and licence metadata in one asset table. If a loop fails to load, store None for that source and continue silently with a small settings message. Do not unwrap normal audio I/O. A successful load on your laptop does not prove a target machine has a working audio device, so include a mute/no-device playtest.

The worked example contains the headless mixing contract. After it passes, connect each returned gain to the already loaded macroquad sound. A typical loading branch is match load_sound(path).await { Ok(sound) => Some(sound), Err(error) => { report(error); None } }. Keep reporting out of the cell loop and remember that an error message is not a reason to corrupt or abandon a save.

#[derive(Debug, PartialEq)]
struct Gains { wind: f32, rain: f32, fire: f32 }
fn gains(wind: f32, rain: f32, burning: usize,
         muted: bool, event_duck: f32) -> Gains {
    let master = if muted { 0.0 } else { 1.0 };
    let bed = master * event_duck.clamp(0.0, 1.0);
    Gains {
        wind: wind.clamp(0.0, 1.0) * 0.15 * bed,
        rain: rain.clamp(0.0, 1.0) * 0.35 * bed,
        fire: (burning as f32 / 200.0).clamp(0.0, 1.0) * 0.30 * bed,
    }
}
fn main() {
    let quiet = gains(0.4, 0.0, 0, false, 1.0);
    let fire = gains(0.4, 0.0, 5000, false, 1.0);
    assert!(quiet.fire == 0.0 && fire.fire <= 0.30);
    assert_eq!(gains(1.0, 1.0, 200, true, 1.0),
               Gains { wind: 0.0, rain: 0.0, fire: 0.0 });
    println!("bounded fire; immediate mute; independent world state");
}

Read what each part does

  1. clamp protects the backend from unbounded activity-derived gains. Reject or normalize non-finite inputs at the simulation/audio boundary.
  2. The example uses linear gain targets; perceptual tuning and smoothing are later adjustments, not hidden simulation rules.
  3. No Sound type is needed in the pure mixer test. The playback layer owns those backend resources.

Expected result

bounded fire; immediate mute; independent world state

Exercises you actually do

01

Make saturation visible

Compare the target gain for 200 and 20,000 burning cells.

Need a hint?

Both reach the chosen saturation count.

Worked solution

Both return fire gain 0.30 before ducking/master changes. The loop count remains one; increased fire activity cannot allocate another 19,800 voices.

How to verify your result

Assert equal gains for both cases.

02

Duck without muting forever

Use event_duck=0.25 during an explosion, then return it to 1.0.

Need a hint?

The bed is scaled, not destroyed.

Worked solution

Every bed gain is temporarily one quarter of its normal value. Restoring the multiplier recovers current activity. Do not restore an obsolete gain captured before the event.

How to verify your result

The mixer output returns to the current, not historical, target.

03

Remove the rain asset

Temporarily point the rain path at a nonexistent file.

Need a hint?

Loading is fallible.

Worked solution

The load branch produces None and records one useful diagnostic. Fire and wind continue; the game can save and quit. Restore the correct path after testing.

How to verify your result

The missing clip never causes a panic or a repeated per-frame error flood.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

Crackle stutters or multiplies

What is happening: play_sound is called every frame.

Try this: Start the loop once; change its gain afterward.

A forest clips or becomes deafening

What is happening: Raw counts drive gain or create voices.

Try this: Normalize/clamp gains and cap one-shot concurrency.

Missing sound quits the whole game

What is happening: An expected load error was unwrapped.

Try this: Keep an optional source and a recoverable diagnostic.

Explain it without the example

Why aggregate burning-cell counts instead of playing one crackle per cell?

Reasoning to compare

Per-cell playback scales poorly and creates noise. Aggregate activity can control a small bounded set of loops and event voices.
