Iterate and inspect a grid without moving it

Inspect and count world contents through borrowed iteration while preserving the world for later frames.

Previously: Move material without duplicating it. Keep that working result available before starting this lesson.

Why we need this now

A renderer and a statistics pass need to read all cells repeatedly. Rust offers several ways to iterate, and choosing the wrong ownership mode can consume the collection. We will compare those modes by their access contract, not by memorizing three similar names.

Your result: Inspect and count world contents through borrowed iteration while preserving the world for later frames.

01Read elements without consuming storage

cells.iter() produces shared references to the vector’s elements. The vector remains owned by World. This is the natural starting point for counting materials or drawing cells, because neither task should take the collection away from the simulation.

A for loop over &cells also borrows its contents. The exact binding type inside the loop matters: with an iterator over references, a value comparison may need dereferencing. Begin with explicit for syntax and print the types mentally before compressing it into chained operations. Concision is useful only after the ownership relation is clear.

02Mutable iteration grants field access, not resizing permission

iter_mut() lends mutable access to elements one by one. It suits an operation such as setting a local flag or resetting a numeric buffer. While such borrows are in use, you cannot freely resize the same vector because reallocation could invalidate references.

Use a fixed-size cell buffer for a simulation pass and separate additions/removals into another owned event list when needed. A grid neighbour-movement pass may be clearer with indices and controlled swaps rather than iter_mut, because it needs to access related slots and avoid aliasing. There is no rule that every loop must be rewritten as an iterator chain.

03Consuming iteration is a different operation

Calling into_iter on an owned Vec consumes the collection and yields owned elements. That can be exactly right when transferring or transforming ownership, but it is wrong for a renderer that must use the same world again next frame. Calling methods on a borrowed value can have different receiver behavior, so inspect the actual receiver type rather than memorizing the method name alone.

The focused example uses a borrowed iter twice to prove the vector survives both passes. Then a separate temporary vector can demonstrate consuming iteration. Do not consume the main world just to print it and then recreate it, because that hides the architectural mistake with unnecessary allocation.

04Derive counts as observations, not additional state

A sand count can be computed from the existing cells by filtering identities. It need not be maintained as a second mutable truth until performance measurements justify a cached counter. Two independent counts that can drift make conservation harder to reason about.

Use enumeration when you need each element’s flat index, then derive row and column from that index and width. That makes drawing a read-only interpretation of storage. End with a prediction: adding one Sand through an explicit paint command changes the observed count by one; drawing and counting alone leave it unchanged.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

#[derive(Clone,Copy,PartialEq,Debug)]
enum Material { Air, Sand, Stone }
fn sand_count(cells:&[Material])->usize {
    cells.iter().filter(|material| **material==Material::Sand).count()
}
fn main() {
    let cells=vec![Material::Sand,Material::Air,Material::Sand,Material::Stone];
    println!("sand={}",sand_count(&cells));
    for (index,material) in cells.iter().enumerate() {
        println!("{index}: {material:?}");
    }
    println!("still owned, len={}",cells.len());
}

Read what each part does

  1. sand_count accepts a slice so it needs read access, not ownership of a Vec.
  2. filter receives a reference to the iterator item, hence the explicit dereference in this simple identity predicate.
  3. enumerate pairs observation with the original flat index.

Expected result

sand=2, followed by the four indexed identities, then still owned, len=4.

02

Mutate numeric elements

Use iter_mut to add1 to each element of vec![1,2,3].

Need a hint?

The loop binding is a mutable reference.

Worked solution

let mut values=vec![1,2,3];
for value in values.iter_mut() { *value += 1; }
assert_eq!(values,[2,3,4]);

Place the fragment inside main.

How to verify your result

The existing vector changes without replacement or cloning.

03

Recover coordinates

For a flat index10 in a4-wide grid, derive row and column.

Need a hint?

Division counts full rows; remainder finds the position within one row.

Worked solution

row=10/4=2 and column=10%4=2. This nonnegative local-buffer mapping differs from signed world-to-chunk mapping, which later uses Euclidean division.

How to verify your result

The derived coordinate maps back to index10.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

World is moved after rendering

What is happening: Rendering consumed the owned vector.

Try this: Iterate a shared borrow instead of consuming World storage.

Cannot push while iterating mutably

What is happening: An active element borrow conflicts with resizing the vector.

Try this: Keep grid size fixed during the pass or defer structural changes.

A filter comparison has the wrong reference level

What is happening: Iterator adapters add reference layers in their callback arguments.

Try this: Inspect the argument type and dereference deliberately rather than guessing.

Explain it without the example

Why can into_iter on an owned vector make that vector unavailable afterwards?

Reasoning to compare

It consumes the collection to produce owned elements. Borrowed iteration instead lends access while retaining the collection with its owner.
