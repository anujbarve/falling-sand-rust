Budget the production scheduler

Switching 64x to 1x leaves no physics backlog. Both measured frame work and uncancellable single-tick overshoots are reported honestly.

Design choice to settle. The current specification leaves a decision here. The example makes the mechanism concrete; document the chosen behavior before treating it as the final game rule.

Why we need this now

The first falling-cell clock taught elapsed time, but production must survive a slow tick, a dragged window and a speed change. The scheduler is a small policy engine: it decides which work is due, how much can run, and what debt is kept or discarded. We can test that policy without sleeping or opening a window.

Your result: Switching 64x to 1x leaves no physics backlog. Both measured frame work and uncancellable single-tick overshoots are reported honestly.

01Separate real elapsed time from simulation time

Measure wall-clock duration between frames, clamp it to the declared 250 ms maximum while unpaused, and accumulate it. Target tick period is 50 ms divided by selected speed. A paused frame contributes no elapsed time. Pause/speed changes reset the specified accumulators so old debt cannot create a burst after resuming. Inject elapsed values in a test rather than waiting for actual time; a test using sleeps is slower and subject to OS scheduling noise.

02Discard capped physics debt explicitly

Compute how many target periods are due. Run no more than the measured count cap and frame-time policy allow, then keep only the sub-period fraction of physics elapsed time. Overdue whole physics updates do not remain queued. Their intended calendar advance is handled by world_tick_accum and multipliers, not by secretly catching up later. This distinction is what prevents a 64x-to-1x speed change from continuing to run a backlog of old physics work.

03A time budget is not a preemption mechanism

The spec targets a single tick at most 10 ms and total simulation work at most 12 ms per rendered frame on the floor machine. Predict available work from measured tick cost before starting another synchronous update. Still measure afterward: a tick that unexpectedly takes 30 ms cannot be interrupted by a check performed after it completes. Report the overshoot honestly, adjust future work and investigate the slow rule. Do not claim that a post-tick if statement guarantees 60 FPS.

04Make planning pure before touching the live loop

The lab below calculates a due count and retained fractional time only. Feed it known accumulated values and caps, including a long stall and cap zero. Production then combines that with pause, speed and predicted time budget. Keep tests for the actual early-stop path because k_plan and completed k can differ. Calendar debt remains owned by its accumulator until consumed by completed updates; the next lesson implements the allocation separately.

fn plan(accumulated_ms:u64, period_ms:u64, cap:u64)->(u64,u64) {
    assert!(period_ms>0);
    let due=accumulated_ms/period_ms;
    (due.min(cap), accumulated_ms%period_ms)
}
#[test]
fn capped_work_does_not_bank_physics_backlog() {
    assert_eq!(plan(30,50,2),(0,30));
    assert_eq!(plan(60,50,2),(1,10));
    assert_eq!(plan(260,50,2),(2,10));
    assert_eq!(plan(260,50,0),(0,10));
}

01

Trace uneven frames

Starting empty at period 50 ms, add 30,30,10,40 ms. How many normal ticks have elapsed?

Need a hint?

Carry fractional time between calls.

Worked solution

After totals 30,60,70,110 ms, two ticks have run and ten milliseconds remain. Frame count did not determine the result.

How to verify your result

The synthetic trace ends with two executed updates and 10 ms fraction.

02

Budget two ticks

A tick usually takes 9 ms. Should you plan two under a 12 ms frame simulation target?

Need a hint?

Reserve the complete predicted second tick, not only its start.

Worked solution

No. Two predicted ticks cost 18 ms. Plan one; a moving average is only a prediction, so still record actual duration and overshoot.

How to verify your result

The plan respects predicted combined cost.

03

Handle a stall

A window drag reports five seconds. What does the current elapsed clamp do?

Need a hint?

The spec deliberately limits accepted wall-clock delta.

Worked solution

It accepts at most 250 ms for that frame. The discarded real time is an intentional policy, so “no calendar drift” applies to accepted elapsed time, not every second of a stalled OS window.

How to verify your result

The stall test names the discarded-time policy.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

The game races after leaving fast-forward

What is happening: Whole overdue periods remain in physics elapsed state.

Try this: Discard whole capped periods and reset on speed change as specified.

Frames hitch despite a count cap

What is happening: Individual or combined tick cost exceeds the frame allowance.

Try this: Measure time as well as number of updates.

Scheduler tests are flaky

What is happening: They depend on sleeping real time.

Try this: Inject synthetic elapsed durations and tick costs.

Explain it without the example

Why can checking a time budget only after a tick still allow an over-budget frame?

Reasoning to compare

A synchronous tick cannot be interrupted by that later check. Prediction reduces risk but worst-case tick duration still needs measurement and a fallback policy.
