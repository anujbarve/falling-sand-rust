Draw one simulation cell

Draw a crisp four-by-four pixel sand cell at a position derived from grid coordinates.

Previously: Open the first window. Keep that working result available before starting this lesson.

Why we need this now

An empty window proves the graphics setup, but the first visible piece of our game is a cell. We will connect the named state from earlier lessons to rectangle arguments, keeping position, size and colour separate so none becomes an unexplained magic value.

Your result: Draw a crisp four-by-four pixel sand cell at a position derived from grid coordinates.

01Place drawing between clear and present

In the window loop, draw_rectangle must run after clear_background and before next_frame().await. Clearing after drawing would erase the cell; drawing after the yield belongs to the next loop’s timing and makes the structure harder to understand. State the order aloud: background, objects, yield.

The rectangle API accepts x, y, width, height and colour. x and y identify the top-left drawing position under this simple default camera. Width and height determine the footprint independently. A rectangle at x=48 with width=4 occupies a small region beginning there; x is not the right edge and width is not a second coordinate.

02Derive the location from a cell coordinate

Use column 12 and row 5. Multiply both by 4.0 after converting the integer coordinates to f32. The resulting drawing origin is 48,20. This conversion reuses the units reasoning we established in the terminal, so graphics does not introduce a different coordinate system by surprise.

The design distinguishes physical screen pixels, art pixels and simulation cells. Here one simulation cell occupies four by four physical pixels in our low-DPI teaching window. Later it will contain two by two art pixels, which are presented at twice their size. Today the rectangle is an occupancy footprint, not a claim that one cell is one display pixel.

03Use one flat material colour

The sand base colour is RGB 226,182,121. Draw it with full opacity and no outline, gradient, noise or glow. A flat block makes its exact footprint easy to inspect and respects the visual direction. Do not add shadows or texture simply because the example looks small. The point is to establish the unit that thousands of cells will share.

Move column to 13 and predict the horizontal displacement: four drawing units. Change row instead and predict vertical movement. When this fails, inspect conversion arguments before blaming the renderer. Separating x/y position from size makes those failures easy to locate.

04Keep state stable across redraws

For this still example, column and row can remain immutable outside the loop. Each frame reads the same values and redraws the same cell. Drawing does not store a persistent grain in the canvas; the program owns state and reconstructs its presentation.

If you place the state declarations inside the loop, this static result still looks correct, which can conceal a later bug. Once movement is added, reconstructing initial state each frame will reset it. Introduce the right lifetime now by declaring the coordinates before the loop, then drawing from them inside. We will group those coordinates into a Cell struct next.

use macroquad::prelude::*;

fn window_conf() -> Conf {
    Conf {
        window_title: "Rusty — learning".to_owned(),
        window_width: 1280,
        window_height: 720,
        high_dpi: false,
        window_resizable: false,
        sample_count: 1,
        ..Default::default()
    }
}

#[macroquad::main(window_conf)]
async fn main() {
    let column = 12;
    let row = 5;
    loop {
        clear_background(Color::from_rgba(15, 26, 51, 255));
        draw_rectangle(column as f32 * 4.0, row as f32 * 4.0,
            4.0, 4.0, Color::from_rgba(226, 182, 121, 255));
        next_frame().await;
    }
}

01

Separate movement from scaling

Double column but keep width and height unchanged.

Need a hint?

The first rectangle argument is position, not size.

Worked solution

Column 24 draws at x=96 while the footprint remains four by four. Doubling a coordinate moves the cell; it does not enlarge it.

How to verify your result

The rectangle moves horizontally and does not change size.

02

Find an erased cell

Move clear_background after draw_rectangle and predict the result before running.

Need a hint?

The later draw call covers earlier contents.

Worked solution

The clear erases the rectangle. Restore background clearing before object drawing. Render order is visible state, not just source organization.

How to verify your result

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

The cell is invisible

What is happening: It may be cleared afterwards, off-screen, or transparent.

Try this: Check draw order, coordinates and alpha independently.

The cell is huge

What is happening: Cell position or window dimensions may have been supplied as width/height.

Try this: Read the rectangle argument order and restore 4.0 sizes.

The cell stretches diagonally when changing one coordinate

What is happening: Both x and y may use the same variable.

Try this: Use column for x and row for y.

Explain it without the example

If column doubles, must the cell width double too?

Reasoning to compare

No. Position and size are separate arguments. The cell remains four pixels wide while its location changes.
