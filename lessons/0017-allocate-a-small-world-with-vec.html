Allocate a small world with Vec

Store a small world in a persistent vector and initialize it with air plus a stone floor.

Previously: Represent air, sand and stone. Keep that working result available before starting this lesson.

Why we need this now

A pile needs many occupied and empty slots. A Vec owns a runtime-sized sequence of same-type elements, which gives us a compact first grid. We will separate allocation, initialization and drawing so the world is not silently recreated every frame.

Your result: Store a small world in a persistent vector and initialize it with air plus a stone floor.

01Allocate slots, not separate loose variables

A 32 by18 teaching world has576 slots. vec![Material::Air; width * height] creates that many initialized elements. Because Material is Copy, the repeated initialization is straightforward. The vector’s length counts valid elements; its capacity describes reserved storage and is not a list of additional cells you may index.

Use usize for dimensions and indices local to this nonnegative buffer. World coordinates will stay signed until validated. That distinction avoids converting negative positions into enormous unsigned indices. The next lesson implements the conversion boundary rather than scattering unchecked casts around the renderer.

02Store dimensions with the collection

Define World with width,height,cells. Keeping dimensions beside storage makes row-major mapping meaningful. A vector alone does not know whether576 items represent32×18,24×24 or one long column. The World interface supplies that interpretation.

Construct the value once before the window loop. The renderer should borrow it rather than allocate a new world every redraw. A still scene might look identical even if reallocated repeatedly, but motion would reset and allocation cost would grow. Correct ownership and lifetime prevent that hidden failure before the simulation becomes busy.

03Initialize a visible floor

For row-major storage, the bottom row begins at index(height-1)*width. Fill exactly width elements from that start with Stone. The example prints the world as dots and hashes: dots are air, hashes are stone. Terminal rendering removes graphics setup from the first storage experiment.

Count the output rows and the stone cells. The floor should contain32 stone cells and no other occupied slots. This tiny count is already a useful invariant. If you accidentally fill the last column instead, the picture and counts expose different aspects of the bug.

04Return to pixels only after storage is correct

Once the terminal fixture is right, draw every valid slot by converting its column and row to drawing units. An empty slot should let the scene background show through. Do not draw a dark rectangle for every Air cell if that would erase sky gradients or cave backgrounds later.

The small vector is deliberately the first representation, not the final infinite world. Chunk storage will reuse the same owned-buffer idea at bounded size. By learning initialization, iteration and mutation on576 cells, we can later change storage organization without losing the simulation rules.

Walk through the working example

Complete focused example — src/main.rs

Download this worked example ↧

#[derive(Clone, Copy, PartialEq)]
enum Material { Air, Sand, Stone }
struct World { width: usize, height: usize, cells: Vec<Material> }
fn main() {
    let mut world = World { width: 8, height: 4,
        cells: vec![Material::Air; 8 * 4] };
    let floor = (world.height - 1) * world.width;
    for column in 0..world.width { world.cells[floor + column] = Material::Stone; }
    for row in 0..world.height {
        for column in 0..world.width {
            let mark = match world.cells[row * world.width + column] {
                Material::Air => '.', Material::Sand => 's', Material::Stone => '#',
            };
            print!("{mark}");
        }
        println!();
    }
}

Read what each part does

  1. The terminal fixture is intentionally small enough to count by eye.
  2. World owns the vector; dimensions give the flat data its grid interpretation.
  3. A production constructor should validate nonzero/overflow-safe dimensions.

01

Resize coherently

Change the fixture to32×18.

Need a hint?

Dimensions and allocation must agree.

Worked solution

Use width32,height18 and allocate width*height elements, preferably through a constructor that receives both values. The floor then starts at544 and contains32 cells. Avoid changing only the dimensions while leaving the allocation at32.

How to verify your result

The vector length is576 and the final row contains32 stones.

03

Detect reinitialization

Move construction inside a simulated repeat loop and explain why state edits disappear.

Need a hint?

A newly initialized vector contains only the initial values.

Worked solution

Move World construction back outside the repeating update/render loop. Persistent state must outlive an individual frame.

How to verify your result

An update remains present on the following iteration.

When it goes wrong

Start with the observed symptom. Change one assumption at a time instead of pasting fixes until the error disappears.

index out of bounds

What is happening: Allocation length and dimensions disagree or a coordinate is invalid.

Try this: Check length, width,height and mapping separately before indexing.

The floor is a vertical stripe

What is happening: Rows and columns were interchanged in the index formula.

Try this: Trace one bottom-row index using row*width+column.

State resets each frame

What is happening: The world is reconstructed inside the frame loop.

Try this: Construct once and borrow it for drawing.

Explain it without the example

Why should the vector belong to the world instead of draw_world creating it each frame?

Reasoning to compare

It is persistent simulation state. Drawing reads that state; allocating a new vector in drawing would replace or disconnect the simulated world.
